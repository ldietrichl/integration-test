# Локальный стенд data-operator EXPLAB-2974

Запускается сервис из архива `06fd6acb646`, Apache Ignite, Kafka и контролируемые заглушки dictionaries/experiments. Сервисный Java-код не изменяется. Тесты используют существующие REST steps проекта через `RestFlows` и сохраняют строгие ожидания контракта v7.

## Запуск и проверка

Из корня проекта в PowerShell:

```powershell
.\local-services\data-operator-explab-2974\start.ps1 -Profile compatible
.\local-services\data-operator-explab-2974\run-functional.ps1 -Profile compatible
.\local-services\data-operator-explab-2974\report.ps1 -Profile compatible
.\local-services\data-operator-explab-2974\stop.ps1 -Profile compatible
```

`run-functional.ps1` выполняет новый полный набор: 70 функциональных + 103 негативных варианта. Для каждой функциональной проверки создаются свои UUID-точки и объекты через реальный REST-контроллер, проверяется загрузка, затем выполняется расчёт и cleanup. Локальный runner задаёт настройки fixture из выбранного профиля; тот же тестовый Java-код в корпоративной среде читает её реальные настройки. [Результаты 173 проверок и корпоративная поставка](../../docs/services/data-operator/EXPLAB_2974/FUNCTIONAL_RUN_20260907.md).

`run-tests.ps1` остаётся отдельным запуском только 103 негативных вариантов; `test-fixtures.ps1` — прежним одиночным D1. Они не заменяют новый полный набор. Если JVM была прервана, сохраните манифесты и сначала восстановите собственные данные по инструкции `LinksFixtureRecovery`; не очищайте весь Ignite.

`start.ps1 -Pull` предварительно скачивает образы. `start-compatible.ps1` остаётся короткой обёрткой для `start.ps1 -Profile compatible -Pull`. Отдельные аргументы версий/портов и `compatible.env` заменены общим [profiles.json](profiles.json). Для исходного стенда используется `-Profile local`.

| Профиль | Ignite | Kafka | HTTP сервиса | Заглушки | Ignite port | Kafka port | Allure |
|---|---|---|---|---|---|---|---|
| local | 2.17.0 | 4.0.2 | 18074 | 18075 | 10874 | 19074 | 18076 |
| compatible | 2.18.0 | 3.9.1 | 18084 | 18085 | 10884 | 19084 | 18086 |

Все порты публикуются только на `127.0.0.1`. Swagger доступен по `/api/v2/data-operator/swagger-ui.html`. Каждый профиль имеет собственный Compose project, каталог работы, процессы и отчёты. В рабочем каталоге сохраняется `stand.json`; его нельзя случайно использовать с другим профилем. При изменении версий/портов в профиле выбирайте новый каталог `-Work`.

Пути по умолчанию вычисляются относительно корня проекта и соседнего каталога `BACK`. `Work`, `Source` и `Libraries` позволяют их переопределить. Java/javac берутся из `JAVA_HOME` или PATH, Maven — из PATH, Python — из установленного Codex runtime или PATH. Для отдельных исполняемых файлов доступны параметры скриптов и переменные `EXPLAB_JAVA`, `EXPLAB_JAVAC`, `EXPLAB_PYTHON`, `EXPLAB_MVN`. Нужен JDK 17.

## Границы ответственности

| Компонент | Назначение |
|---|---|
| `profiles.json`, `Stand.psm1` | Общая конфигурация, управление процессами, блокировка одновременных операций, готовность и чтение состояния кэшей. |
| `start.ps1`, `prepare_service.py`, `verify_service.py` | Подготовка отдельной копии, проверка исходников и зависимостей, сборка и запуск сервиса. Повторное использование JAR проверяется по SHA-256 POM/JAR. |
| `compile_tests.py`, `test-sources.json`, `test-libraries.lock.json` | Явная область компиляции, фиксированный classpath с проверкой SHA-256, новый каталог классов при каждой сборке. |
| `DataOperatorLinksValidationFlowTest`, `LinksHttpEvidence` | Flow/rest-сценарии, строгие assertions, структурированная запись фактического HTTP-обмена до проверки ответа. |
| `LocalScenarioRunner.java` | Исполнение через JUnit Platform и структурированные вердикты. Ожидаемое число вариантов берётся из каталога запросов. |
| `run-tests.ps1` | Проверка предусловий, манифест прогона, сохранение состояния/лога в `finally`, запуск офлайн-анализа. |
| `analyze_run.py` | Анализ JSON-артефактов без обращения к сервису. Разделяет нарушения контракта и неполный/инфраструктурный прогон; сравнивает сценарий + вариант. |
| `report.ps1`, `stop.ps1` | Показ выбранного отчёта и остановка только процессов/контейнеров выбранного профиля. |

Процесс проверяется по PID, времени создания и командной строке. Занятый порт не считается доказательством готовности нашего процесса. При перезапуске старые логи сохраняются под именами `.bak`; исторические результаты не перезаписываются. Образы и тома не удаляются. Ignite работает в памяти; после остановки его контейнера начальные справочники заново загружаются при запуске сервиса.

## Зависимости тестов

Текущий classpath содержит **121** явно зафиксированную библиотеку вместо прежнего перебора 176 JAR из разных задач. Jackson согласован на **2.17.2**, JUnit Jupiter **5.10.3** — с Platform **1.10.3**, Groovy — **4.0.22**. Дубликаты, Gradle-плагины и посторонние AI/Spring runtime-библиотеки исключены. При отсутствии нужного файла или несовпадении SHA-256 сборка останавливается с указанием библиотеки; другая версия из кэша не подставляется.

Локальный корпоративный комплект остаётся `lib-1.10.3-beta`, Perfeccionista — 0.9.3-Beta. Различие со штатным Gradle, где указана 0.9.4-Beta, явно сохраняется. Сборка через локальный JUnit-адаптер не означает успешный запуск корпоративного Gradle. AI-agent исходники не входят в REST-область компиляции.

## Результаты и диагностика

Рабочий каталог по умолчанию: `BACK/06_temp_work/explab-2974-<профиль>`; имя исходного профиля — `explab-2974-local`.

Каждый `run-*` содержит:

- `run-manifest.json`: выбранная конфигурация, фактические image ID, хэши сборки сервиса/тестов и состав области компиляции.
- `results.json`: вердикты JUnit, ожидаемое число вариантов, сбои контейнеров тестов.
- `http-evidence/*.json`: запрос/ответ каждого варианта с JUnit ID. Эти же обмены прикладываются к Allure.
- `results-with-http.json`, `analysis.json`: объединённые результаты, распределение ответов, сравнение и инфраструктурные проблемы.
- `pre-run-state.json`, `post-run-state.json`: состояние сервиса и кэшей до/после запросов.
- `service.stdout.log`, `service-test-interval.log`, `service-errors.log`: полный снимок и выделенный тестовый интервал.
- `allure-results`, после `report.ps1` — `allure-report`.

Коды завершения `run-tests.ps1`: **0** — все проверки прошли, **1** — падения проверок контракта, **2** — неполное исполнение/ошибка инфраструктуры или сбора доказательств. Ошибка компиляции завершает скрипт исключением до тестового запуска. Отсутствие ответа не превращается в якобы полученный HTTP 500. Повреждённый или не-JSON ответ сохраняется без падения анализатора.

Сравнение с предыдущим прогоном:

```powershell
.\local-services\data-operator-explab-2974\run-tests.ps1 -Profile compatible `
  -BaselineResults A:/Codex/Functional/BACK/06_temp_work/explab-2974-compatible/run-20260907-192019/results-with-http.json
```

Повторить анализ сохранённых результатов можно при выключенном стенде:

```powershell
python .\local-services\data-operator-explab-2974\analyze_run.py --run <каталог-прогона>
```

После рефакторинга выполнены 103/103 варианта: **0 passed, 103 failed**, HTTP 500 — 77, HTTP 200 — 24, HTTP 400 с неверной схемой — 2. Инфраструктурных ошибок нет; каждый HTTP-статус совпал с прежним прогоном. [Проверка архитектурных изменений](../../docs/services/data-operator/EXPLAB_2974/HARNESS_ARCHITECTURE_20260907.md).

## Ограничения локального контура

Закрытые `com.sbt.ignite` заменены Apache Ignite только в локальном POM, SE security-модули исключены. dictionaries/experiments — заглушки используемых клиентом контрактов с начальной точкой MAPPER и изолированными наборами D1. H2 работает в памяти внутри data-operator для JPA-конфигурации; метод links использует Ignite.

103 сценария `run-tests.ps1` проверяют входной контракт и не создают объектов/экспериментов. Перед их запуском нужны пустые кэши объектов, полей и актуализации; имеющиеся данные скрипт не удаляет. `test-fixtures.ps1` отдельно создаёт D1 через REST и запускает позитивный flow/rest SL-01. Его `finally` удаляет только записи двух собственных точек. Остальные позитивные сценарии плана ещё не реализованы.

TLS/mTLS, Ignite SE и сквозная работа настоящих соседних сервисов этим стендом не подтверждаются. [Недостающие корпоративные компоненты](../../docs/services/data-operator/EXPLAB_2974/INFRASTRUCTURE_REQUIREMENTS.md). Jira/TestOps не используются.

Регрессионные проверки самого комплекта:

```powershell
python -m unittest discover -s local-services/data-operator-explab-2974 -p test_harness.py -v
.\local-services\data-operator-explab-2974\test-stand.ps1
```

## Заглушки D1 и подготовка данных

Версия `EXPLAB-2974-D1-v2`, здоровье: `http://127.0.0.1:18085/health` для compatible. Обновление уже работающего процесса без остановки SUT/Kafka/Ignite:

```powershell
.\local-services\data-operator-explab-2974\restart-dependencies.ps1 -Profile compatible
.\local-services\data-operator-explab-2974\test-fixtures.ps1 -Profile compatible
```

| Маршрут заглушки | Поведение |
|---|---|
| GET `/api/v2/dictionaries/so-data-source-dict` | Форма из ФП: схемы JSON-объекты; фильтр `splittingPoint` с повторением параметра или через запятую. |
| POST того же пути | Совместимость с Feign из `06fd6acb646`: тело `{ "splittingPoint": "..." }`, схемы JSON-строки. Фильтр соблюдается. |
| GET `/api/v2/dictionaries/so-param-dict` | Полные метаданные MAPPER и всех активных тестовых точек, включая object/parent keys и JSONPath. |
| GET `/api/v1/experiments/splits` | Два синтетических сплита E1/E2, родительская связь и статусы; фильтр `ids` int64. |
| POST `/__fixtures`, GET/DELETE `/__fixtures/{leaseId}` | Только локальное управление набором D1. Создание: `{ "dataSet": "D1" }`. DELETE удаляет определения из заглушки; очисткой SUT управляет lifecycle. |

Нет совпадений — `[]`; неправильные типы/JSON — 400, неизвестные маршруты — 404, неподдерживаемые методы известных маршрутов — 405. Это оговорённое поведение тестовой заглушки, а не подтверждение всех ошибок корпоративных API. Сам `/splitting-objects-links` не заглушается.

Каждый набор получает `EXPLAB2974_<uuid>_SP1/SP2`. Данные соответствуют D1 тест-плана: 6 объектов SP1 + X из SP2, полный JSON Schema. Сервис загружает параметры через `PUT /update-dicts`; семь объектов — через REST `POST /kafka/stub/{point}` с корнем `cjConfig`. Эксперименты не записываются в SUT: links получает их идентификаторы/условия в запросе.

В архиве обновление **источников** жёстко запрашивает только `MAPPER`. Поэтому `FixtureCacheTool.java` устанавливает две записи source metadata через Ignite thin client — это явно ограниченный fallback. Заглушка не выдаёт чужие точки в ответе на фильтр MAPPER. REST удаления объектов в архиве/проанализированной ФП не найден: тот же helper точечно удаляет собственные ключи из object, field, actualization, param и data_source caches, проверяя UUID набора и текущее значение записи. Произвольная очистка/MAPPER запрещены. Классы/библиотеки helper берутся из проверенного JAR самого сервиса; Java-код SUT не меняется.

Наборы заглушки переживают перезапуск в `Work/dependency-fixtures.json`, вызовы зависимостей журналируются без тел/заголовков в `dependency-requests.jsonl`. До изменения SUT сохраняется `run-fixture-*/fixture-manifest.json`; рядом остаются HTTP-обмены подготовки, состояние загруженных данных и `fixture-cleanup.json`. Принудительное завершение ОС не исполняет `finally`; восстановление по сохранённому манифесту:

```powershell
.\local-services\data-operator-explab-2974\cleanup-fixture.ps1 -Profile compatible -Manifest <полный-путь-к-fixture-manifest.json>
```

Команда проверяет принадлежность манифеста стенду и берёт общую блокировку. Повторная очистка допустима. Результат считается завершённым только после проверки нулевого остатка во всех пяти кэшах и освобождения набора в заглушке. Загруженные данные не оставляются после успешной проверки.

Проверки HTTP-контрактов заглушек:

```powershell
python -m unittest discover -s local-services/data-operator-explab-2974 -p test_dependency_stub.py -v
```
