# TestOps для выбранных тестов

Задачи группы **testops** готовят и отправляют Allure-результаты тех тестов, которые вы выбрали в IDEA или через Gradle `test --tests`. Они не запускают тесты и не выбирают фичи по именам: состав отчёта определяется файлами в исходном raw-каталоге.

Среда берётся из сохранённого `src/test/resources/test.properties`:

```properties
env=dev
```

Для ИФТ установите `env=ift`. Используйте корень проекта как Working directory в IDEA и терминале. Значения `-Denv`, `-Penv` и `ENV` не заменяют файловый выбор среды. Настройки сервисов, Kafka, Ignite и TestOps должны соответствовать выбранной среде.

Если нужные результаты уже получены, перед первой отправкой **не запускайте очистку**. Дождитесь завершения тестов, проверьте выбранную среду и исходный каталог, затем переходите к подготовке и загрузке. Очистка перед запуском нужна только для нового независимого набора, когда предыдущие результаты уже сохранены или отправлены.

## Задачи и каталоги

После **Reload All Gradle Projects** откройте **Tasks → testops**:

| Задача | Действие |
| --- | --- |
| `cleanTestOpsResults` | Удалить подготовленный набор текущей среды и распознанные Allure-файлы из разрешённого raw-каталога перед новым выбранным набором |
| `prepareTestOpsResults` | Проверить raw-результаты и собрать набор для TestOps без отправки |
| `testOpsUpload` | Выполнить подготовку, затем загрузить набор с действующими настройками TestOps |

При стандартной настройке исходный каталог — `build/allure-results`. Явный `testOpsSourceResultsDir` выбирает другой источник для сборщика; без него используется `allure.results.directory`, разрешённый текущим Gradle-вызовом, а при отсутствии этой настройки — `build/allure-results`. Обычная задача `test` использует ту же настройку Allure. Если путь был задан только в IDEA Run Configuration, передайте фактический каталог сборщику явно: отдельный Gradle-вызов не получает VM options этой конфигурации.

Подготовленный набор сохраняется отдельно по средам:

```text
build/testops-results/
  dev/
    allure-results/
    manifest.json
  ift/
    allure-results/
    manifest.json
```

`manifest.json` описывает исходный каталог и состав подготовленного набора. Raw-каталог `build/allure-results` общий для прямых запусков; после сохранения или отправки предыдущих результатов очистите его перед новым набором и перед сменой среды, чтобы результаты прежних фич не попали в следующий отчёт. Обычный `clean` удаляет весь `build`, включая подготовленные TestOps-наборы и регрессионные результаты/манифесты. Пользовательский внешний raw-источник является входом сборщика и обычным `clean` не очищается.

Четыре выделенных регресса используют группу **regression** и собственные каталоги. Их загрузка — `regressionTestOpsUpload`, подготовка — `prepareRegressionTestOpsResults`, очистка — `cleanRegressionResults`. В частности, `dataOperatorRegression` сохраняет свои результаты и фикстуры по правилам [инструкции регрессов](../project/REGRESSION_TASKS.md).

## Запуск через IDEA

Следующий порядок предназначен для нового набора. Для уже имеющихся результатов начинайте с подготовки и загрузки без очистки.

1. Сохраните нужное `env` и подготовьте настройки выбранных тестов.
2. Выполните **Tasks → testops → cleanTestOpsResults** и дождитесь завершения.
3. В Project выберите тестовую папку/package, класс или метод и выполните **Run Tests / Run**. Для JUnit-конфигурации укажите Working directory = `$PROJECT_DIR$`.
4. После завершения тестов выполните **prepareTestOpsResults** для проверки набора либо сразу **testOpsUpload**, который сам выполняет подготовку.
5. После отправки или сохранения нужных результатов выполните **cleanTestOpsResults**, когда набор больше не нужен.

Очистку запускайте отдельно до нового набора тестов. Между запуском выбранных тестов и подготовкой/загрузкой не выполняйте `clean` или `cleanTestOpsResults`: они удаляют raw-результаты. Подготовку, загрузку и последующую очистку выполняйте последовательно, после завершения активных тестов; перед следующей операцией дождитесь завершения предыдущей.

## Выбор тестов через PowerShell

Откройте терминал в корне корпоративного проекта и настройте кодировку для русского вывода:

```powershell
Set-Location 'C:\Work\IdeaProjects\integration-test'
chcp 1251 > $null
$enc = [System.Text.Encoding]::GetEncoding(1251)
[Console]::InputEncoding = $enc
[Console]::OutputEncoding = $enc
$OutputEncoding = $enc
```

Перед новым независимым набором, после сохранения или отправки прежних результатов:

```powershell
.\gradlew.bat cleanTestOpsResults --offline --console=plain
```

Затем выполните один из вариантов выбора. Пакет общих REST-проверок data-operator:

```powershell
.\gradlew.bat test --offline --console=plain --rerun-tasks `
  --tests 'ru.sber.qa.dataoperator.regression.*'
```

Все тесты фичи EXPLAB-2411:

```powershell
.\gradlew.bat test --offline --console=plain --rerun-tasks `
  --tests 'ru.sber.qa.dataoperator.EXPLAB_2411.*'
```

Один метод:

```powershell
.\gradlew.bat test --offline --console=plain --rerun-tasks `
  --tests 'ru.sber.qa.dataoperator.EXPLAB_2411.DataOperatorReturnIdsValidationFlowTest.nonBooleanReturnIdsShouldBeRejected'
```

Заменяйте фильтр на нужный package, класс или метод. `--rerun-tasks` обеспечивает фактический повторный запуск после очистки raw-каталога. Обычная задача `test` сохраняет штатные правила допуска и исключения тестов проекта; фильтр `--tests` не отменяет их.

Несколько фич можно намеренно объединить: укажите несколько `--tests` в одном вызове либо последовательно выполните выбранные запуски без очистки между ними. Все результаты из raw-каталога войдут в набор, включая повторные запуски одного теста. Если нужен новый независимый отчёт, сначала сохраните или загрузите текущий набор, затем выполните `cleanTestOpsResults`.

Эти задачи не включают фикстуры EXPLAB-2974 автоматически и не меняют настройки ИФТ. При прямом запуске тестов с фикстурами используется их обычная конфигурация. Для подготовленного полного регресса data-operator используйте `dataOperatorRegression` и группу **regression**.

## Подготовка и отправка

Для уже полученных результатов начинайте здесь, без предварительной очистки. Дождитесь завершения тестов. Следующие команды выполняйте по очереди; `testOpsUpload` самостоятельно повторяет подготовку перед загрузкой.

Проверить результаты без загрузки:

```powershell
.\gradlew.bat prepareTestOpsResults --offline --console=plain
```

Проверить подготовку и параметры загрузки без отправки:

```powershell
.\gradlew.bat testOpsUpload --offline --console=plain '-PallureDryRun=true'
```

Загрузить:

```powershell
.\gradlew.bat testOpsUpload --offline --console=plain
```

Выполняйте загрузку отдельной командой и после завершённого тестового прогона с ненулевым кодом Gradle: failed/broken результаты сохраняются и должны попасть в отчёт. Не связывайте загрузку с успешным завершением тестов через `&&`. Если JVM оборвалась и результаты неполны, проверка укажет, какие файлы или ссылки нужно проверить.

Подготовка проверяет JSON, UUID, ссылки контейнеров на результаты и наличие вложений. Метка `testEnvironment` должна соответствовать `test.properties`. Старый результат только с меткой `testStage` принимается при совпадении ожидаемого stage с предупреждением: эта метка может быть переопределена отдельно и не различает `ift` и `ift-dm`. Если нет ни `testEnvironment`, ни `testStage`, сборщик отклоняет результат и просит повторный запуск с актуальным reporting extension. Среда не определяется по имени теста, каталогу или текущему значению `env` вместо отсутствующих метаданных.

Сборщик сохраняет исходные статусы и отдельные результаты повторных запусков. Он не превращает failed/broken в passed и не объединяет дубликаты одного теста. Ошибки структуры или конфликтующие файлы требуют исправления исходного набора.

`--offline` управляет разрешением Gradle dependencies. Для фактической загрузки нужны корпоративная сеть, доступный `allurectl` и заполненные настройки TestOps. Секреты в приведённые команды добавлять не требуется.

## Другой исходный raw-каталог

Если Allure писал результаты в другой каталог, передайте его при подготовке или загрузке:

```powershell
.\gradlew.bat prepareTestOpsResults --offline --console=plain `
  '-PtestOpsSourceResultsDir=C:/Work/test-results/EXPLAB-2411/allure-results'
```

```powershell
.\gradlew.bat testOpsUpload --offline --console=plain `
  '-PtestOpsSourceResultsDir=C:/Work/test-results/EXPLAB-2411/allure-results'
```

`testOpsSourceResultsDir` выбирает существующий источник для сборщика. Он не меняет место записи запускаемых тестов. Передавайте тот же путь при каждой подготовке и загрузке этого набора. Без параметра сборщик наследует разрешённый Gradle-путь `allure.results.directory`, стандартное значение которого — `build/allure-results`.

`cleanTestOpsResults` разрешает автоматическую очистку raw только в `build/allure-results` или корневом `allure-results` проекта. Из выбранного каталога удаляются распознанные Allure result/container JSON, вложения и метаданные; неизвестные файлы и сам raw-каталог сохраняются. Подготовленный набор текущей среды `build/testops-results/<env>` удаляется целиком. Эта адресная задача сохраняет `build/regression-results`, `build/regression-fixtures` и манифесты фикстур; обычный `clean` удаляет их вместе со всем `build`.

Для любого нестандартного source, в том числе внутри проекта, задача отказывается от очистки и сохраняет подготовленный набор. После отправки или сохранения результатов очистите такой source отдельно вручную. Чтобы затем удалить подготовленный набор через `cleanTestOpsResults`, выберите разрешённый стандартный raw-путь; учитывайте, что его распознанные Allure-файлы также будут удалены.
