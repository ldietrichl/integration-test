# Постоянное хранилище корпоративного Ignite

Дата: 2026-09-29.

## Что теперь переносить

Подготовленная рабочая директория:
`<workspace>/BACK/00_projects/integration_test_ready_20260929`.

При переносе на корпоративную машину каталог `runtime` обязателен:

```text
integration-test/
  runtime/
    corporate-ignite-runtimes/
      data-operator-explab-2974/<runtime-sha256>/
      ignite-client/<runtime-sha256>/
    corporate-ignite-libraries/
      <library-sha256>/lib/
  build/
    ignite-helper-classes/
```

`runtime` содержит установленный корпоративный пакет. Он исключён из Git, но
не должен исключаться из поставки рабочей директории. Архив только из отслеживаемых
Git файлов не заменяет такую поставку. Переносите обе подпапки вместе, не один lock.

`build` содержит пересоздаваемые классы и отчёты. Библиотеки Ignite больше не
требуют сохранения `build`. Однако журналы восстановления незавершённых фикстур
в `build` по-прежнему важны: перенос runtime не даёт разрешения их удалять.

## Изменения

- Два существующих пакета перенесены из `build` в `runtime`.
- Относительный путь от lock до общих библиотек не изменён.
- Lock-файлы, helper-исходники, JAR и runtime SHA-256 сохранены.
- В `src/test/resources/ignite.properties` изменён только префикс каталогов
  runtime для DEV и IFT. Версии библиотек, env, адреса, SSL и секреты не менялись.
- Обновлены оба `latest-runtime.txt`; selector не выбирает профиль автоматически.
- `prepareCorporateIgniteClient` и `prepareExplab2974CorporateClient` публикуют
  новые пакеты в постоянное хранилище. Их выполнение требует корпоративных
  репозиториев и локально не запускалось.
- Java-адаптер разрешает библиотеки нового хранилища. Старые schema-2 пакеты внутри
  `build/corporate-ignite-runtimes` поддерживаются только при явном выборе этого пути.
  Автоматического поиска другого пакета или переключения окружения нет.
- Обычный `clean` не затрагивает `runtime`. Пересечение настроенного buildDirectory
  с `runtime` запрещено. Скрипт `Clean-IntegrationTest.ps1` также защищает `runtime`.

## Установка

1. Остановите прогоны и Gradle-задачи. Сохраните корпоративную директорию целиком
   в отдельную резервную копию, включая секреты, настройки и recovery-журналы.
2. Перенесите обновлённую подготовленную рабочую директорию. Не ограничивайтесь
   копированием `runtime`: нужны также обновлённые Java-адаптер, Gradle-скрипты
   и пути в `ignite.properties`.
3. При объединении с корпоративной копией сохраняйте её действующие адреса,
   сертификаты и секреты. Меняются только согласованные пути runtime.
   Не заменяйте пакет незавершённой фикстуры другим: сначала завершите recovery.
4. В IDEA нажмите Reload All Gradle Projects.
5. Запустите `service → prepareIgniteHelpers`; для probe отдельно
   `service → prepareIgniteProbe`. Они проверяют пакет и компилируют helper,
   не открывая соединения.
6. После успешной подготовки и проверки профиля запускайте нужный регресс.
   Успешная подготовка не подтверждает правильность подключения или готовность стенда.

После разрешённого `clean` задачи подготовки пересоздадут
`build/ignite-helper-classes` из сохранённого пакета. Скачивать JAR повторно не нужно.
Не объединяйте `clean` с тестами или Ignite-подготовкой в одном запуске.

## Локальные проверки

Отчёт и логи: `docs/project/ignite-runtime-storage-validation`.
Проверка очистки выполняется на отдельной временной копии, не на корпоративном
проекте и не на основной подготовленной директории.

Офлайн-проверка использует локальные библиотеки платформы. Из-за отсутствующего
в локальном кэше optional Fabric8 HTTP provider временный init заменяет classpath
только двух задач подготовки helper на compileClasspath. Корпоративные определения
задач сохраняют runtimeClasspath. Это не подтверждает корпоративную runtime-среду.
Тесты, подключения к стенду/БД и отправка в TestOps не выполняются.
