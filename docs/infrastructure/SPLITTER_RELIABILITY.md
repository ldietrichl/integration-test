# Надёжность запуска и выгрузка завершённых стадий

EXPLAB-2984 (06.10.2026): четыре функциональные задачи Reactions/Mapper Rest/Kafka
подключены через каталог и используют общие read-only lease gates, приватную
JVM-диагностику и `build/allure-results`. `explab2984LocalChecks` изолирована в
`build/local-checks/explab2984`; отдельного uploader нет. КАП наблюдается через
SplitterKafkaReportClient с ограничениями BoundedKafkaObservation и фиксацией
offsets до split. Проверка REST и КАП независима в пределах одного теста.
Команды, локальная верификация и границы покрытия —
`docs/services/splitter/EXPLAB_2984/README.md`; стендовый результат пока не подтверждён.

Патч splitter-reliability-20261005-v1 применяется поверх архитектурного рефакторинга
и задач восстановления блокировки. Бизнес-проверки EXPLAB_2690, EXPLAB_2885 и
EXLAB_2891, включая уточнения АК, не меняются.

## Kafka

SplitterKafkaConfigLoadClient обрабатывает только текущую порцию poll. Буфер клиента
очищается до poll и в finally после обработки. Закрывает кешируемый KafkaConsumerClient
сам KafkaService при завершении теста; ручного close в сценарии нет.

Диагностическая выборка: максимум 10 сообщений и 32 КиБ UTF-8 плюс короткая сводка.
Перед парсингом проверяется размер сообщения: максимум 1 МиБ. Для JSON действуют
ограничения глубины 64, длины числового токена 128 и обхода 16384 узлов. Невалидные,
слишком большие и чрезмерно сложные сообщения не участвуют в поиске сигнала.
Если подходящий сигнал не найден, тест завершается ошибкой ожидания; пропуск
сообщения никогда не превращается в успешную проверку. Сохраняется исходный порядок
поиска сигналов внутри JSON. Лимиты ограничивают работу наблюдателя после poll,
но не отменяют ограничения fetch и памяти самого Kafka-клиента.

## JVM и приватный журнал

У поддержанных задач запуска трёх заявок heap по умолчанию 1024m; переопределение:
`-PsplitterTestHeap=2g`. GC-логи (3 файла по 8 МиБ) и heap dump при OOM сохраняются
в `.workload-recovery/jvm/<task>-<uuid>/` с правами текущего пользователя.
Heap dump не имеет малого фиксированного лимита; его размер может быть сопоставим с heap.
Эта папка не входит в Allure, TestOps и корпоративный ZIP.

Общий Fabric8 сохраняет приватные preimage и журнал в
`.workload-recovery/private/<env>/<uuid>/`. `stand.artifacts.directory` разрешён
только внутри `.workload-recovery/private`, пути через ссылки отклоняются.
Перед изменением пишется WRITE_INTENT с namespace/context/UID, владельцем блокировки,
путём поля, исходным и новым значениями; файл сбрасывается на диск до PATCH.
После проверочного GET записывается WRITE_CONFIRMED. Восстановление и удаление пода
также имеют отдельные записи намерения и подтверждения. Полный журнал не прикладывается
к Allure. Существующие ConfigMap, runtime metadata и текстовые логи пода сохраняются.

Стандартный Gradle clean удаляет build, но не `.workload-recovery`.
Журнал содержит исходные значения ConfigMap: не отправлять его в TestOps и не коммитить.
Он помогает ручному восстановлению после аварии; автоматического проигрывания журнала,
автоматического снятия блокировки и гарантии rollback после уничтожения JVM нет.
Снятие lease через explab2885ReleaseLease по-прежнему не восстанавливает конфигурацию.

## Preflight

В Tasks > tickets доступны `explab2885StandCheck` (REACTIONS) и
`explab2891StandCheck` (MAPPER). Проверка читает Deployment/ConfigMap через общий
Fabric8. При чужой или оставшейся после аварии блокировке Test task не стартует:
одна ошибка preflight вместо каскада упавших сценариев. До начала теста блокировка
может появиться у другого запуска, поэтому атомарный захват внутри тестов сохранён.

Автоматические зависимости настроены для splitterRestRegression,
splitterKafkaRegression, задач explab2690* и exlab2891MapperRest/Kafka/Fresh.
У стандартной test учитываются явно заданные фильтры трёх заявок. Harness/SDK/Oracle
не требуют проверки стенда. Имена ресурсов по умолчанию splitter-{mapper,reactions}-service
и одноимённая ConfigMap плюс ConfigMap с суффиксом -lib. Для другой топологии:

```powershell
.\gradlew.bat explab2885StandCheck '-Pworkload.reactions.deployment=<deployment>' '-Pworkload.reactions.configmaps=<service-map>,<rules-map>'
```

Аналогичные свойства `workload.mapper.*` доступны для MAPPER. Эти свойства меняют
только цель preflight; настройки самих сценариев должны указывать на те же ресурсы.
Среда берётся из существующего test.properties. Параметры stand.* передаются JavaExec.

## Allure и TestOps

После остановки Test Executor коллектор сверяет JUnit XML и summary. Наличие
ошибки Gradle Test Executor делает `completed=false`, `executionCompleted=false`,
сохраняет executorErrors и pending. `completed` означает завершение выполнения,
а не отсутствие failed. Коллектор также сверяет количество и статусы бизнес-тестов.
Это не доказательство запуска всех задуманных фильтром сценариев: отсутствующие
сценарии при аварии нельзя считать passed или обычными skipped.

Обычные prepareTestOpsResults/testOpsUpload сохраняют строгую блокировку при pending.
Для осознанной выгрузки только завершённых стадий добавлены две задачи в tickets:

```powershell
.\gradlew.bat prepareCompletedTestOpsResults '-PtestOpsCompletedStages=splitter-rest,mapper-rest,mapper-kafka'
Get-Content build\completed-testops\dev\manifest.json
.\gradlew.bat completedTestOpsUpload '-PtestOpsCompletedStages=splitter-rest,mapper-rest,mapper-kafka' -PallureDryRun=true
.\gradlew.bat completedTestOpsUpload '-PtestOpsCompletedStages=splitter-rest,mapper-rest,mapper-kafka'
```

Используются существующие настройки TestOps и allurectl. Список обязателен, исключения
явно перечислены в manifest.json. Допустимы также `splitter-kafka` и `2690-core`.
Splitter выбирается из последнего архивного запуска соответствующего режима;
MAPPER и 2690 — по последнему JUnit соответствующей задачи, классу, режиму и временному
интервалу. Повторные совпадения, несовпадение JUnit/Allure, незавершённые контейнеры,
недостающие вложения и изменения исходных файлов блокируют подготовку.

Копируются выбранные result/container JSON и их вложения; затем применяется общий
строгий валидатор. Итог: `build/completed-testops/<env>/allure-results` и manifest.
Исходные результаты, архивы и pending не удаляются. При ошибке прежний подготовленный
пакет сохраняется. Каждая новая попытка upload повторно валидирует выборку.
Подготовку/выгрузку выполнять отдельной командой, без clean и тестов в том же вызове.
Эти задачи не изменяют глобальный источник обычного testOpsUpload.

## Исправление v2: журнал и состав прогона

В v1 корпоративный `regression.gradle.kts` переопределял `stand.artifacts.directory`
каталогом внутри build. Защита приватного журнала отвергала его, поэтому 56 сценариев
2885 в каждом режиме завершались BROKEN ещё на подготовке. В v2 производители пути
в REST/Kafka и workloadContractChecks используют `.workload-recovery/private`.
Журнал сохраняется после clean. Ошибка открытия содержит фазу и безопасную причину;
проверка ACL и запрет записи через перенаправленные пути сохраняются.

Четыре класса `Precalc2885DiagnosticsTest`, `Precalc2885EvidenceScopeTest`,
`Precalc2885OracleTest`, `Precalc2885ReportingTest` исключены из функциональных
Gradle Test-задач. Их 43 проверки запускаются отдельно:

```powershell
.\gradlew.bat explab2885LocalChecks
```

Задача находится в tickets; результаты — `build/local-checks/explab2885`,
а не общий `build/allure-results`. Существующие архивы автоматически не переписываются.
Старые 99 результатов режима (43 локальных + 56 BROKEN) не доказывают проверку
предрасчёта. Для сравнения нужен новый запуск после установки v2.

В шести MAPPER-параметрах 2690 исправлено ожидание ALL при отсутствии MAIN:
при `allow-result-without-main=true` проверяется точная сработавшая связь ALL,
при false результат должен быть пустым. Пустой MAIN по-прежнему считается ошибкой.
Описание оснований и противоречия в спецификации — в EXPLAB_2690/README.md.
Негативные проверки 2891, включая пустой objectParams, не ослаблены.

Перед новым полным набором сохраните нужный прежний build за пределами проекта;
затем выполните clean один раз. Между REST/Kafka/2690/2891 clean не выполнять.
Наличие FAILED при завершённом исполнении не блокирует отчёт само по себе;
авария исполнителя, pending, потерянные вложения и несовпадение JUnit/Allure блокируют.
Формат штатных вложений не меняется: ConfigMap, текстовые логи операции и runtime
metadata; подробные события подов остаются диагностикой сбоя.

## Исправление v3: общий пакет TestOps для ticket-задач

`prepareTestOpsResults` и обычный `testOpsUpload` объединяют файлы из корня
`build/allure-results` и известных подпапок задач: `explab2690MapperCoverage`,
`explab2690ReactionsCoverage`, `explab2690Coverage`, `splitterExtensionRegression`,
`explab2972Test`, `explab2972ManagedTest`, `explab2972LaunchPlanTest`.
Исходные папки остаются на месте; плоский пакет создаётся в
`build/testops-results/<env>/allure-results`. Папки локальных проверок не включаются.
Произвольные и более глубоко вложенные каталоги отклоняются.

Для каждого непустого каталога задачи проверяются JUnit, классы, число результатов,
статусы и временное окно последнего исполнения; для задач 2690 также REST-режим.
Старые накопленные попытки в каталоге задачи, не соответствующие последнему JUnit,
блокируют подготовку. Автоматического выбора/удаления старых попыток нет.
Ссылки на вложения и fixture children проверяются внутри исходной папки до объединения.
Коллизии JSON результатов/контейнеров запрещены, даже при одинаковом содержимом.
Одноимённые вложения/метаданные объединяются только при равных размере и SHA256.
Дубли UUID и несовместимые метаданные отклоняются. Исходные Allure и JUnit повторно
сверяются перед заменой подготовленного пакета; при отказе прежний пакет сохраняется.

Manifest содержит sourceScopes, taskEvidence, junitSourceFiles и flattenedSources:
по нему можно проверить происхождение каждого файла. Общий pending-guard сохраняется.
`cleanTestOpsResults` очищает распознанные Allure-файлы и в разрешённых подпапках;
неизвестные файлы, JUnit и архивы регрессии сохраняются. Это явная очистка результатов:
не запускайте её перед отправкой нужного текущего прогона.

Для уже выполненного набора 2690 + 2885 REST/Kafka + 2891 REST/Kafka достаточно:

```powershell
.\gradlew.bat prepareTestOpsResults
.\gradlew.bat testOpsUpload -PallureDryRun=true
.\gradlew.bat testOpsUpload
```

Перезапуск тестов и clean для применения исправления не нужны. Проверка самого
сборщика без стенда и отправки: `.\gradlew.bat allureSourceLayoutCheck`.
Задача запускает 22 проверки в изолированном Gradle-проекте на синтетических данных.
На предоставленном прогоне проверены обычная подготовка и dry-run: 213 результатов,
180 passed, 33 failed. Java-сценарии и бизнес-проверки этим исправлением не меняются.

## Исправление v4: профили сервисов и единая структура результатов

В T07 EXPLAB-2690 `ReactionsFinalExperimentsSteps.endpointMode()` явно возвращает
REACTIONS. Подготовка ConfigMap, маршрут readiness, runtime metadata и сбор лога
pod теперь используют тот же профиль, что config/split. Имена тестов, параметры,
бизнес-assertions и число функциональных выполнений не меняются. Локальная проверка
профиля прошла; исправленный сценарий на стенде ещё не подтверждён.

Все обычные Test-задачи заявок используют `build/allure-results` без подпапок задач,
включая 2690, 2891, 2972 и новые Test-задачи с общими conventions. JUnit и HTML Gradle
по-прежнему разделены по задачам. Отдельные raw-каталоги предназначены для bypass,
регрессов и локальных технических проверок, которые не являются функциональными
результатами для TestOps.

- Заявки / обычный `test`: `build/allure-results`.
- Bypass: `build/bypass-registration/<env>/runs/<id>/allure-results`.
- Регрессы: `build/regression-results/<env>/<stage>/runs/<id>/allure-results`.
- Копия завершённых REST/Kafka регрессов: `build/allure-results-splitter-rest-kafka`.
- `splitterExtensionRegression`: `build/allure-results-splitter-extension`.
- Самопроверки: прежние `build/local-checks` и `build/reports/.../allure-results`.

Коллектор регрессов больше не копирует их в результаты заявок. Pending нового
регресса содержит каталог назначения: он блокирует подготовку именно этого источника,
не блокирует независимый пакет заявок и не удаляется очисткой заявок. Старый pending
без сведений о назначении остаётся блокирующим до разбора; защита не отключается.

Вся реализация подготовки/выгрузки TestOps находится в `gradle/testops`:

```text
gradle/testops/
  artifacts.gradle.kts       проверка raw, manifest, атомарная подготовка пакета
  upload.gradle.kts          единственный общий uploader и dry-run
  results.gradle.kts         подготовка обычных/bypass/регрессионных пакетов
  scheduler.gradle.kts       выбор и выгрузка архивного прогона Scheduler
  completed-stages.gradle    явно выбранные завершённые стадии
  splitter-results.gradle    сбор завершённых REST/Kafka результатов отдельно
  run-integrity.gradle       общая проверка завершённости JUnit
  layout-check.gradle        регистрация локальной проверки структуры
  tasks.gradle               подключение задач из перечисленных модулей
```

Корневой корпоративный build остаётся модульным. Он подключает `artifacts.gradle.kts`
до производителей результатов и `tasks.gradle` после настройки регрессов.
В `gradle/build-logic` остаются запуск тестов, параметры и conventions; в
`gradle/architecture` — только каталог отображения задач. Старые реализации
TestOps в build-logic/tickets удаляются установщиком после проверки хешей.

Для заявок команды не изменились:

```powershell
.\gradlew.bat explab2690Coverage
.\gradlew.bat prepareTestOpsResults
.\gradlew.bat testOpsUpload -PallureDryRun=true
.\gradlew.bat testOpsUpload
```

Регрессы выгружаются отдельно через `prepareRegressionTestOpsResults` /
`regressionTestOpsUpload`; выбор отдельных завершённых стадий — через прежний
`completedTestOpsUpload`. Для отдельного extension-набора можно явно выбрать
`-PtestOpsSourceResultsDir=build/allure-results-splitter-extension` при подготовке
и upload. Один и тот же параметр следует передавать обеим командам.

Установка не перемещает и не удаляет существующие результаты. Стандартный сборщик
продолжает читать известные старые подпапки для совместимости. Выбор `2690-core`
читает общий raw и прежнюю подпапку; коллизии не разрешаются молчаливым выбором.
Перед первым новым набором сохраните нужный старый build вне проекта и выполните
clean один раз: это отделит прежние смешанные результаты и индекс публикации от
новой структуры. Между задачами текущего набора clean не выполняйте. Повторные
запуски в общий raw накапливают попытки; выгружается весь выбранный raw, а не только
последний JUnit. Старые результаты автоматически не удаляются.

Проверено локально: компиляция изменённых Java-компонентов и классов EXPLAB-2690
на доступном корпоративном classpath; 7 локальных проверок, 29 проверок подготовки,
маршрутов и миграции на реальных Gradle-скриптах. Производственные модули TestOps
совместно проверены на копии 49 результатов: 38 passed/11 failed, dry-run без сети.
Полная сборка проекта с корпоративным Nexus и стендовый прогон не выполнялись.
