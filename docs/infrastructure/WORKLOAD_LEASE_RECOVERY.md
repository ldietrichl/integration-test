# Восстановление после аварийного завершения прогона

`SCHEDULER_RUN_BUSY` означает, что ConfigMap уже содержит аннотацию
`scheduler-regression.explab/run-owner`. Это историческое имя общей блокировки,
оно применяется и к splitter. `clean` не удаляет аннотации Kubernetes.
При аварии JVM (в том числе OutOfMemoryError) штатный rollback может не выполниться.
Владелец блокировки — UUID; сам по себе он не доказывает, что процесс завершён.

## Задачи

Файл `gradle/tickets/EXPLAB_2885-recovery.gradle` подключён через
`gradle/architecture/task-catalog.gradle`. После обновления Gradle в IDEA задачи
доступны в `Tasks > tickets`, дополнительные init-скрипты не нужны.

1. Остановить/дождаться завершения всех запусков, использующих этот сервис,
   включая другие рабочие станции и CI. Не запускать новые тесты во время восстановления.
2. Из корня проекта выполнить проверку без изменений стенда:

```powershell
.\gradlew.bat explab2885InspectLease
Get-Content .workload-recovery\EXPLAB_2885.json
```

Проверить environment, namespace, context, deployment и ConfigMap в плане.
По умолчанию Deployment — `splitter-reactions-service`, ConfigMap —
`splitter-reactions-service` и `splitter-reactions-service-lib`.
Каждая ConfigMap должна действительно использоваться указанным Deployment.
Если стенд использует другие имена, задать `-PrecoveryDeployment=...` и
`-PrecoveryConfigMaps=имя1,имя2` в **обеих** командах.
Проверка не сохраняет содержимое ConfigMap, только идентификаторы и SHA256.
План вне `build` переживает `clean` и не попадает в Allure/TestOps.

3. Только после подтверждения отсутствия активных запусков снять блокировки:

```powershell
.\gradlew.bat explab2885ReleaseLease -PrecoveryConfirmStopped=true
```

`recoveryConfirmStopped=true` — подтверждение оператора, а не автоматическая
проверка активности. Требуются уже настроенные разрешения
`stand.<env>.mutations.enabled=true`, `mutations.configmap.enabled=true` и
`mutations.namespace-confirmation`, совпадающее с namespace подключения.
Среда берётся из `test.properties`; TLS, контекст и авторизация — из общего
`KubernetesTunnelConfigScope` / Fabric8. Разрешения автоматически не включаются.

Сначала проверяются все объекты плана. Перед удалением каждого владельца JSON Patch
атомарно проверяет UID, resourceVersion и точное значение аннотации. Изменение
плана/объектов прерывает операцию. Другие аннотации, данные ConfigMap и поды не меняются.
Между несколькими ConfigMap нет общей транзакции. При частичном выполнении или
неоднозначной сетевой ошибке нужно сделать новую проверку с **новым** путём:

```powershell
.\gradlew.bat explab2885InspectLease -PrecoveryPlan=.workload-recovery/EXPLAB_2885-next.json
.\gradlew.bat explab2885ReleaseLease -PrecoveryPlan=.workload-recovery/EXPLAB_2885-next.json -PrecoveryConfirmStopped=true
```

Существующий план не перезаписывается. Снятая блокировка не восстанавливается
автоматически; следующий обычный запуск приобретёт нового владельца.

## Ограничение восстановления

Снятие блокировки **не восстанавливает исходные настройки до аварии**. Для этого
нужны сохранённые preimage-файлы предыдущего запуска. До патча надёжности они
находились в `build/stand-artifacts`; после патча — в `.workload-recovery/private`.
В доступном новом наборе их нет. Следующий обычный сценарий подготовит требуемый
профиль через общий Fabric8, но его rollback вернёт настройки, обнаруженные на
старте этого нового запуска. Если нужны именно исходные настройки стенда,
сначала восстановить их по подтверждённому preimage/эталону; неизвестные значения
не угадывать. После `clean` preimage могли быть удалены локально.

## Проверки кода и повторный прогон

```powershell
.\gradlew.bat testClasses workloadLeaseRecoveryCheck
.\gradlew.bat splitterRestRegression --tests 'ru.sber.qa.splitter.EXPLAB_2885.SplitterReactionsPrecalc2885FlowTest' --tests 'ru.sber.qa.splitter.EXPLAB_2885.SplitterReactionsPrecalc2885ContractFlowTest' --rerun-tasks
```

`workloadLeaseRecoveryCheck` — локальные проверки защит восстановления, без стенда.
REST-профиль включает `SPLITTER_API_CONFIG_LOAD=true` через общую подготовку.
Для Kafka профиль переключает его в false:

```powershell
.\gradlew.bat splitterKafkaRegression --tests 'ru.sber.qa.splitter.EXPLAB_2885.SplitterReactionsPrecalc2885FlowTest' --tests 'ru.sber.qa.splitter.EXPLAB_2885.SplitterReactionsPrecalc2885ContractFlowTest' --rerun-tasks
.\gradlew.bat validateSplitterRestKafkaAllureResults splitterRestKafkaAllureReport
.\gradlew.bat prepareSplitterRestKafkaAllureResultsForTestOps
```

Не выполнять `clean` между REST и Kafka. Сначала проверить REST; причиной прошлого
обрыва Kafka был OutOfMemoryError, и снятие блокировки само по себе эту причину
не исправляет. Новые блокировки не будут автоматически сниматься при ошибках.
Снятие нельзя объединять в одну команду с проверкой плана или тестами.

## План следующего патча — после анализа исправленных сценариев

Зафиксировано 2026-10-05. Статус: анализ предоставленного прогона завершён,
реализация следующего патча ещё не начата.
Заключение: [прогон после уточнений АК](../services/splitter/RUN_REVIEW_20261005_AFTER_AK.md).
REST 2885 и оба режима 2891 завершены; Kafka 2885 повторно оборван OOM,
2690 и FRESH/SDK 2891 в наборе отсутствуют. Это ограничения покрытия, а не PASS.
Пользователь подтвердил, что текущая проблема с блокировкой устранена.
План ниже реализован патчем splitter-reliability-20261005-v1 в описанных пределах:
[состав, ограничения и команды](SPLITTER_RELIABILITY.md). Сетевой прогон после
установки патча остаётся обязательной проверкой в корпоративной среде.

### Обязательный предшествующий этап

Сначала проанализировать прогон исправленных сценариев EXPLAB_2690, EXPLAB_2885
и EXLAB_2891 в пределах фактически предоставленного набора:

1. Установить версии патчей, режимы REST/Kafka и полноту выполнения по shell-логу,
   JUnit XML и исходным Allure results. Не смешивать прежние результаты с новым прогоном.
2. Проверить изменённые ожидания по комментариям АК (они имеют приоритет),
   сопоставить падения с запросами, ответами, состоянием ConfigMap и логами сервиса.
3. Разделить дефекты сервиса, сценариев и инфраструктуры. Невыполненные проверки
   отметить отдельно; восстановление блокировки не считать успешным бизнес-прогоном.
4. Зафиксировать заключение по прогону и только затем переходить к реализации
   следующего патча с учётом обнаруженных проблем.

До завершения этого анализа не менять Kafka-буферы, жизненный цикл блокировок,
настройки памяти и хранение preimage. Текущий опубликованный патч не пересобирать.

### Состав следующего патча

| Работа | Ожидаемый результат и проверка |
| --- | --- |
| Ограничить накопление Kafka-сообщений | Обрабатывать каждую полученную запись один раз, освобождать обработанный буфер, ограничить диагностическую выборку по числу записей и байтам. Проверить большой поток нерелевантных сообщений, нахождение нужного сообщения, тайм-аут и отсутствие повторной обработки. |
| Проверить жизненный цикл Kafka-клиентов | Учесть, что корпоративный KafkaService кеширует consumer и закрывает его в afterTest. Не закрывать общий consumer посреди сценария; проверить очистку буфера и штатное освобождение ресурсов без нарушения повторного использования. |
| Вынести журнал восстановления из build | До мутаций сохранять владельца, идентичности ресурсов, исходные значения изменяемых ключей и этапы операций в защищённую папку вне build и Allure/TestOps. Проверить сохранность после clean и восстановление только при совпадении владельца и ожидаемого состояния. |
| Предварительная проверка блокировки | До запуска набора выдавать одну понятную инфраструктурную ошибку с владельцем и командой восстановления вместо каскада зависимых падений. Сохранить атомарную проверку при приобретении блокировки: предварительная проверка её не заменяет. |
| Диагностика памяти тестовой JVM | Настроить явный лимит heap с учётом ресурсов среды, GC-лог и heap dump при OOM. Диагностику хранить локально, не загружать в Allure/TestOps. Увеличение heap не считать исправлением накопления сообщений. |
| Ограничить разбор Kafka payload и уточнить итог прогона | Новый стек OOM проходит через parseJson/collectCandidateJsonRoots при разборе message. Проверить не-JSON и большие сообщения, размеры диагностических строк и повторный разбор. В сводке отдельно учитывать ошибку Gradle Test Executor и неполное исполнение: completed=true не должно скрывать обрыв. |
| Формирование и выгрузка завершённых стадий TestOps | Воспроизведён глобальный запрет prepareTestOpsResults из-за splitter-kafka.pending, хотя 108 результатов завершённых стадий проходят полную проверку пакета. Добавить явный выбор завершённых прогонов с проверкой принадлежности результатов, манифестом включённых run ID/статусов и исключённых незавершённых стадий. Сохранять pending и защиту полной выгрузки; не выгружать старые или частичные данные под видом полного набора. Проверить dry-run и отсутствие неявной сетевой выгрузки. |
| Проверка и доставка | Локальные проверки защит и Kafka-буфера, компиляция на корпоративном classpath, патч полными файлами с PowerShell-установкой и откатом, задачи в группе tickets. Затем отдельный стендовый прогон и сравнение с результатом предшествующего анализа. |

Основание для Kafka-доработки: в SplitterKafkaConfigLoadClient список observedPayloads
растёт без ограничения, а limit(10) применяется только при формировании вложения.
В исследованной корпоративной версии KafkaConsumerClient poll добавляет записи
в сохраняемый список, который цикл повторно обходит. Это подтверждённый риск
накопления; связь именно с предыдущим OutOfMemoryError пока не доказана heap dump.

Автоматическое снятие блокировки по возрасту/TTL не входит в план. Если позднее
потребуется автоматическое восстановление, его нужно проектировать отдельно:
внешний процесс, подтверждение завершения прежнего владельца и проверки журнала
через общий Fabric8. Shutdown hook или finally сами по себе не гарантируют
восстановление после аварии JVM. Все операции Kubernetes остаются в общем механизме.
