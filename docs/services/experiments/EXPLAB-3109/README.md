Текущая редакция реализует 12 сценариев: прежние девять с усиленными assertions
и три новых — повтор после завершения, удаление связи и две задачи с разными
реальными данными. [Матрица](COVERAGE.jira.txt),
[подготовка и ограничения](READINESS.jira.txt),
[полный план и изменения](EXPANDED_PLAN_12_20261023.jira.txt).

Прежние имена методов и ID сохранены: 01/09/18/60/61 и 22/23/26/27.
Добавлены 28/29/30. Все методы находятся в ExperimentLinksCore3109FlowTest;
Environment, общий Workload lifecycle и профили подключения переиспользуются.
Сценарии и проверки расположены в существующих предметных steps/fixture/assertions;
отдельных клиентов Kubernetes и собственного механизма управления pod нет.

## Запуск

Нужны env=ift, JDK17, корпоративные зависимости, действующие подключения ИФТ
и согласованное окно изоляции. Каждая команда выполняется отдельным вызовом:

```powershell
.\gradlew.bat testClasses
.\gradlew.bat explab3109Api
.\gradlew.bat explab3109Kafka
```

Api выбирает 5 методов 01/09/18/60/61. Kafka выбирает 7 методов
22/23/26/27/28/29/30. Для одного полного запуска вместо двух наборов:

```powershell
.\gradlew.bat explab3109Core
```

Core выбирает все 12. Только три новых сценария можно запустить отдельно:

```powershell
.\gradlew.bat explab3109Extended
```

explab3109ExistingData остаётся совместимым именем Api5. Не объединять несколько
наборов в одном вызове и не выполнять clean между сохраняемыми прогонами.
Общий сборщик результатов, runId, Allure и TestOps не изменяются.

## Реальные данные и инфраструктура

Сохраняются consumer explab_ift273/275:9092/PLAINTEXT, configured producer binding
273/275:9093, V1 mTLS и двухузловый primary DB1636/1637. Настройки ИФТ сохранены при переносе в структуру develop; секреты остаются вне Git.
[Маршрут и общий pod lifecycle](KAFKA_ROUTING_PODS_20261023.jira.txt).
Job/периоды читаются и сохраняются прежним профилем; lease, readiness, условные
рестарты, логи и восстановление остаются в общем Environment/Workload/Fabric8.

Чанк и страница не задаются. Чанк1 проверяется по событию, page/size читаются
из опубликованного запроса. В28/29/30 первая собственная реальная задача позволяет
наблюдать размер страницы. Затем до проверяемых задач независимо читается Campaign
с этим же размером и повторно проверяется стабильность. Ответ журнала не является
эталоном. Чужие связи только читаются при ограниченном подборе кандидатов.

28 повторяет завершённую задачу с тем же непустым ограничением expIds/cjIds.
29 создаёт свой конфиг, исключающий все фактически прочитанные WORKING communication
IDs, и требует настоящий HTTP200 с собственным configScope, isLastPage=true, cjs=[].
Исходная собственная связь подготавливается из реального независимого Campaign-снимка.
30 создаёт два разных своих эксперимента; разные фильтры исключают все реальные
коммуникации, кроме одной разной в каждом. Два непустых различающихся ответа должны
быть независимо подтверждены до постановки обеих задач. Если условия не получены,
сообщается BLOCKED_ENVIRONMENT с причиной. Глобальный пересчёт не запускается.

## Усиленные проверки

Строго проверяются JSON-типы и диапазоны Long, hostname и requestId. Только четыре
Set-поля Campaign сравниваются по составу; порядок страниц, остальные списки,
структура, фильтры и значения проверяются точно. В23/26/27/28/29/30 сверяется вся
дельта БД со всеми createdLinks/updatedLinks/deletedLinks, включая отсутствие ложных
соседних действий. Сохраняется ID существующей связи; nullable ID новой допускается
по контракту. Scope проверяется у всех наблюдаемых событий своей задачи до выбора
временного окна, повтор одинакового payload не трактуется как новая обработка.

request_dt ограничен независимыми часами БД до и после POST с явным допуском
разницы часов приложения/БД ±30 секунд. Это допустимая граница, не измеренный offset.
После очистки SELECT подтверждает отсутствие всех зарегистрированных собственных
экспериментов, конфигов, связей, задач и барьера. Чужое состояние не удаляется.
