h1. EXPLAB-3109 — разовая настройка consumer и восстановление комментариев

Историческая заметка: последующий аудит подтвердил, что профильift вёл в ООД.
Текущий маршрут3109 исправлен на explab_ift; эта разовая SSL-настройка больше не
является его предусловием. Настройки UTF-8 остаются применимыми; заполненные ключи
не удаляются. Актуальное обоснование: KAFKA_ROUTING_PODS_20261023.jira.txt.

h2. Состав и границы пакета

Пакет предназначен для проекта с установленными V7, исправлением DB failover,
REST V1 и временем задач. Все5 API-тестов прошли на ИФТ в запуске16:57.
Новый запуск20261023-172840-749-3b7b745b прошёл проверку заполненности Kafka,
но все4 метода остановились в prepare: No resolvable bootstrap urls given in
bootstrap.servers. В stdout12 предупреждений DNS: три bootstrap-хоста на каждый
тест. Тела Kafka не выполнялись; все4 cleanup passed. TLS/ACL/топик/доставка событий
этим запуском не проверены. Summary, JUnit, raw Allure и ссылки на вложения согласованы.

Используются текущие tsldq-mvp000243/244/245.cloud.delta.sbrf.ru:9093, профильift.
Адреса, порт, security protocol, размеры чанка/страницы, HTTP/DB и код девяти
тестов этим пакетом не изменяются. DNS-отказ не устраняется заменой пароля.

Одноразовый файл settings/secure.kafka-ift.once.properties содержит два заполненных
ключа: SECURE_KAFKA_CONSUMER_IFT_SSL_KEYSTORE_PASSWORD и
SECURE_KAFKA_CONSUMER_IFT_SSL_TRUSTSTORE_PASSWORD. Значения взяты из полей
key-store/trust-store password строки Kafka ООД, стр34 документа «05. Стенды»,
версия166 от23.10.2026. Именно эта строка совпадает с текущими bootstrap-адресами.
Отдельная строка Kafka ExpLab содержит другие hosts; её настройки не выдаются
за подтверждённый адрес данного consumer. Соответствие текущего кластера фактическому
producer-explab развёрнутого сервиса остаётся условием стендового запуска.

Пакет с рабочими значениями выдаётся разово по запросу. Установщик читает его из
распакованного пакета, заполняет только отсутствующие/пустые/шаблонные поля корневого
secure.local.override.properties и сохраняет уже заполненные значения. Остальные
ключи, в том числе REST/DB/Kubernetes, остаются побайтово прежними. Полная копия
чужого рабочего override не подменяется локальным файлом. Пути JKS не меняются:
проверить SECURE_KAFKA_IFT_KEYSTORE_PATH и SECURE_KAFKA_IFT_TRUSTSTORE_PATH и реальные
файлы на машине запуска. Заполненное поле означает только сохранённую настройку,
а не доказательство её действительности.

h2. Кодировка

Аудит актуальных430 файлов не выявил повреждённого UTF-8; оба локальных secure-файла
читаются корректно. Корпоративный скриншот показывает нечитаемые комментарии, но не
содержит исходных байтов файла. Поэтому массовое перекодирование не выполняется.

При установке известные комментарии вида «# ИМЯ_КЛЮЧА: описание» восстанавливаются
в UTF-8 по карте150 описаний из штатного шаблона. Это применяется к существующим
secure.local.override.properties и secure.local.properties. Неизвестные комментарии
сохраняются. Значения свойств, продолжения строк, BOM и окончания строк сохраняются;
для двух разрешённых пустых Kafka-полей применяется разовое заполнение.
Файлы неизвестной байтовой кодировки отклоняются до записи, а не преобразуются
предположительно. Шаблон не копируется поверх рабочего override.

.editorconfig закрепляет UTF-8; .idea/encodings.xml явно указывает UTF-8 для двух
secure-файлов и src/test/resources. После установки перечитать файлы с диска в IDE;
если IDE предлагает Reload/Convert, выбрать Reload in UTF-8. Уже повреждённые
комментарии сначала исправляет установщик, смена отображения не восстанавливает их.
Properties.load(InputStream) сохраняет своё поведение: значения вне ASCII должны
использовать Java Unicode escapes. Значения не перекодируются вместе с комментариями.
Исходные Allure/JSON прошлого запуска не переписываются ради отображения терминала.

h2. Локальные проверки

PowerShell5.1:14 проверок восстановления комментариев, сохранение всех остальных
байтов, BOM/EOL, continuation, неизвестных комментариев и no-op здоровых файлов.
Дополнительно проверены узкое заполнение, сохранение уже заполненных literal/ENC/
Vault/escaped значений, whitelist, дубли, SHA, CAS, backup и побайтовый откат.
Два пароля офлайн открывают существующие JKS; это не TLS-проверка брокеров.
У проверенного локального клиентского JKS обнаружен истёкший сертификат; один из11
сертификатов truststore также истёк. Это не доказывает ошибку живого TLS-сеанса или
непригодность всех цепочек truststore. JKS в пакет не включаются; для реального
подключения нужны действующие материалы именно машины запуска.

Стендовых вызовов и отправки TestOps при подготовке не выполнялось. Новое успешное
выполнение Kafka4 и всех9 после установки пока не подтверждено.

h2. Следующий шаг

До повторного explab3109Kafka проверить корпоративный DNS и TCP9093 для текущих
bootstrap-адресов, затем подтвердить Kafka listener/топик кластера, куда пишет
producer-explab развёрнутого сервиса. Порт KafkaUI9090 не подставлять как broker.
При изменении bootstrap сверять фактическую конфигурацию сервиса; не выбирать новый
кластер, IP или отключение TLS ради прохождения проверки.
Установка, диагностика DNS и проверенный откат описаны в INSTALL_CORP.md.
