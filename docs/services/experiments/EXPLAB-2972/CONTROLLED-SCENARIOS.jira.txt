h1. EXPLAB-2972 — управляемые сценарии на реальном стенде

Окружение выбирается через env в test.properties. Перед каждым сценарием зафиксировать сборки двух сервисов, время, id и requestId, пользователя, значения серверных флагов и состояние jobs. Собирать HTTP, SELECT-снимки и реальные scheduler/Kafka/audit/monitoring доказательства. Все данные выделенные. Для 16 сценариев изменения режима выполняет контроллер по CONTROL-API.md; остальные внешние предусловия готовит оператор. Тесты не запускают shell-команды и не изменяют БД напрямую.

U: POST /api/v2/experiments/status {requestId,expId,status,comment}. B: POST /api/v2/experiments/status/bulk {requestId,requestDt,requestSource,actions:[{id,status,userId,employeeId,traceId}]}. J — штатный processor. F — выделенный эксперимент с именем EXPLAB-2972-*. G — другой контрольный тестовый эксперимент. DRAFT/version=5, MAPPER/MODEL_TEST, даты/права/флаги сверить до запроса.

P01: подтвердить сборки EXPLAB-2972; P02: сверить env/URI/сертификат/права; P03: миграции и доступ наблюдения; P04: тестовые пользователи; P05: наблюдение реального scheduler; P06: отдельные фикстуры; P07: выделенное окно jobs и снимок очереди; P08: адресный подготовленный отказ и план восстановления; P09: восстановление после отказа; P10: offsets и чтение Kafka; P11: корреляция всех событий по UUID. Нельзя подменять реальную серверную настройку клиентским -D свойством.

P06 уточнение: создавать F через POST /api/v2/experiments из полного валидного шаблона с условиями отбора, группами, долями и результатами. Минимальная INSERT-запись эксперимента не заменяет такую фикстуру. Если нужное предусловие нельзя получить через API, после API-создания допускается адресная подготовка только выделенного объекта в согласованной изолированной среде: status/version/даты/scheduleParam, затем проверка через API или SELECT. Подготовленный статус не является доказательством успешного бизнес-перехода. Для TP-24/37 создать и проверить PLANNED-задачу через scheduler до включения отказа удаления. Очереди и оставшиеся от предыдущих сценариев запросы изолировать до следующего прогона, сохраняя снимки.

Ожидания ниже описывают контракт, а не результат текущего повторного прогона. Для смены статусов используется v2.5 из PDF v17, стр. 2234–2268; раздел v2.2 расположен позже в этом же PDF и не заменяет v2.5. Для EXP-публикации requestSource=UI прямо задан на стр. 3115.

h2. Восстановление и фиксация результата
После каждого случая восстановить зависимости/серверные флаги/jobs, проверить состояние реально созданных задач и записей по requestId, сохранить evidence и адресно завершить тестовые объекты. Для STARTING/IN_PROGRESS/STOPPING не применять глобальное удаление таблиц. Недостигнутые из-за ошибочного перехода зависимые шаги не считать выполненными; не завершать вручную ради успешного TP-59. Вопросы Q03/Q04/Q05 и оставшиеся вопросы Q07 по внешним контрактам/дедупликации согласовать с владельцем требований. Ожидание TP-13 определено v2.5; нормализация requestSource для TP-45 определена PDF v17, стр. 3115.
