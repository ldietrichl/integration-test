## Защитные условия

1. Существующие подтверждения выделенного стенда, namespace, разрешения ConfigMap, удаления pod и управления фикстурами сохраняются.
2. Для job-проверок добавлено отдельное разрешение `stand.<env>.workloads.scheduler.regression.jobs.enabled`.
3. Перед включением джобы проверяется отсутствие чужих PLANNED/IN_PROGRESS, включая записи без действий. При наличии чужих активных задач профиль не включается. Чужие записи никогда не удаляются.
4. На выделенном стенде не должно быть параллельных писателей и других прогонов. Одного чтения БД недостаточно для распределённой блокировки других приложений; ResourceLock действует только внутри одного запуска JUnit.
5. Все семь ранее одобренных флагов должны быть false. Включается только master v2 и одна выбранная V2-джоба.
6. Изменение ConfigMap выполняется через существующий CAS с сохранением pre-image и отдельным GET/assert. Для применения выполняется удаление конкретного pod с UID-precondition и ожиданием нового Ready pod.
7. В finally профиль возвращается к выключенным джобам, pod пересоздаётся, выполняется health-проверка. Только затем разрешено удаление собственных фикстур.
8. Если возврат в безопасное состояние не подтверждён, автоматическое удаление фикстур и возобновление исходных джоб блокируются. Используются сохранённые артефакты для ручного восстановления. Ошибка восстановления не затирает исходную ошибку сценария.
9. После класса восстанавливается первоначальная конфигурация стенда существующим механизмом. Действий над experiment-service, DB-триггеров, изменения схемы и заглушек нет.

Физические ограничения схемы на version=0/2 должны допускать эти тестовые значения. Если схема их не допускает, это несовместимость подготовки, не доказательство ошибки фильтрации. Тест не изменяет ограничения БД и не принимает нарушение предусловий как PASS.

## Настройки стенда

Пример фрагмента находится в `config/examples/scheduler-real-jobs.properties`. Этот файл не загружается автоматически; объедините необходимые ключи со своим существующим `test.properties`, не заменяя файл целиком.

Для выбранного DEV после согласования выделенного стенда:

```properties
stand.dev.workloads.scheduler.regression.jobs.enabled=true
stand.dev.workloads.scheduler.regression.timeout.seconds=240
```

Для cleanup нужны фактические значения конфигурации работающего scheduler:

- `stand.dev.workloads.scheduler.regression.execution-timeout.millis`: значение `service.execution.v2.task_execution_timeout_millis`.
- `stand.dev.workloads.scheduler.regression.overdue.minutes`: значение `service.execution.v2.schedule_outdated_timeout_minutes`.

В исходном архиве defaults равны 5000000 миллисекунд и 1440 минут. Это НЕ подтверждение эффективных значений корпоративного pod. Эти строки в примере закомментированы намеренно. Получите фактические значения из одобренной конфигурации развертывания и заполните их перед cleanup-сценариями. Учтите настройки, которые могли переопределить application.yml.

Для IFT/LT используются соответствующие `stand.ift.*` / `stand.lt.*`. Секреты, текущий env, kubeconfig, URI и общие подключения не меняются этим патчем. Без нового разрешения job-сценарии не включают джобы и завершаются ошибкой предусловий; это не скрытое @Disabled.

## Компиляция

Разрешённая попытка выполнена на Gradle 8.4 без тестов и сетевых обращений:
`compileWithoutTests --offline --no-daemon --console=plain`.

Временный локальный init-скрипт позволил использовать закэшированный Allure plugin. Сборка дошла до разрешения compileClasspath, но остановилась: локально отсутствуют модули `ru.sber.qa.platform-v-at-framework` версии `1.10.3-beta` (api, database, kafka, session, containers, allure2, sbermock). Java-компилятор не подтвердил корректность исходников. Зависимости не подменялись другими версиями или пустыми классами.

Локальный init-скрипт не входит в корпоративный патч. На ВАРМ сначала выполните `compileWithoutTests` через существующий wrapper и Nexus; при ошибке не запускайте регресс. Тесты и подключения к стенду здесь не выполнялись.
