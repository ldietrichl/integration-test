## 4. Сверка спорных требований

- Стр.2643: человекочитаемые названия статусов фиксированы, ожидания тестов верны.
- Стр.2644-2647: поля дат реестра integer; OpenAPI string/date-time расходится с первичной спецификацией. В примерах встречаются секунды и миллисекунды, поэтому новый общий assert не объявляет единицы окончательно согласованными.
- Стр.2662: splittingPointCode, scheduleDateTime и createdBy отмечены обязательными.
- Стр.2670-2672: одна task с несколькими actions и единая транзакция.
- Стр.2673: version обязателен в ответе; это не означает, что номер версии URL должен совпадать с task.version. В корпоративном коде API v2 сохраняет task.version=1, соответствующая правка фикстур сохранена.
- Стр.2673: splittingPoint.name берется из словаря, а не вычисляется из code.
- Раздел v2 находится в статусе «Разработка». Противоречия таблиц/примеров/алгоритма перечислены явно и не устранены подменой ожиданий.

## 6. Запуск из IDE

Проверены настройки проекта и места, приводившие к отличию выбора тестов. Компиляция main/test/bypassTool выполнена.
Фактическое нажатие Run на корпоративной IDEA и выполнение тестов НЕ проводились; утверждение «все сценарии проходят по кнопке» было бы недостоверным.

- Импортировать проект как Gradle, использовать Wrapper 8.4 и JDK 17.
- Для обычных корпоративных классов/пакетов выбрать Run tests using Gradle; тогда используется тот же eligibility scanner, что и для CLI.
- Для прямого JUnit-runner ресурсы читаются через TestConfigurationFiles из проекта/classpath; env выбирается в test.properties. Рабочая директория должна быть корнем integration-test.
- @Disabled, manual/outdated, условные профили и явные разрешения на мутации не обходятся кнопкой IDE.
- Специальные managed/launch-plan классы других сервисов, исключенные глобальными Gradle-фильтрами, остаются для своих специализированных задач. Патч не объявляет каждый такой класс допустимым для обычного test.
- Перезапуски/ConfigMap/scale только на выделенном стенде. Не запускать параллельные Gradle/IDE JVM с мутациями одного namespace.
- Старые названия RO-006/INF-007 в тестовых классах пока содержат OpenAPI string/date-time, хотя проверка переведена на первичную спецификацию. Это оставшийся косметический дефект, требующий отдельного переименования.

## 7. Рекомендуемый порядок следующего корпоративного прогона

1. Установить файлы замены с резервной копией. Reload Gradle.
2. Проверить общий kubeconfig/CA и учетную запись локально, не пересылая токен/пароль.
3. Убедиться в исходных значениях ConfigMap по приватным backup старого прогона. Не использовать новые тесты как автоматическое восстановление исторического состояния.
4. Запустить read-only диагностику и сценарий ConfigMap snapshot; затем согласованные мутационные сценарии по одному.
5. Запустить `schedulerRegression` в новом каталоге результатов. Отдельно сохранить task/run id и полный исходный набор результатов.
6. Приложить к сервисным дефектам логи строго по времени/корреляции упавшего сценария и digest образа.
