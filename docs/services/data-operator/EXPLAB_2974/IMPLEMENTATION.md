Основной класс: `src/test/java/ru/sber/qa/dataoperator/EXPLAB_2974/DataOperatorLinksValidationFlowTest.java`.

`DataOperatorLinksInvalidRequests` строит каждый вариант из нового базового JSON. Удалённое поле и явный `null` различаются; большие числа передаются без потери точности; отсутствие HTTP-тела не подменяется строкой `null`. Эти запросы проверяют валидацию до работы с объектами. `expId` в теле links не создаёт эксперимент. Записи в БД/кэше не создаются, поэтому данным сценариям teardown не нужен.

`SplittingObjectsLinksRequestDto` и `DataOperatorLinksTestDataFactory` подготовлены для следующих сценариев. Рабочие имена: запрос `objectsSelectConditions`, ответ `objectSelectConditions` / `splittingObjects`; неоднозначность U1 остаётся в плане.

`DataOperatorLinksAssertions.shouldHaveLinks(...)` проверяет полное множество пар `(parentId,id)` для каждого `(expId,number)`, типы ключей, обязательные массивы, сохранение пустых условий, строковые идентификаторы и отсутствие повторов. Отсутствующий родитель отличается от явного `null`; одинаковый `id` под разными родителями допустим. Этот общий метод пока проверен только локальными тестами на синтетических ответах и не засчитывается как выполненный сценарий сервиса.

Вывод ограничен проверенными разделами ФП и приложенной сборкой: подтверждённой пары REST create/delete, достаточной для всех D1-вариантов, нет. Удаление эксперимента через REST не означает удаление объектов в кэшах data-operator.

Указанное пользователем исключение для прямой записи применимо к метаданным и очистке Ignite. Сервис использует `com.sbt.ignite:ignite-core:17.6.0`; эта закрытая версия по-прежнему недоступна. Для локального запуска установлен Apache Ignite 2.17.0, а сервис собран с публичными зависимостями и неизменённым Java-кодом. Корпоративная совместимость этим не подтверждается. [Недостающие компоненты](INFRASTRUCTURE_REQUIREMENTS.md).

Порядок следующей fixture: до REST-загрузки проверить доступность точечного удаления; создать уникальные коды точек; через fallback подготовить только собственные метаданные; объекты загрузить REST-запросом; проверить полный набор загруженных пар; выполнить links; в `finally` удалить собственные записи из `splitting_field_cache`, `splitting_object_cache`, `actualization_cache`, `param_cache`, `data_source_cache` и проверить их отсутствие. Частично выполненный setup также должен очищаться. Ошибка очистки должна завершать тест ошибкой, сохраняя исходную ошибку через suppressed exception. Реализация этой fixture пока не добавлена.

## Запуск и фактическая проверка

Для стенда настроить внутренний `rest.<env>.data-operator.base-uri` и штатный mTLS проекта. Существующий resolver разрешает fallback на gateway, поэтому для этого back endpoint необходимо явно задать адрес data-operator. Не передавать секреты литералами в командной строке.

```powershell
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksValidationFlowTest' -x testOpsUpload
```

Локальные проверки генератора и оракула, без запросов к сервису:

```powershell
.\gradlew.bat test --tests 'request.dataoperator.v2.DataOperatorLinksInvalidRequestsTest' --tests 'util.dataoperator.DataOperatorLinksAssertionsTest' -x testOpsUpload
```
