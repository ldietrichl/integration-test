# EXPLAB-2974: подключение зависимостей из проекта data-operator

Подготовлен отдельный вариант клиента с координатами Ignite из POM сервиса `06fd6acb646`. На ВАРМ зависимости разрешились, но первая версия задачи остановилась на слишком строгом запрете дублирования `BinaryObject.class` в `ignite-core` и `ignite-binary-api` версии `17.6.0`. **Этот запрет исправлен; компиляция исправленного комплекта и подключение к Ignite ещё не подтверждены.** По указанию пользователя Gradle, Maven, Nexus и тесты локально не запускались. Следующие действия выполняются на ВАРМ.

## Что подключается

| Зависимость | Версия / источник |
|---|---|
| `com.sbt.ignite:ignite-core` | `17.6.0` |
| `com.sbt.ignite:ignite-indexing` | `17.6.0` |
| `com.sbt.security.ignite:security-core` | `17.6.0` |
| `com.sbt.security.ignite:security-ldap` | `17.6.0` |
| `javax.cache:cache-api` | `1.1.1` |
| `com.fasterxml.jackson.core:jackson-databind` | Управление версией через BOM Spring Boot `3.5.8`, как у сервиса |

Также подключаются транзитивные зависимости. В конфигурацию импортированы BOM Spring Boot `3.5.8` и Spring Cloud `2025.0.1` из проекта сервиса. Это клиентская часть его зависимостей. Координаты определены в `tools/data-operator-explab-2974/pom-corporate.xml`; Gradle читает этот файл, отдельного списка версий в скрипте нет.

Импорт BOM в отдельную Gradle-конфигурацию фиксирует управляемые версии. Фактический результат разрешения всех транзитивных библиотек нужно сверять по сформированному `dependency-resolution.json`: одинаковые прямые зависимости не гарантируют побайтовое совпадение с неизвестной сборкой работающего сервиса.

Корневые `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties` и classpath тестового фреймворка не меняются. Скрипт `-I` регистрирует отдельную конфигурацию и задачу, использует репозитории и учётные данные уже настроенного проекта. Он не добавляет свои адреса Nexus, Maven Central или секреты. Maven на ВАРМ не нужен.

## Перед запуском

Нужен установленный предыдущий патч `EXPLAB-2974-corporate-static-client-ONE-TIME-20260908-101914`, в том числе `LinksCacheTool.java`, `LinksCacheSchema.java`, новый `LinksFixtureRuntime` и `DataOperatorLinksConnectionTest`. Проект должен запускаться с JDK 17 и штатной конфигурацией `env=dev`.

При смене клиентского комплекта незавершённые fixture других запусков сначала восстанавливаются исходным клиентом. В `progon_2` подготовка остановилась до записи данных и таких fixture нет. Старые каталоги клиентов и манифесты сохраняются.

## Команды на ВАРМ

Команды выполняются отдельно, из корня `C:\Work\IdeaProjects\integration-test`.

**1. Загрузить зависимости и собрать клиентский комплект:**

```powershell
.\gradlew.bat -I tools/data-operator-explab-2974/corporate-client.init.gradle prepareExplab2974CorporateClient -x testOpsUpload --console=plain
```

Эта задача разрешает зависимости через репозитории проекта и Gradle-кэш, но не подключается к Ignite или REST-сервису. Она проверяет прямые версии, контролирует выбор ключевых классов Ignite, копирует библиотеки, считает SHA256 и компилирует оба helper-класса с `--release 17`. Скачанные зависимости не добавляются в classpath самого тестового проекта. Транзитивные модули, объявленные самой корпоративной поставкой, разрешаются штатно; библиотеки прежнего Apache-комплекта не подмешиваются из его каталога.

Прямые зависимости идут в порядке POM, затем транзитивные — по имени файла. Поэтому `ignite-core` предшествует `ignite-binary-api`. Этот порядок сохраняется в lock и одинаков при компиляции и запуске клиента. Одинаковые байты дублированного проверяемого класса допускаются. Для обнаруженной пары `com.sbt.ignite:ignite-core/ignite-binary-api` той же версии отдельно допускается дублирование `BinaryObject.class`, с выбором класса из core даже при различии байтов. Это явный выбор для пробного подключения, а не доказательство бинарной совместимости всей поставки: дальше остаются компиляция и диагностический тест без записи. Другие неодинаковые копии проверяемых классов останавливают задачу с пояснением.

Поставщики классов, SHA256 их байтов и фактический порядок записываются в `build/explab-2974-client-compile/dependency-diagnostics.json` до проверки конфликтов; в готовом комплекте они также находятся в lock и `dependency-resolution.json`. Оба исходных JAR сохраняются целиком, исключения зависимостей для обхода этой ошибки не вводятся.

Только после успешного завершения создаётся/выбирается неизменяемый каталог:

```text
tools/data-operator-explab-2974/corporate-runtimes/<runtime-sha256>/
  lib/*.jar
  LinksCacheTool.java
  LinksCacheSchema.java
  client-libraries.lock.json
  pom-corporate.xml
  dependency-resolution.json
```

Путь к готовому каталогу записывается в `corporate-runtimes/latest-runtime.txt`. При ошибке разрешения или компиляции этот указатель не обновляется. После неуспешной подготовки не переходить к следующей команде: там мог остаться путь предыдущего комплекта. Неполный каталог `.preparing-*` не выбирается автоматически.

**2. Выбрать подготовленный комплект для dev в текущем PowerShell:**

```powershell
$env:LINKS_FIXTURE_DEV_RUNTIME_DIRECTORY = (Get-Content -LiteralPath '.\tools\data-operator-explab-2974\corporate-runtimes\latest-runtime.txt' -Raw).Trim()
```

Эта настройка действует только в текущем терминале и запускаемых из него процессах. Она имеет приоритет над fixture-параметром из файла защищённых настроек. Проверьте отсутствие старого JVM `-Dlinks.fixture.dev.runtime.directory`, поскольку JVM property имеет ещё более высокий приоритет.

Для постоянного выбора вручную добавьте/обновите **один** ключ `links.fixture.dev.runtime.directory` в существующем `secure.local.override.properties`, указав путь из `latest-runtime.txt`. Пароль, адреса Ignite и настройки HTTP остаются прежними. Для другого `env` нужен его собственный ключ; dev не применяется к ift.

**3. Проверить подключение и чтение без записи:**

```powershell
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksConnectionTest' --rerun-tasks -x testOpsUpload --console=plain
```

Это первая проверка корпоративного подключения новым клиентом. Успех подтверждает вход, чтение пяти кэшей и формат хранения; права записи/удаления ещё не проверены.

**4. При успешной диагностике запустить функциональный набор:**

```powershell
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksFunctionalFlowTest' --rerun-tasks -x testOpsUpload --console=plain
```

Ожидается выполнение 70 вариантов с очисткой собственных данных после каждого. При первом запуске не нужно повторять 103 негативных варианта: замена клиента fixture не исправляет их HTTP 500.

## Если подготовка или подключение упали

| Ошибка | Что означает / следующий шаг |
|---|---|
| `Could not resolve`, 401/403, timeout, сертификат Nexus | Проверить доступ к уже настроенным репозиториям и их учётные данные на ВАРМ |
| `Could not find com.sbt...:17.6.0` | В настроенных репозиториях не найден нужный артефакт; запросить у команды сервиса репозиторий с этой поставкой и подключить его штатным способом проекта |
| `Expected one provider of ...BinaryObject.class` | Запущена предыдущая версия init-скрипта. Заменить его исправленным файлом и повторить ту же команду; удалять скачанные JAR и Gradle-кэш не требуется |
| `Missing or conflicting providers` | Отсутствует обязательный класс либо обнаружены разные копии вне разрешённой пары core/binary-api. Проверить `dependency-diagnostics.json`, не удалять JAR вручную |
| `Corporate helper compilation failed` | API корпоративного клиента отличается от Apache; лог находится в `build/explab-2974-client-compile/<hash>/compile.log`, подготовка не переключает клиент. Потребуется адаптация helper по конкретной ошибке |
| Повторный `Channel is closed` | Смена библиотек сама по себе проблему не решила. Нужны серверные логи handshake, проверка эффективного TLS и политики доступа с ВАРМ |
| Ошибка чтения/схемы после успешного входа | Подключение продвинулось дальше прежнего сбоя; проверить права/метаданные по тексту probe, не отключать проверки схемы |

Для разбора сохранить `dependency-diagnostics.json`, а при их создании — `dependency-resolution.json`, `client-libraries.lock.json`, `compile.log`, `build/explab-2974-fixtures/dev/probe-*`, JUnit XML и сырые Allure. Перед отправкой проверять логи сторонних компонентов на наличие секретов. Пароли и настройки Nexus скрипт не печатает.

## Откат выбора клиента

Если меняли только переменную текущего PowerShell:

```powershell
Remove-Item -LiteralPath 'Env:\LINKS_FIXTURE_DEV_RUNTIME_DIRECTORY' -ErrorAction SilentlyContinue
```

Если сохраняли настройку в файл, восстановить прежнее значение `links.fixture.dev.runtime.directory` либо удалить только добавленный ключ. Исходный Apache-комплект остаётся на месте; это возможность отката конфигурации, а не исправление его прежнего обрыва подключения. Не удалять клиенты, которыми были созданы незавершённые fixture.

При повторной подготовке прежний каталог переиспользуется, если библиотеки и исходники не изменились. Изменения создают другой каталог по SHA256, поэтому старый клиент остаётся доступен для восстановления данных. JAR data-operator для этой схемы не нужен.
