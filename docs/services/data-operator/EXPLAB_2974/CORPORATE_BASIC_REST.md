# EXPLAB-2974: базовые REST-проверки в корпоративной среде

Пакет содержит **103 варианта проверки входного контракта** `POST /api/v2/data-operator/splitting-objects-links` по v7. Запросы выполняет существующий REST-клиент проекта через `EnvironmentConfigWithRest`, `RestFlows` и `DataOperatorV2Steps`. Ответы возвращает развёрнутый data-operator выбранного тестового стенда.

## Окружение и необходимые условия

Окружение выбирается штатной настройкой `env` проекта. Для него используется `rest.<env>.data-operator.base-uri`; `RestEndpointResolver` выполняет существующую нормализацию окружений. Например, `ift-ds` соответствует ключам `rest.ift.*`, а `ift-dm` — `rest.ift-dm.*`. В сохранённой корпоративной версии источником этих значений служит `src/test/resources/test.properties`. В более новой версии проекта сохраняется её штатный приоритет настроек.

Адрес data-operator необходимо задать явно: существующий resolver допускает fallback на gateway. Base URI содержит только адрес размещения сервиса, без повторного добавления `/api/v2/data-operator`; путь endpoint добавляет `Endpoints.DataOperatorV2.SPLITTING_OBJECTS_LINKS`. Учитывайте действующий ingress-префикс своего проекта. В Allure нужно проверить итоговый URI фактического запроса.

Используются действующие сертификаты, ключи, настройки доступа и REST-конфигурация проекта. Патч их не заменяет. Обязательны доступ к выбранному тестовому стенду и версия data-operator, содержащая метод EXPLAB-2974. Базовое тело запросов использует точку `MAPPER`, параметр `productName`, тип `STRING` и оператор `equal`, как существующий `DataOperatorV2TestDataFactory`. Для диагностики запросов, которые дефектная реализация пропускает через валидацию, проверьте наличие соответствующих метаданных на стенде. Значение `expId=101321` является частью запроса расчёта и не создаёт эксперимент.

В каждом варианте проверяется HTTP 400, JSON Content-Type и контракт ошибки: `id` UUID, строковое `message="Некорректный запрос"`, допустимая длина, объектный `params` при наличии. Это также частично проверяет SL-50. Тело передаётся как исходный JSON, чтобы сохранить отсутствующие поля, null, неверные типы и большие числа. Отсутствующее HTTP-тело не подменяется JSON null. Запрос/ответ сохраняются вложением Allure до проверки результата, в том числе при падении.

Сценарии не создают объекты, эксперименты или метаданные, не отправляют сообщения Kafka и не выполняют запись/очистку БД. Поэтому подготовка D1 и teardown данным проверкам не нужны. Патч не содержит заглушек, локального сервиса, Docker-конфигурации, подмены HTTP-ответов или unit-тестов с синтетическими ответами.

## Границы поставки и интерпретация результатов

Это базовая часть заявки: 10 идентификаторов плана с негативными вариантами и общие проверки SL-50. **103 варианта не означают 103 требования, полное выполнение 50 строк плана или покрытие 83%.** Позитивные границы SL-41/42, положительные сценарии на D1, проверки отказов и транспортной безопасности в этот архив не включены.
