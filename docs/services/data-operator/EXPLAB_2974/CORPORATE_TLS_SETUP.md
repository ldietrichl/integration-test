# EXPLAB-2974: TLS корпоративного fixture-клиента

## Подтверждённые результаты 08.09.2026

1. `keytool -printcert -sslserver` получил цепочки сертификатов с каждого узла `tsled-mvp000384/385/386.esrt.sber.ru:10800`. Имена DNS в сертификатах соответствуют узлам, сроки действия до 31.10.2028. Это подтверждает ответ TLS на адресах; доверие Java к цепочке и вход в Ignite этим не проверены.
2. В `result_shell_terminal (8).txt` последняя попытка использовала корпоративный runtime `4cb3dd5896dda8616b95136295dfa413b1dc7c20db313517aa29ba41864fc3d3` и `sslEnabled=true`. Выполнился один диагностический тест, он упал. 42 секунды — время всей сборки.
3. В `probe-3649d914-ca37-4abf-a770-66ffcf66a297.log` исходная ошибка — `IllegalStateException: KeyManagerFactoryImpl is not initialized` из `ClientSslUtils.getKeyManagers:221`. Она возникает при создании SSLContext до сетевого подключения. Ошибки сертификата сервера, пароля Ignite или доступа к кэшам в этой попытке ещё не диагностировались.

По контракту JDK `getKeyManagers()` выбрасывает такое исключение, если фабрика не инициализирована. В публичном исходнике Apache Ignite 2.17.0 имеется соответствующая ветка: при отсутствии пути keystore вызов init пропускается, а getKeyManagers выполняется. Это объясняет механизм; точный исходник корпоративного ClientSslUtils 17.6.0 в присланных артефактах отсутствует.

- [JDK KeyManagerFactory](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/javax/net/ssl/KeyManagerFactory.html#getKeyManagers())
- [Apache Ignite ClientSslUtils 2.17.0](https://github.com/apache/ignite/blob/2.17.0/modules/core/src/main/java/org/apache/ignite/internal/client/thin/ClientSslUtils.java)

Ошибка не доказывает обязательность клиентского сертификата на сервере. Поле `clientAuth` в назначениях сертификата сервера также не устанавливает требования сервера к входящим клиентам.

## Исправление helper

`LinksCacheTool` передаёт явную фабрику SSLContext через `setSslContextFactory`; такой способ подключения используется и в исходнике data-operator. Фабрика helper:

- загружает настроенный клиентский keystore и инициализирует KeyManagerFactory до получения менеджеров;
- без keystore использует пустой набор клиентских ключей; сервер, требующий клиентский сертификат, по-прежнему вправе отклонить подключение;
- всегда инициализирует TrustManagerFactory: из указанного truststore или стандартного хранилища доверия JDK;
- сохраняет проверку сертификатов, не включает trust-all и не добавляет произвольные сертификаты в доверенные;
- печатает только факт подготовки контекста, наличие настройки keystore и источник truststore, без паролей и содержимого ключей.

Существующие fixture-ключи `ignite.ssl.keyStore`, `keyStorePassword`, `keyStoreType`, `trustStore`, `trustStorePassword`, `trustStoreType` сохраняются. Если значения не переданы в среде helper, учитываются соответствующие свойства `javax.net.ssl.*` его JVM. Тип явно указанного хранилища по умолчанию JKS, как у прежнего клиента; PKCS12 следует указывать явно.

TLS включается только при `links.fixture.<env>.ignite.ssl.enabled=true`. Для разовой проверки корпоративный build принимает `-Plinks.fixture.dev.ignite.ssl.enabled=true`: существующий ключ из защищённого файла переопределяется project property и передаётся в JVM теста. После успешной проверки можно сохранить true в существующем `secure.local.override.properties` только для нужного окружения.

## Применение и последующая проверка

Изменён исходник helper, поэтому старый готовый runtime содержит прежний код. После установки патча надо подготовить **новый** runtime и выбрать его. Скрипт подготовки вычислит новый SHA256; существующий каталог с hash `4cb3...` не редактировать. Зависимости и их версии не менялись. Сначала можно использовать `--offline` с уже заполненным Gradle-кэшем ВАРМ; при нехватке метаданных повторить подготовку без этого флага в корпоративной сети.

После успешной подготовки новый путь брать из `corporate-runtimes/latest-runtime.txt`. Для диагностики `-Plinks.fixture.dev.runtime.directory=<новый путь>` имеет приоритет в корпоративном build, если этот ключ уже есть в защищённом файле. Если такого ключа нет, использовать `LINKS_FIXTURE_DEV_RUNTIME_DIRECTORY` в текущем PowerShell. Подробная команда, применяющая оба варианта выбора, находится в INSTALL_CORP.md патча.

Ожидаемое изменение: в probe-логе появляется `FIXTURE_TLS_CONTEXT=initialized`. Это означает только успешное создание локального TLS-контекста. Далее возможны:

| Результат | Следующее действие |
|---|---|
| `PKIX path building failed` / ошибка доверия | Настроить truststore с проверенной корпоративной цепочкой CA; сам факт получения цепочки через keytool не является проверкой её доверенности |
| Сервер сообщает об отсутствии/неприемлемом клиентском сертификате | Уточнить mTLS и получить разрешённый клиентский keystore; серверный сертификат не заменяет клиентский приватный ключ |
| `ClientAuthenticationException` | Проверить учётную запись Ignite и серверный журнал аутентификации |
| Снова `Channel is closed` после создания TLS-контекста | Сопоставить TLS и Ignite журналы с моментом попытки; это уже иной этап, чем ошибка неинициализированной фабрики |
| Отсутствие кэша / ошибка схемы / прав чтения | TLS и вход могли пройти; разбирать конкретное исключение probe |
| PASSED и корректный `probe-result.json` | Подключение, чтение пяти кэшей и схема проверены; можно переходить к функциональным сценариям |

Локальные Gradle, компиляция, тесты и соединения не запускались по указанию пользователя. Выполнены статическая проверка пути инициализации JDK-менеджеров и проверка состава архива. Подтверждение компиляции корпоративным клиентом и прохождения TLS остаётся за запуском на ВАРМ. Изменение не добавляет библиотек, секретов или заглушек; данные fixture в неуспешной попытке не создавались.
