# EXPLAB-2974: корпоративные тесты без JAR сервиса

Эта версия заменяет подготовку данных через библиотеки развёрнутого сервиса. **Параметр `links.fixture.<env>.service.jar` больше не нужен.** Все необходимые клиентские библиотеки находятся в `tools/data-operator-explab-2974/lib` и входят в архив. На корпоративном компьютере для них не требуются Maven, скачивание из интернета или распаковка приложения. Штатные зависимости самого тестового проекта остаются прежними.

## Что изменилось

Отдельная JVM использует фиксированный Apache Ignite 2.18.0 и Jackson 2.17.2. Десять библиотек перечислены в `client-libraries.lock.json` с SHA256; перед запуском проверяются их контрольные суммы. В runtime не подключаются классы `explab.dataoperator` и библиотеки Spring Boot приложения. JDK 17 компилирует две небольшие утилиты при первом запуске; собранный клиент переиспользуется последующими сценариями. Его библиотеки не добавляются в Gradle classpath тестов.

Метаданные точек формируются через BinaryObject API по фиксированному контракту `explab-2974-storage-v1`. До записи проверяются имена, типы и полный состав полей трёх структур, а также существующие соответствия имён и номеров enum. Сверка выполняется с реальной метаинформацией Ignite. Неизвестная схема останавливает подготовку до записи строк тестовых данных; клиент не пытается угадать новый формат. Совместимое добавление enum в конец списка допустимо, перестановка прежних значений — нет.

Обновление сервиса, сохраняющее этот контракт хранения и протокол Ignite, не требует замены клиентского набора. При изменении структуры метаданных потребуется обновить адаптер тестов. Совместимость Apache-клиента с корпоративным Ignite из поставки Сбер пока должна быть подтверждена на ВАРМ отдельным диагностическим тестом. Успешный TCP-тест не подтверждает протокол, аутентификацию или права.

Подход BinaryObject без классов приложения соответствует [документации Apache Ignite](https://ignite.apache.org/docs/ignite2/latest/key-value-api/binary-objects). Ограничения на смену типов полей и порядок enum учтены проверкой контракта.

## Состав и жизненный цикл

Бизнес-набор прежний: **70 функциональных + 103 негативных = 173 варианта**. Функциональные проверки сохраняют flow/rest-стиль и существующие методы проекта. Каждый вариант получает две уникальные точки `EXPLAB2974_<UUID>_SP1/SP2`. Объекты создаются реальным REST-запросом `/api/v2/data-operator/kafka/stub/{point}`; этот путь принадлежит сервису и действительно сохраняет данные. В корпоративном архиве нет HTTP-заглушек, локального Docker-стенда или реализации ответов сервиса.

Метаданные создаются через Ignite, поскольку в исследованном архиве отсутствует нужный REST CRUD. До записи проверяется отсутствие чужих записей с такими точками; используется `putIfAbsent`. Перед первой записью создаётся файл владения. После REST-загрузки проверяются ключи, все поля и количества собственных объектов. После каждого сценария, в том числе упавшего, удаляются только принадлежащие его UUID записи в пяти кэшах и проверяется нулевой остаток.

Отдельный `DataOperatorLinksConnectionTest` выполняет вход в Ignite, чтение кэшей и проверку схемы. Он не создаёт данные и не считается дополнительным покрытием заявки. Успешный результат не доказывает права записи/удаления: они проверяются фактическим жизненным циклом функциональных сценариев. Та же проверка запускается автоматически перед функциональным классом.

## Настройки

Адрес сервиса и окружение выбираются штатными `env` и `rest.<env>.data-operator.base-uri`. Приоритет fixture-параметров: JVM property, переменная среды, штатный файл защищённых настроек, `test.properties`. Пути указаны относительно корня проекта; рабочий каталог IDE/Gradle должен быть корнем проекта.

| Параметр | Назначение |
|---|---|
| `links.fixture.dev.enabled=true` | Включить подготовку тестовых данных на dev |
| `links.fixture.dev.ignite.addresses` | Адреса трёх узлов из ConfigMap |
| `links.fixture.dev.ignite.ssl.enabled=false` | Режим из ConfigMap dev; HTTP HTTPS/mTLS не изменяется |
| `links.fixture.dev.ignite.username` | Учётная запись Ignite |
| `links.fixture.dev.ignite.password` | Ссылка на ключ секрета; само значение хранится в локальном защищённом файле |
| `links.fixture.<env>.runtime.directory` | Необязательный путь к комплекту клиента; по умолчанию `tools/data-operator-explab-2974` |
| `links.fixture.<env>.output.directory` | Необязательный путь для манифестов и логов; по умолчанию `build/explab-2974-fixtures/<env>` |

Существующие параметры Ignite username/password и TLS keystore/truststore сохраняются для окружений с SSL. `service.jar`, `service.jar.sha256` и `helper.source` текущий runtime не использует. Для нового окружения нужны его собственные fixture-настройки; dev-параметры не применяются к ift автоматически.

Разовая поставка по явному запросу пользователя включает `secure.local.override.properties`, подготовленный на основе предоставленного корпоративного файла. Его прежние значения сохранены, добавлены только fixture-настройки dev и отдельный ключ пароля Ignite. Шаблон в документации остаётся без секретов. Не переносить пароль в исходники, обычную документацию или манифесты. Разовый архив содержит секреты; следующие поставки по умолчанию должны снова исключать этот файл.

## Проверка на ВАРМ

Сначала выбрать `env=dev` в существующем `src/test/resources/test.properties` и проверить REST-адрес именно тестируемого data-operator. Файл `test.properties` патч не заменяет.

Проверить компиляцию:

```powershell
.\gradlew.bat testClasses -x testOpsUpload --console=plain
```

Проверить вход и чтение Ignite без записи:

```powershell
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksConnectionTest' --rerun-tasks -x testOpsUpload --console=plain
```

Запустить оба бизнес-класса:

```powershell
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksFunctionalFlowTest' --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksValidationFlowTest' --rerun-tasks -x testOpsUpload --console=plain
```

Ошибка диагностики содержит путь к `probe-*.log` в каталоге fixture. Серверное исключение в этом файле позволяет отличить неверный пароль, несовместимость клиента, недостаточные права и изменение схемы. Не заменять неуспешную диагностику пропуском тестов или успешным результатом. Сведения о пароле в отчёт не добавляются; соединение получает секрет через среду дочерней JVM.

## Восстановление и обновления

Новые манифесты имеют schemaVersion=3 и `fixtureRuntimeSha256`. После прерванной JVM запустить `util.dataoperator.LinksFixtureRecovery.main` с test classpath из корня проекта, передав абсолютный путь к `fixture-manifest.json`. Проверяются окружение, адреса, UUID и исходный клиентский комплект. Повторная очистка допустима. Пять значений `remaining` должны быть нулевыми.

Незавершённые манифесты предыдущего schemaVersion=2 необходимо восстановить предыдущей версией патча до установки этой версии. Они привязаны к прежнему runtime и JAR. Сначала восстановить данные, затем менять клиент или запускать `clean`; иначе будут потеряны сведения для адресной очистки. Завершённые старые результаты можно сохранить как историю.

Результаты локальной проверки новой версии и фактический состав архива фиксируются в `INSTALL_CORP.md` и манифесте конкретной поставки. Тесты не ослабляют ожидания v7 для получения зелёного отчёта.
