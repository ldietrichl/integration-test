# EXPLAB-2974: функциональные REST-сценарии и корпоративный запуск

**Обновление 08.09.2026:** текущая версия использует фиксированный клиент и больше не требует JAR сервиса. Актуальные настройки, запуск и миграция — [в инструкции без JAR](CORPORATE_STATIC_CLIENT.md). Ниже сохранено описание предыдущей поставки от 07.09.2026; её требования `service.jar` относятся только к старому runtime.

Набор включает **70 функциональных вариантов** в `DataOperatorLinksFunctionalFlowTest` и **103 варианта входного контракта** в `DataOperatorLinksValidationFlowTest`. [Матрица функциональных сценариев](FUNCTIONAL_CASES_20260907.md). Ответ рассчитывает реальный data-operator, выбранный штатной REST-конфигурацией проекта.

## Функциональная область

Проверяются точные множества связей, группировка и отсутствие дублей; несколько экспериментов/условий и пустые результаты; AND/OR; сравнения INTEGER, NUMBER, STRING, BOOLEAN; IN/NOT IN; is_null/is_not_null; отсутствие/null/пустые фильтры и их пересечение; одинаковый id у разных родителей, строковые ключи `001`, `1`, `CJ-01`; отсутствие родительского ключа и типа ключа объекта; точные границы expId и number. Ожидания заданы по D1 независимо от кода сервиса.

Функциональные варианты затрагивают 31 ID плана, вместе с негативными — 39 из 50 ID. SL-50 дополнительно проверяется частично общим оракулом ошибок. **39/50 — 78% по наличию автоматизированных сценариев, не полное покрытие требований и не доля успешных проверок.** Полнота строки требует выполнения всех её условий; проверки текстового лога, транспортной безопасности и спорные варианты не считаются закрытыми. Не реализованы SL-14/15/23/24/28/44/46/47/48/49 и остаток SL-50. Неоднозначные ожидания из U-вопросов плана не подменяются текущим поведением сервиса.

## Жизненный цикл данных

Каждый функциональный вариант создаёт две собственные точки `EXPLAB2974_<UUID>_SP1/SP2`. Перед записью проверяется отсутствие записей этих точек во всех пяти кэшах. В `build/explab-2974-fixtures/<env>/case-<UUID>/` сохраняется манифест, а перед первой записью — отдельный файл владения. Существующие записи не перезаписываются.

Метаданные параметров и источников двух точек добавляются точечно через Ignite. Это необходимый fallback исследованной сборки: в ФП и архиве не найден REST CRUD для этих метаданных, а `update-dicts` читает источники с фиксированной точкой MAPPER. Для метаданных используются DTO и мапперы из JAR развёрнутого сервиса, а не собственная модель сериализации.

**Объекты загружаются только REST-запросами** `/api/v2/data-operator/kafka/stub/{point}` через существующий `DataOperatorV2Steps`. Это контроллер настоящего data-operator из архива; он вызывает реальные очистку JSON, flattening и сохранение записей. Само наличие слова `stub` в URI не означает, что тест подменяет ответ. В корпоративном пакете нет HTTP-сервера, имитаторов зависимостей, локального Docker-стенда или изменённого кода сервиса.

После загрузки проверяются собственные количества во всех пяти кэшах, полный набор ключей и фактические значения объектов. Только затем отправляется запрос расчёта связей. Для SL-12 загружаются только метаданные, поскольку проверяется ранний ответ при отсутствии типа ключа.

`try-with-resources` выполняет cleanup после каждого варианта, включая упавшее утверждение и частичную подготовку. Удаляются только записи точек текущего UUID в `splitting_object_cache`, `splitting_field_cache`, `actualization_cache`, `param_cache`, `data_source_cache`; используются условные удаления конкретных ключей. После удаления проверяется нулевой остаток. Ошибка cleanup сохраняет манифест и завершает тест ошибкой; при исходной ошибке она остаётся suppressed exception. Убийство JVM требует отдельного восстановления по сохранённому манифесту.

## Почему нет REST-очистки

Код `saveRecords` удаляет прежние записи только при замене непустыми входящими объектами. Пустой набор не содержит родителей, которые нужно удалить; `messageInfo.action` загрузчик не обрабатывает. Эксперимент 07.09.2026 на собственных локальных точках подтвердил:

| Действие | Фактический ответ | Остаток объектов / полей |
|---|---|---:|
| POST с `cjConfig.objects=[]` | 200 OK | 7 / 46, без удаления |
| POST объектов с `messageInfo.action=DELETE` | 200 OK | 7 / 46, без удаления |
| HTTP DELETE на маршрут загрузки | 500 от обработчика ошибок сервиса | 7 / 46, без удаления |
| Точечная очистка Ignite по UUID | Удаление подтверждено | 0 / 0, также 0 собственных метаданных |

Очистка первого из двух одновременно подготовленных наборов сохранила все 59 записей второго. Подстановка MAPPER в манифест отклонена. Частичная загрузка из 6 объектов, 39 полей, 1 актуализации и 4 метаданных очищена; повторное восстановление тоже оставило ноль записей. Поэтому пустой POST или DELETE-сообщение не используются как фиктивная очистка.

## Настройки корпоративного окружения

REST-адрес и HTTP-сертификаты остаются штатными настройками проекта: `env`, `rest.<env>.data-operator.base-uri`, действующий keystore и секреты. Нужен явный адрес data-operator, поскольку существующий resolver допускает fallback на gateway. Для `ift-ds/eift` используются нормализованные ключи `ift`; для `ift-dm` — `ift-dm`.

Дополнительные параметры подготовки привязаны к тому же нормализованному окружению. В существующий `test.properties` вручную добавляются несекретные значения; пароли — в существующий локальный защищённый файл настроек. Используйте прямые слеши в путях `.properties`.

| Суффикс после `links.fixture.<env>.` | Назначение |
|---|---|
| `enabled=true` | Включение подготовки собственных данных на выбранном стенде |
| `service.jar` | Полный путь к Spring Boot JAR именно развёрнутого data-operator; бинарник в патч не включён |
| `service.jar.sha256` | Необязательная проверка SHA256 указанного JAR |
| `ignite.addresses` | Реальные адреса thin-client Ignite этого data-operator: `host:port`, несколько через запятую |
| `ignite.ssl.enabled` | Обязательное `true`/`false`, соответствующее настройкам данного Ignite |
| `ignite.username`, `ignite.password` | Учётные данные Ignite, если включена аутентификация |
| `ignite.ssl.trustStore`, `ignite.ssl.trustStorePassword`, `ignite.ssl.trustStoreType` | Доверенное хранилище TLS Ignite при необходимости |
| `ignite.ssl.keyStore`, `ignite.ssl.keyStorePassword`, `ignite.ssl.keyStoreType` | Клиентский сертификат TLS Ignite при необходимости |
| `output.directory` | Необязательный каталог манифестов; по умолчанию `build/explab-2974-fixtures/<env>` |

Приоритет дополнительных параметров: JVM property → переменная среды с преобразованным именем → штатные `secure.local*.properties` → `test.properties`. Плейсхолдеры и защищённые значения обрабатывает существующий `SecurePropertyResolver`. Пароли передаются helper-процессу через среду, не через командную строку или манифест. TLS не отключается автоматически. Настройки HTTP mTLS и TLS Ignite относятся к разным соединениям.

JDK 17 извлекает библиотеки из указанного JAR в каталог runtime рядом с манифестами и один раз компилирует `tools/data-operator-explab-2974/LinksCacheTool.java`. Helper запускается отдельной JVM; он не запускает сервис. Его библиотеки не добавляются в общий Gradle classpath, зависимости тестового проекта не заменяются. Временные соединения ограничены таймаутами. При недостающих настройках/JAR класс завершается ошибкой подготовки, без успешных или пропущенных сценариев.

Доступность REST-загрузки и thin-client Ignite на корпоративном стенде пока не подтверждена. Если они закрыты, для выполнения этих сценариев нужны доступ к ним либо согласованный реальный API подготовки/удаления. Обход контроля доступа не предусмотрен; GET справочников и `update-dicts` не заменяют отсутствующий CRUD.

## Запуск и восстановление

Запускайте из корня проекта с выбранным окружением:

```powershell
chcp 1251 > $null
$enc = [System.Text.Encoding]::GetEncoding(1251)
[Console]::InputEncoding = $enc
[Console]::OutputEncoding = $enc
$OutputEncoding = $enc

.\gradlew.bat testClasses -x testOpsUpload --console=plain
.\gradlew.bat test --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksFunctionalFlowTest' --tests 'ru.sber.qa.dataoperator.EXPLAB_2974.DataOperatorLinksValidationFlowTest' --rerun-tasks -x testOpsUpload --console=plain
```

Ожидаются 70 + 103 = 173 исполнившиеся проверки. Старый локальный `DataOperatorLinksFixtureFlowTest` не нужен и в новый корпоративный патч не входит. `bypassTests` для проверки endpoint не применяется. Автозагрузка в TestOps исключена.

После прерванной JVM запустите main-класс `util.dataoperator.LinksFixtureRecovery` в IDE с test classpath, рабочим каталогом корня проекта и единственным аргументом — абсолютным путём к `fixture-manifest.json`. Используйте то же окружение, адреса и JAR. Перед очисткой проверяются принадлежность файла каталогу данного окружения, совпадение адресов/сборки и точные UUID точек. В `fixture-cleanup.json` все пять значений `remaining` должны быть 0. Сначала восстановите незавершённые наборы, затем повторяйте тесты. Не удаляйте каталог манифестов командой clean до восстановления.

## Локальная проверка перед архивом

Два полных последовательных запуска на настоящем data-operator из архива `06fd6acb646`: каждый **173/173, 52 passed, 121 failed, 0 skipped/broken/aborted**. Функциональная часть: **52 passed / 18 failed из 70**; негативная: **103 failed из 103**. Исходные 74 Java-файла сервиса не менялись; локальный профиль использовал Apache Ignite 2.18.0 и Kafka 3.9.1. Результаты повторов совпали, инфраструктурных проблем не обнаружено.

Во втором прогоне удалены 464 объекта, 3051 поле, 136 актуализаций и по 140 записей метаданных параметров/источников. Остаток собственных данных всех 70 наборов — 0. Сверены 173 JUnit-результата, 173 HTTP-обмена, 173 Allure result-файла, 186 container-файлов и 1067 вложений, без потерь. Запросы подготовки и диагностические эксперименты не посчитаны дополнительными приёмочными сценариями.
