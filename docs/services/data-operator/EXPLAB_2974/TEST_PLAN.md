## Фиксированная выборка D1

`SP1` — тестовая точка с ключом объекта типа `INTEGER` и родительским ключом типа `INTEGER`; `SP2` — другая точка. `id` и `parentId` хранятся/передаются строками. Имена точек и идентификаторы ниже синтетические. Не заменять ими существующие бизнес-данные.

| Объект | Точка | parentId | id | productName / STRING | channelId / INTEGER | amount / NUMBER | enabled / BOOLEAN | note / STRING |
|---|---|---|---|---|---:|---:|---|---|
| A | SP1 | `1001` | `101` | Кредит | 10 | 9.50 | true | A |
| B | SP1 | `1001` | `102` | Кредит | 20 | 10.00 | true | пустая строка |
| C | SP1 | `1002` | `103` | Вклад | 20 | 10.50 | false | поле отсутствует |
| D | SP1 | `1002` | `101` | Кредит | 30 | 20.00 | false | D |
| E | SP1 | отсутствует | `104` | Страхование | 30 | 0.00 | true | поле отсутствует |
| F | SP1 | `1002` | `105` | Авто Кредит VIP | 10 | -1.00 | false | F |
| X | SP2 | `9001` | `999` | Кредит | 20 | 10.00 | true | X |

Для строк таблиц ниже `A,B,D` означает ровно три пары из D1, сгруппированные как `parentId=1001 → ids=["101","102"]`, `parentId=1002 → ids=["101"]`. `∅` означает пустой `splittingObjects` внутри сохранённой записи эксперимента и условия; это не означает пустой корневой `links`. Базовый запрос: `SP1`, `expId=101321`, условие `number=1`, `rules=[[productName STRING equal ["Кредит"]]]`, ограничения идентификаторов отсутствуют.

Для DATE/DATETIME, строковых ключей, отсутствующего родительского ключа и большого объёма используются отдельные вариации D1, указанные в сценариях. Все поля, участвующие в правилах, должны быть описаны в справочнике тестовой точки.

## Бизнес-выборка D2: эксперимент — CJ — конфигурация коммуникации

На выделенном контуре создать тестовые CJ MAPPER с реальными записями источника и дождаться загрузки в Ignite. Маппинг S3: `cjId` из `$.Id` — родитель INTEGER (стр. 543); `configCommId` из `$.stages[].products[].channels[].templates[].configCommId` — ключ STRING (стр. 552); `productName` — STRING (стр. 549). Значения ниже — фиксированные тестовые идентификаторы; при занятости заменить взаимно однозначно и сохранить таблицу соответствия. Каждый configCommId поместить в отдельный элемент products, чтобы изменение productName у M2 не меняло M1. У CJ остальные обязательные поля валидны по его схеме. Внешние боевые данные не используются.

| Объект | CJ / parentId | configCommId / id | productName |
|---|---|---|---|
| M1 | 71001 | 81001 | Кредит |
| M2 | 71001 | 81002 | Кредит |
| M3 | 71002 | 81003 | Вклад |
| M4 | 71002 | 81004 | Кредит |
| M5 | 71003 | 81005 | Страхование |

Подготовить два реальных тестовых эксперимента MAPPER с допустимым для пересчёта статусом (не STOPPED/COMPLETED), одним условием number=1 и одной связанной группой каждый. Записать expId, condition_id и group_code. E_CREDIT отбирает productName STRING equal ["Кредит"], E_DEPOSIT — equal ["Вклад"]. Ограничения id отсутствуют. Запускать штатный пересчёт через внутренний `POST /api/v2/experiments/so-link-update` (mTLS, JSON): requestId — новый UUID, requestSource="EXPERIMENT_UPDATE", splittingPoint="MAPPER", expIds — массив двух числовых expId E_CREDIT/E_DEPOSIT (S3, стр. 1680–1683). Ожидать HTTP 200 без тела: это подтверждает постановку запроса, а не завершение расчёта. Не отправлять пустой expIds. Дождаться завершения по calcId/логу, затем снимать данные потребителя. Предел ожидания — параметр стенда, не SLA заявки.

| Контроль | Точный ожидаемый результат |
|---|---|
| Типы ответа links | objectIdType=STRING; parentIdType=INTEGER; сами ids и parentId — JSON-строки. |
| E_CREDIT / 1 | Ровно 71001 → ["81001","81002"] и 71002 → ["81004"]. |
| E_DEPOSIT / 1 | Ровно 71002 → ["81003"]. CJ 71003 не связан ни с одним из этих экспериментов. |
| Связи у потребителя | exp_so_link хранит exp_id, condition_no=1, соответствующие condition_id/group_code, parent_object_id=CJ; exp_so_link_id связан через link_id и содержит дочерние splitting_object_id. Сверять объединённые строки по этим полям и отсутствие лишних записей. |

## Правила операндов и область интерпретации

S1 ссылается на operator_dict. По S3, стр. 505,507, `is_required` задаёт обязательность правого операнда, `is_multiple` — его множественность. Поэтому V21–V22 уточняют общий необязательный values из S1 условно по оператору: у is_null/is_not_null допустимы отсутствие/null/[], у остальных 13 операторов нужен операнд. Проектное ожидание HTTP 400 для нарушения этих ограничений выведено из справочника и правила проверки входной структуры S1, стр. 9; это явно указанная интерпретация совместных источников, не подтверждённое поведение кода. Семантика LIKE при валидных операндах остаётся Q5.
