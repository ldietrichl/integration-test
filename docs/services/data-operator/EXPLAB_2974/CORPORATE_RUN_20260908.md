## 1. Исправление конфигурации функционального набора

Причина в строках 2912–2927 лога: [LinksFixtureConfiguration](../../../../src/test/java/util/dataoperator/LinksFixtureConfiguration.java) требует `links.fixture.dev.enabled`, а [DataOperatorLinksFunctionalFlowTest](../../../../src/test/java/ru/sber/qa/dataoperator/EXPLAB_2974/DataOperatorLinksFunctionalFlowTest.java) проверяет конфигурацию до создания набора данных. При данной ошибке этот класс не дошёл до записи метаданных или объектов; cleanup для него ещё не требовался. Это не утверждение о данных более ранних запусков.

В корпоративном проекте проверить `env` и `rest.<env>.data-operator.base-uri` в `src/test/resources/test.properties`. Здесь выбран `dev`. Если нужен другой стенд, сначала выбрать его штатной настройкой проекта, затем использовать одинаковый нормализованный суффикс для REST и fixture. Параметр `-Denv` сам по себе не переопределяет окружение в имеющемся `TestPropertiesLoader`.

Для dev дополнить существующий `test.properties` следующим шаблоном, заменив ВСЕ значения в угловых скобках реальными:

```properties
links.fixture.dev.enabled=true
links.fixture.dev.service.jar=C:/Work/service-artifacts/<JAR-развернутого-data-operator>.jar
links.fixture.dev.ignite.addresses=<thin-client-host>:<port>
links.fixture.dev.ignite.ssl.enabled=<true-или-false-по-конфигурации-Ignite>
```

Одного `enabled=true` недостаточно: следующими проверяются адрес Ignite, путь к JAR и явный режим TLS. JAR должен соответствовать развёрнутому сервису; он нужен для его DTO, мапперов и библиотек клиента, сервис из этого JAR тесты не запускают. HTTP ingress не заменяет адрес thin-client Ignite. Параметры HTTP mTLS и Ignite TLS относятся к разным соединениям. Пути в `.properties` записывать с прямыми слешами.

Если Ignite использует аутентификацию/TLS, добавить соответствующие `links.fixture.dev.ignite.username/password`, `ignite.ssl.trustStore/trustStorePassword/trustStoreType` и при необходимости клиентский `keyStore/keyStorePassword/keyStoreType` в штатные локальные защищённые настройки. Значения берутся из конфигурации именно этого стенда. Полный список и порядок разрешения — в [корпоративной инструкции](CORPORATE_FUNCTIONAL_REST.md#настройки-корпоративного-окружения).

Для выполнения также нужны разрешённые доступы к реальному REST-загрузчику `/api/v2/data-operator/kafka/stub/{point}` и к пяти кэшам Ignite для своих UUID-точек. Текущий лог ещё не проверял эти доступы. Объекты создаются через REST, метаданные и точечная очистка используют ранее исследованный Ignite fallback. Заглушки для этого запуска не нужны. Адреса, сертификаты и JAR нельзя достоверно восстановить из данного терминального лога.

## 2. HTTP 500 вместо 400 и контракт ошибки

В первом полном обмене (строки 240–295) отправлен `dataType="UNKNOWN"`, во втором (390–445) — `dataType=123`. Оба запроса на `/api/v2/data-operator/splitting-objects-links` получили:

```json
{
  "error": "Internal Server Error",
  "status": 500,
  "timestamp": "...",
  "message": "Внутренняя ошибка сервиса"
}
```

По v7 эти негативные варианты требуют **HTTP 400**, `message="Некорректный запрос"` и обязательный `id` в формате UUID. В показанных ответах отсутствует `id`. Таким образом, смена одного HTTP-статуса не исправит контракт тела. Сейчас тест останавливается на первой проверке статуса, поэтому отдельное падение на `id/message` ещё не отображается. Оракул основан на [плане по v7](TEST_PLAN_ENDPOINT_V7.md), SL-35–43, SL-45 и общей схеме ошибок.

В доступном архиве сервиса `06fd6acb646` обнаружены следующие причины и необходимые исправления:

| Код / дефект в архиве | Что исправить в data-operator |
|---|---|
| `GlobalExceptionHandler` имеет общий `@ExceptionHandler(Exception.class)` с HTTP 500; нет отдельных обработчиков `HttpMessageNotReadableException` и `MethodArgumentNotValidException` | Ошибки JSON, типов, enum, обязательных полей и диапазонов возвращать как 400 с единым DTO ошибки по v7. Не переводить все исключения в 400: настоящие внутренние сбои должны сохранять свой статус |
| Вложенные DTO не имеют каскадной `@Valid` на всём пути `exps → objectsSelectConditions → rules` | Обеспечить каскадную проверку и запрет недопустимых null-элементов до вызова бизнес-логики |
| `@NotBlank` применяется к `List<List<RuleDto>>` и enum `dataType/operatorCode` | Заменить на ограничения подходящего типа: enum — `@NotNull`, коллекции — ограничения наличия/элементов согласно v7. Простое добавление `@Valid` без этой правки способно вызвать `UnexpectedTypeException`/`HV000030` |
| `exps` отмечен только `@NotNull`; `number` — `Integer` без границ int16 | Запретить пустой `exps`, ограничить `number` диапазоном −32768…32767; не вводить неоговорённый запрет отрицательных значений внутри диапазона |
| Приведение JSON-чисел/boolean к строкам и дробей к целым может принимать неверный контракт | Строго проверять JSON-типы и точность чисел для этого запроса; не менять глобальные настройки остальных endpoint без проверки совместимости |
| Общая схема ошибки содержит `timestamp/status/error`, но не обязательный `id` | Формировать согласованный `id/message/params` по v7, использовать тот же `id` в серверном логе |

Пустые `rules` и пустые группы не следует безусловно запрещать в рамках этой правки: их трактовка имеет противоречие U2 в спецификации и выделена в SL-44. Для строк `values` необходимо сохранить допустимое отсутствие/пустоту у унарных операций.

Обработчик из архива объясняет показанные 500 при неверном `dataType`, но версия развёрнутого корпоративного сервиса и его фактический стек в файле не указаны. Поэтому это подтверждённые дефекты доступного кода и вероятный механизм корпоративных ответов, а не доказанная причина каждого из 103 результатов. В частности, если корпоративная сборка уже включает каскадную валидацию, ошибочные `@NotBlank` могут давать общий `UnexpectedTypeException`.

Число негативных вариантов по группам: SL-35 — 4, SL-36 — 1, SL-37 — 8, SL-38 — 6, SL-39 — 29, SL-40 — 27, SL-41 — 7, SL-42 — 7, SL-43 — 10, SL-45 — 4. Всего 103 уникальных индекса внутри соответствующих методов, все со статусом 500 по assertion-стекам.

На локальном прогоне 07.09.2026 негативные варианты также падали, но статусы различались: 77 ответов 500, 24 ответа 200, 2 ответа 400 с неверной схемой. Корпоративное распределение **103×500** отличается. Нельзя автоматически переносить прежнюю классификацию причин: проверить версию/image digest сервиса, маршрутизацию ingress и серверные исключения.
