# Полный план регресса data-operator

Дата анализа: 10.09.2026. Основание: локальная документация сервисов, ФП ExpLab v17 от 07.09.2026, планы задач и текущие исходники тестов. Это план проверок, а не отчёт о прогоне. В рамках подготовки документа запросы к стендам и автотесты не запускались.

План охватывает API чтения, расчёт связей, справочники, Kafka-загрузку, преобразование объектов, актуализацию Ignite, межсервисные сценарии и эксплуатационные риски. Полнота относится к обнаруженным требованиям и рискам; требования со статусом «Разработка»/«Изменение» применяются после сверки состава поставки. Открытые вопросы ниже не считаются согласованным контрактом.

**Объём: 234 сценарные строки, включая 6 проверок готовности; P0 — 95, P1 — 135, P2 — 4.** Это не количество отдельных запусков: варианты внутри строки и общая матрица RULE для трёх API выполняются отдельно. Строки LINK и RULE частично пересекаются по проверяемым требованиям; их количество не является процентом покрытия.

Аудит по отдельным положениям документации: [матрица трассировки и пробелы](REQUIREMENTS_TRACEABILITY.md). Реестр сохранён: 394 положения; полностью выражены 335 (85,03%), частично — 6, требуют уточнения ожиданий — 51, без сценария — 2. ## 2. Как выполнять и трактовать таблицы

Все строки изначально имеют статус **Не запускался**. Каждую перечисленную вариацию выполнять отдельно; например, отсутствие поля, null и неверный тип — три проверки. Для результата сохранять `ID + вариант`, сборку, среду, предусловия, запрос/сообщение, ожидаемый и фактический результат, HTTP-статус/offset, ссылки на логи и дефект. Секреты не включать в доказательства.

| Обозначение | Значение |
|---|---|
| P0 | Основной контракт, правильность выборки и сохранность данных; первый обязательный проход |
| P1 | Полный функциональный регресс, границы, ошибки и интеграции |
| P2 | Расширенная нагрузка, эксплуатация и дополнительные исследования |

Успешный REST-ответ: HTTP 200 и контракт JSON соответствующего метода. Ошибка: проверять настоящий HTTP-статус, обязательные `id` UUID и `message`, `params` при наличии — объект, плюс запись ошибки в текстовом логе. Код 422 внутри message при HTTP 400/500 не является HTTP 422. Для 400 текст «Некорректный запрос», для 500 — «Непредвиденная ошибка». Варианты текста 422 и ограничения message — Q08/U5. Эти требования относятся к прикладным ответам, не к отказу TLS/gateway до backend.

Буквы A–F в ожиданиях — точные множества объектов фикстуры. Для LINK сравнивать пары `(parentId,id)` отдельно по `(expId,number)`, проверять дубли отдельно. Для IDS проверять ещё порядок; семантика сортировки спорных строковых/числовых ID — Q04. Для OBJ сравнивать порядок объектов, состав полей и значения; не вводить порядок колонок без подтверждения.

## 3. Данные и подготовка

### Фикстура R1 для OBJ / RULE / IDS / PARAM

Выделенная точка `REG_DO_<runId>` с уникальными строковыми ID; другой набор X в `REG_OTHER_<runId>`. Метаданные: id — key/INTEGER, parentId — parent_key/INTEGER; productName/note — STRING; channelId — INTEGER; amount — NUMBER; enabled — BOOLEAN. Отображаемые поля имеют order, родительские — parentOrder. Дополнительно создать одно скрытое поле (оба order=null) и поле с расшифровкой value/name. Фактические имена флагов метаданных сверить с поставкой (Q12).

| Объект | id | parentId | productName | channelId | amount | enabled | note |
|---|---|---|---|---:|---:|---|---|
| A | 101 | 1001 | Кредит | 10 | 9.50 | true | A |
| B | 102 | 1001 | Кредит | 20 | 10.00 | true | пустая строка |
| C | 103 | 1002 | Вклад | 20 | 10.50 | false | отсутствует |
| D | 104 | 1002 | Кредит | 30 | 20.00 | false | D |
| E | 105 | 1003 | Страхование | 30 | 0.00 | true | отсутствует |
| F | 106 | 1003 | Авто Кредит VIP | 10 | -1.00 | false | F |
| X, другая точка | 999 | 9001 | Кредит | 20 | 10.00 | true | X |

Базовый OBJ: `{page:0,size:2,splittingPointCode:<R1>,parent:false,rules:[]}`, returnIds отсутствует. Базовый IDS: `{splittingPointCode:<R1>,parent:false,rules:[]}`. Правило `productName=Кредит` означает `{dataType:"STRING",parameterCode:"productName",operatorCode:"equal",values:["Кредит"]}`. Объекты заполняются через подтверждённую схему источника; затем их состояние независимо сверяется с исходным манифестом.

Текущую автоматизированную часть запускает команда ниже после подготовки корпоративных зависимостей и выбора `env` в `src/test/resources/test.properties`. Полные инструкции и управление фикстурами: [REGRESSION_TASKS.md](../../../project/REGRESSION_TASKS.md).

```powershell
.\gradlew.bat dataOperatorRegression --offline --console=plain
```

В существующий selector входят `ru.sber.qa.dataoperator.regression.*`, `EXPLAB_2411.*`, `DataOperatorLinksFunctionalFlowTest`, `DataOperatorLinksValidationFlowTest` и `ru.sber.qa.splitter.EXPLAB_2729.*`. Отдельные ConnectionTest и FixtureFlowTest не выбираются этой задачей. Результаты сохраняются в `build/regression-results/<env>/data-operator/runs/<run-id>/`, сгенерированные фикстуры и манифесты — в `build/regression-fixtures/<env>/<run-id>/`. Обычный `clean` удаляет эти артефакты; до очистки сохраните нужные результаты и завершите восстановление данных стенда. Это описание команды; в рамках анализа она не выполнялась.

Полный регресс завершён, когда выполнены все применимые варианты, закрыты либо явно приняты оставшиеся риски, нет непринятых блокирующих дефектов P0, а исключения и непройденные P1 не скрыты общим зелёным статусом. Решения по Q/U и согласование SLO — входные условия соответствующих проверок. Skipped/broken в подготовке не считаются Pass. Если часть областей не выполнена, итог называется частичным регрессом с перечислением пробелов.
