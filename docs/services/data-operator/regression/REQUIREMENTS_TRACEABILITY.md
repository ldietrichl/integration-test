# Покрытие плана регресса data-operator по документации

Версия от 10.09.2026: дополнение до порога 85%. **Строгое покрытие — 335/394 = 85,03%**, ранее 261/394 = 66,24%. Добавлено 37 строк: [план регресса](REGRESSION_PLAN.md) теперь содержит 234 сценарные строки. Полностью выражены ещё 74 положения на неизменном реестре.

Это статическая оценка содержания плана, **не покрытие кода, автоматизации или успешного прогона**. Тесты и запросы к стенду при подготовке не выполнялись; все новые строки имеют статус «Не запускался». Статус C не снимает необходимость подготовки стенда и сверки версии поставки.

## 1. Единица и метод подсчёта

Сохранён реестр **394 проверяемых положений** восьми разделов ФП: контракты полей и ограничений, ветви алгоритмов, операции и типы данных. Это рабочая декомпозиция документа, а не официальный каталог требований его владельца. Исходные ID, тексты положений, страницы и знаменатель не изменялись; P/U/G не исключались из расчёта.

Для C требуется применимый сценарий с данными/классом эквивалентности и определённым ожидаемым результатом по данному положению. Проверки другого API не заменяют его собственный сценарий. Общая RULE-матрица выполняется отдельно для OBJ, IDS и LINK. Формула строгого покрытия: C/N×100. Наличие трассировки: (C+P+U)/N×100; это не полное покрытие.

| Статус | Значение | В строгом числителе |
|---|---|---|
| C | Проверяемое положение полностью выражено в плане в границах его формулировки | Да |
| P | Не хватает конкретной проверки или полного оракула | Нет |
| U | Ожидание остаётся неоднозначным | Нет |
| G | Нет применимого сценария | Нет |
| E | Ожидание противоречит документу; исторический статус до исправления | Нет |

Границы этой оценки существенны. Положения о LIKE сформулированы в исходном реестре как «поддержка и результат на классе эквивалентности». RULE-18/19 теперь задают такой класс на литералах, включая различие ANY/ALL и отрицание; это не 100% семантики LIKE, масок, регистра или null. По ограничениям длины/размера C означает проверку установленной границы успешного ответа либо входа; недокументированный способ обработки превышения остаётся Q14. Неопределённый результат такого запуска нельзя засчитать как Pass. Компонентные проверки ветви лимита используют управляемый результат отбора; их нельзя считать сквозным тестом поиска.

Явно заданные присваивания и константы ФП проверяются буквально. Их подозрительное название или расхождение с кодом само по себе не отменяет ожидание. Возможная редакторская правка ФП требует отдельного решения владельца; здесь она не объявляется согласованной. Противоречащие друг другу нормативные таблицы/алгоритмы (например DTO, координаты Kafka) остались P/U.

## 7. Воспроизводимость и контроль целостности

[JSON-реестр](REQUIREMENTS_TRACEABILITY.json) хранит все 394 положения, baseline_status первого аудита, previous_status/previous_note перед дополнением, текущие status/note и ссылки на сценарии. Метаданные содержат счётчики, цель 85%, число новых строк и хеши.

SHA-256 плана перед дополнением: `c19459be1e6a4ee2730e3c8e5832fc82c4df254bab68b60b2034299baf6f4d75`.
SHA-256 текущего плана: `992a22a0c52ca7a3886605ea09d470c7e8b1f3021645d79ab651f29197f1e9f8`.

Проверены уникальность и непрерывность REQ/DO-ID внутри групп, существование всех ссылок на сценарии, неизменность 394 ID/текстов/источников, совпадение Markdown-матрицы с JSON, сводные счётчики и порог без округления. Формула: число записей status=C делить на длину requirements; P/U/G не имеют дробного веса. Новые 37 строк не увеличивают знаменатель, поскольку описывают положения уже опубликованного реестра.

При следующем обновлении не удалять открытые положения ради процента. Если вводится более дробная декомпозиция (например отдельные требования на синтаксис каждой маски), публиковать новый знаменатель и пересчитывать сравниваемые версии по нему. Факт исполнения, дефекты, применимость версии и готовность стенда вести отдельно от статического покрытия.
