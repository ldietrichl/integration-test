Счётчики проверяются до split. Для проверки использования кеша текущие параметры split противоречат сохранённым:
сохранённый gold должен остаться связанным при запросе silver; сохранённый silver не должен получить связь при gold.
После невалидного запроса новый объект не должен появиться в таблице. Следующий корректный набор обязан примениться.
MAPPER использует штатные mapperFinalExp/mapperAlternative/mapperFilter; в результате эксперимента задан actionType=0.

## Уточнения по спецификации

- Входной предрасчёт: splittingObjects может быть пустым; objectParams не может быть пустым (PDF стр. 204/213/224, соответствующие версии API).
- Ошибка валидации SDK — VALIDATION_FAILED. errorDetails необязателен и может быть объектом; тест не требует непременно строки или списка всех полей.
- REST MVC может отклонить @Valid раньше SDK. В этом случае проверяются HTTP 400 и стандартный envelope с точным путём MAPPER. Это не считается проверкой Java cause-chain.
- §6.3, стр. 428: автоконфигурация — SplitterAutoConfiguration / SplitterKafkaAutoConfiguration.
  Тесты стартовых настроек выполняются изолированно: реальный Spring binding и реальная фабрика splittingExecutor для MAPPER.
  Полный старт всего приложения с Kafka/БД этими компонентными тестами не воспроизводится.
- Стр. 423–425 задают значения по умолчанию для настроек. Отсутствующее свойство с документированным default не используется как негативный тест.
  Негативные случаи: неверные типы boolean/integer/enum, вложенный null в правилах, отсутствующий/повреждённый YAML, неизвестный enum в YAML.
  Для Kafka отдельно проверяются явно заданные пустые значения шести вложенных topic-полей при создании Spring-контекста.
- Повторный uniqueConfigurationId с различающимися параметрами: спецификация не определяет выбор первого/последнего либо отказ.
  T16 не автоматизирован как приёмочный тест; наблюдаемое `(v1,v2)->v1` в SDK не превращено в требование.
- T17 требует приложения из исходного лога (`cjmapper`, `kafka-mapping-config`). В этой поставке воспроизводится вход SDK на MAPPER.
  Отправка конфигурации через `splitting-config-created` не заменяет исходный путь потребителя; T17 не заявлен покрытым.
- T22–T23 относились к альтернативной трактовке «автоконфигурации» — начальной загрузке бизнес-конфига.
  После сверки терминов документации они исключены из этой задачи; обычная загрузка REST/Kafka остаётся подготовкой сценариев.
- Граничные null-элементы, пробельные строки и конфликтующие дубликаты не получили произвольных ожиданий из реализации.

## Подготовка стенда и вложения

Требуется корпоративный общий Fabric8 с API диагностики из поставки EXPLAB_2885 v9.
Перед каждым сценарием через WorkloadRunScopeExtension.ensure читаются реальные ссылки Deployment → ConfigMap,
проверяется preliminary-calculation-enabled=true и нужный api-config-load. Изменение приводит к замене pod и ожиданию готовности.
При уже подходящих значениях повторный рестарт не требуется. Исходные значения восстанавливает общий root scope после прогона.
В fresh-профиле выполняется дополнительный рестарт; api-config-load=true отключает Kafka consumer бизнес-конфигов согласно документации.
Бизнес-конфигурация тестов после прогона не восстанавливается: используйте выделенный тестовый MAPPER, как для других изменяющих config тестов.

Имена по умолчанию взяты из EXPLAB_2690:
- workload: splitter-mapper;
- Deployment/Service/container: splitter-mapper-service;
- ConfigMap правил: splitter-mapper-service-lib;
- ключ: splitter-rules-mapper.yml.

Переопределения: exlab2891.mapper.stand.workload / .service / .deployment / .container / .service-port,
exlab2891.mapper.configmap.rules.name / .key; общие stand.<env>.workloads.* сохраняют силу.
При необходимости нестандартных имён переменных используйте exlab2891.mapper.application-env.<имя-флага>.
Разрешения общих механизмов мутации автоматически не включаются — используйте корпоративную настройку, работавшую для 2690/2885.

Allure: реальные JUnit setup → test body → teardown, именованные шаги, Splitter runtime metadata для MAPPER,
фактические управляемые ключи ConfigMap до/после, текстовый лог pod только за окно операции.
Подробности pod только при сбое; квота и readiness timeline не добавляются. Лимиты общего сборщика логов остаются действующими;
признак усечения/недоступности находится в текстовом вложении. Новый Kubernetes-клиент или kubectl не добавлены.

## Запуск в корпоративном проекте

```powershell
chcp 1251 > $null
$enc = [System.Text.Encoding]::GetEncoding(1251)
[Console]::InputEncoding = $enc
[Console]::OutputEncoding = $enc
$OutputEncoding = $enc

.\gradlew.bat testClasses
.\gradlew.bat -I gradle/exlab2891.init.gradle exlab2891OfflineChecks
# SPLITTER_API_CONFIG_LOAD=true; выставляет общий Fabric8
.\gradlew.bat -I gradle/exlab2891.init.gradle exlab2891MapperRest
# SPLITTER_API_CONFIG_LOAD=false; выставляет общий Fabric8
.\gradlew.bat -I gradle/exlab2891.init.gradle exlab2891MapperKafka
# Отдельный рестарт, API_CONFIG_LOAD=true
.\gradlew.bat -I gradle/exlab2891.init.gradle exlab2891MapperFresh
.\gradlew.bat allureReport
.\gradlew.bat testOpsUpload
```

Стендовые и SDK-задачи сразу пишут raw в build/allure-results. Не требуется перенос из отдельной папки задачи.
Проверки инфраструктуры OfflineChecks пишут в build/reports/exlab2891-offline/allure-results и не засоряют выгрузку функциональных результатов.
Не выполняйте clean между прогонами. Папка общая: старые результаты в ней тоже будут кандидатами на выгрузку;
перед новым независимым запуском сохраните старую папку отдельно. Автоматической отправки в TestOps нет.
Общий корпоративный testOpsUpload использует существующий механизм подготовки; manifest подготовленного набора следует проверить перед отправкой.

Компонентные проверки запускаются отдельно с **SDK из тестируемой сборки MAPPER и его runtime-зависимостями**:

```powershell
.\gradlew.bat -I gradle/exlab2891.init.gradle exlab2891SdkChecks "-Psdk2891Classpath=C:\Work\splitter-sdk-runtime"
```

Это каталог обычных jar (включая Spring Boot 3, Hibernate Validator и зависимости SDK), а не один executable fat jar сервиса.
Допускается список jar/каталогов через `;`. В classpath должен находиться ровно один splitter-sdk.
Компонентные тесты загружают настоящий SDK через reflection, чтобы не добавлять зависимость на неподтверждённую версию
в общий корпоративный build. Несовместимый API или отсутствующая зависимость дают ошибку; тесты не подменяют SDK своей реализацией.
Сверьте версию этого SDK с runtime metadata MAPPER. Основные стендовые задачи не требуют локального SDK и не запускают эти тесты.

## Проверка поставки

Локальная компиляция Java 17 выполняется на настоящих корпоративных main-классах и зависимостях плюс общий API v9.

## Изменения v2

Параметризация сохраняет 26 исполнений на режим, 1 fresh и 21 SDK. Пустой objectParams входит в invalidField
как `objectParams:empty-array`; прежнего метода emptyParameters больше нет. T26/T27 объединены в originalCauseChain
с именованными вариантами; в проверке порядка дубликатов вместо true/false выводятся понятные названия.
JUnit создаёт отдельный результат Allure для каждого набора данных. Изменённые имена методов/параметров могут создать
новую историю соответствующих автотестов в TestOps.

Проверяются точные типы чисел, полный набор objectId, MAIN и ALL без дублей и точные параметры результата.
Сохранность таблицы проверяется до повторного предрасчёта; последующие счётчики обнаруживают лишние частично добавленные объекты.
Fresh содержит уникальный контрольный объект и динамический split для проверки загруженного эксперимента.
SDK допускает дополнительные обёртки исключений, но требует сохранения типов, сообщений, порядка причин и места возникновения.
errorDetails остаётся необязательным; готовый SplitterException должен сохранять уже имеющиеся детали.
Подробности и границы локальной проверки: ASSERTION_AUDIT_20261005.md.
