## 1. Пустой objectParams принимается

Тест: `SplitterMapperValidation2891FlowTest.emptyParameters`, EXLAB-2891-T05.
Воспроизведено в REST- и Kafka-режимах загрузки бизнес-конфигурации.

Отправляется валидный объект с `objectParams: []`. Ожидание: отказ валидации; для используемого HTTP-адаптера — HTTP 400.
Факт: HTTP 200, soConfigVersion=102, counter.objectsAdded=1, objectsDeleted=2, totalObjects=1, notLinkedObjects=1.
Ответ сообщает об успешном применении нового набора. Последующая фактическая проверка сохранности таблицы не выполнялась:
сценарий остановился на проверке HTTP-кода.

REST requestId: `270c0098-bd58-4c35-8a8d-41155abc54e1`.
Allure UUID REST: `15ded857-eafd-4a0a-be3a-e86710aad43b`.
Allure UUID Kafka: `c448b442-9163-41a5-b8c4-fe994cc46920`.

Спецификация v16, структура предрасчёта (стр. 204/213/224 для соответствующих версий API): objectParams обязателен и не может быть пустым.
Ожидание теста обосновано. В доступном исходнике PreliminarySplittingObject.objectParams имеет @NotNull,
который допускает пустую коллекцию. Добавление только каскадного @Valid не запрещает пустой список.
Это согласуется с фактом прогона; точный commit развёрнутого SDK по строке 0.12.3 не определяется.

## 2. После предрасчёта без бизнес-конфига не появляется ожидаемый результат после его загрузки

Тест: `SplitterMapperFresh2891FlowTest.duplicateBeforeBusinessConfig`, EXLAB-2891-T15/T18.
Allure UUID: `1fa385aa-053d-4462-80c1-369c0f73066c`.

Последовательность:

1. После чистого рестарта отправлены два одинаковых объекта с ключом
   `2891-2d256576-65b3-43e1-89bf-37b840f720ec-FRESH`, segment=gold, soConfigVersion=101.
2. Ответ: HTTP 200, objectsAdded=1, totalObjects=1, totalExps=0. Дедупликация на этом этапе успешна.
3. Загружена конфигурация эксперимента 101: условие segment=gold, группа A с полным диапазоном 0..10000, actionType=0.
   Ответ LOADED, currentConfigVersion=179115670455401.
4. Выполнен split того же ключа с текущим segment=silver. Это намеренная проверка использования сохранённого gold.
5. Ответ содержит именно загруженную splittingConfigVersion, но objectResults=[] вместо MAIN эксперимента 101/группы A.

Precalculate requestId: `1738bc34-0948-4bc6-a53b-09093753a5d6`.
Split requestId: `cd743569-48dc-4070-a2a4-3f9ede3b3fa7`.
Лог: Config updated и Config load result: LOADED предшествуют Splitting completed.
Окно операции: 05.10.2026 02:31:43–02:31:45 MSK.

Спецификация v16, загрузка конфигурации (стр. 250–251): при включённом предрасчёте и существующей таблице
для новых экспериментов рассчитываются и добавляются связи с сохранёнными объектами.
Проверка MAIN обоснована. Сбой относится к актуализации связей; ошибки Duplicate key в этом сценарии не было.
Без отдельного сравнения с одиночным объектом нельзя утверждать, что причиной сбоя является именно наличие дубликата.

Вероятная причина в доступном SDK: SplitterPreliminaryLinkService.addStarted() формирует newConfigIdToObject,
объединяет с ним старые записи, но возвращает configIdToObject. Метод refresh() публикует возвращённую карту,
то есть новые связи могут не попасть в опубликованную таблицу. Это гипотеза по предоставленному снимку кода;
само отсутствие ожидаемого результата подтверждено стендовым ответом.
