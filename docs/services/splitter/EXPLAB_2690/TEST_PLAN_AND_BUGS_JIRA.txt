h1. EXPLAB-2690 — тестовый план и разбор прогона

*Исторический разбор. Актуализация 07.10.2026:* уточнение АК разрешило спор MAIN: при true требуется MAIN.resultExps=[], при false объект возвращается как несвязанный. Прежние 11 failed по запрету пустого MAIN — ошибка ожиданий автотестов, не доказательство дефекта сервиса. Текущий контракт описан в README.md и TEST_PLAN_JIRA.txt. Статусы и доказательства ниже не изменены; новый стендовый прогон после исправления assertions ещё требуется. Исправление профиля T07 подтверждено отдельным прогоном 06.10.2026.

Дата анализа: 06.10.2026. Прогон: 05.10.2026, 18:34:24–18:45:18 МСК, задача {{explab2690Coverage}}, DEV, загрузка бизнес-конфигурации через REST.
Runtime metadata: splitter 0.12.3. Номер версии сервиса не подтверждает конкретный commit или ветку поставки.

h2. Границы и предусловия

План описывает фактически выполненный REST-набор EXPLAB-2690 для MAPPER и REACTIONS. Проверки Kafka/report, расширенные матрицы других пакетов и другие заявки в этот отчёт не входят.

# Подготовить профиль сервиса общим механизмом Fabric8: прочитать текущую ConfigMap, при необходимости изменить управляемые параметры, перезапустить pod и дождаться готовности. Соблюдать lease и восстановить исходное состояние после завершения; чужой lease не снимать.
# Для REST включить {{SPLITTER_API_CONFIG_LOAD=true}}, возврат ALL и пустых объектов; выставить {{SPLITTER_ALLOW_RESULT_WITHOUT_MAIN}} согласно варианту. Конкретное применённое состояние проверять по вложению «ConfigMap — перед операцией», а не только по приложенному образцу YAML.
# Загрузить бизнес-конфигурацию через {{POST /api/v1/splitter/mapper/config}} либо {{/api/v1/splitter/reactions/config}} с новой версией, проверить HTTP 200 и {{result=LOADED}}.
# Для каждого варианта выполнить {{POST /api/v1/splitter/mapper/split}} либо {{/api/v1/splitter/reactions/split}}. splittingId подобрать под заданный диапазон распределения; идентификатор запроса уникален. Условия связывания должны соответствовать объектам варианта.
# Проверить HTTP 200, версию загруженной конфигурации, состав объектов без потерь и дублей, затем правила, эксперименты, группы и параметры согласно сценарию. Сохранить setup → test body → teardown, запросы/ответы, runtime metadata, ConfigMap, текстовый лог pod за интервал операции; подробные события — при сбое.

Для обычной сработавшей группы проверяются {{expGroup=finalExpGroup}}, корректный {{conditionId}}, параметры результата, идентификатор эксперимента и отсутствие лишних строк. Для альтернативы MAPPER {{expGroup}} относится к связи объекта, {{finalExpGroup}} — к реально сработавшей группе; альтернативная строка не должна попадать в публичный ALL. REACTIONS не должен возвращать альтернативу.

*Открытое требование R-MAIN:* текущие assertions запрещают технический пустой MAIN. Спецификация v16, стр. 91, требует результат без записи MAIN; модель v10, стр. 5–6, также требует отсутствия блока для несработавшей группы. Но алгоритм v16, стр. 96, предписывает пустую запись финального правила, а описание свойства на стр. 425 допускает пустой MAIN. До решения АК это спорный критерий, а не однозначный дефект реализации. Сам факт присутствия технической записи доказан.
При allow=true отсутствие MAIN не отменяет ALL действительно связанной сработавшей группы. Ожидание «полностью пустой ответ» в T05/T08 при true было бы неверным; текущие проверки его не используют.

h2. DRAFT-2690-01 — технический пустой MAIN при отсутствии итогового эксперимента

*Статус:* воспроизведено; классификация как продуктового бага требует согласования АК из-за противоречия требований. DRAFT-2690-01 — идентификатор раздела документа, не зарегистрированный ключ Jira.
*Окружение:* DEV, splitter 0.12.3, REST, MAPPER и REACTIONS, allow-result-without-main=true.
*Частота в этом прогоне:* 11 из 11 соответствующих выполнений; устойчивость между отдельными повторными прогонами здесь не измеряется.

h3. Минимальное воспроизведение

# Выполнить общие предусловия для MAPPER с allow=true.
# Загрузить конфигурацию и выполнить [EXPLAB-2690-02-NO-MAIN|#EXPLAB-2690-02-NO-MAIN]: объект связан с группами A/B/C, но splittingId попадает в 7500–10000, где ни одна группа не срабатывает.
# Получить успешный HTTP 200 и проверить objectResults.

*Фактически:* объект содержит запись:
{code:json}
{"ruleCode":"MAIN","resultExps":[]}
{code}
Это фрагмент ответа, не полный response. В T05/T08 одновременно возвращается корректный ALL; лишним по текущей тестовой модели считается именно технический MAIN. В T02/T06/RG-NONE сработавшей группы для объекта нет, ALL отсутствует, но MAIN=[] остаётся.

*Ожидается по текущим assertions, стр. 91 v16 и модели v10:* техническая запись MAIN отсутствует; ALL сохраняется только для реально связанной сработавшей группы. При отсутствии такой группы результат объекта пуст.
*Противоречие:* алгоритм v16, стр. 96, предписывает пустую запись финального правила; описание свойства на стр. 425 говорит о пустом MAIN при true. Поэтому фактический ответ совместим с этими пунктами, но расходится с указанной моделью и стр. 91.

*Влияние:* неоднозначная форма REST-контракта для потребителей, проверяющих наличие MAIN как признак выбранного эксперимента. Потеря реально выбранного эксперимента, неверная группа или неверный ALL этим симптомом не доказаны.
*Корневая причина:* не установлена. Присутствие MAIN=[] не доказывает, какой внутренний этап сервиса его сформировал.

h3. Контроль и решение по дефекту

Все 23 выполнения allow=false прошли, включая соответствующие отрицательные по выбору MAIN варианты. Это подтверждает управляемость профиля и зависимость наблюдения от allow=true; не разрешает противоречие спецификации.
В T05/T08 агрегированные проверки показывают единственное расхождение в составе правил: ожидался ALL, получен ALL+MAIN. В T02 строгая проверка пустоты прерывается на наличии MAIN, поэтому последующие проверки нельзя объявлять выполненными.

*Вопрос АК:* должен ли публичный REST-ответ при allow=true и отсутствии итогового эксперимента содержать MAIN с пустым resultExps или полностью исключать MAIN, сохраняя только допустимый ALL?
* Если подтверждено отсутствие MAIN — зарегистрировать один дефект по этому описанию и повторить 11 вариантов, затем весь набор 49.
* Если подтверждён пустой MAIN — уточнить модель и противоречивые пункты спецификации, затем изменить только согласованные assertions; точный состав ALL и контроль allow=false сохранить.
