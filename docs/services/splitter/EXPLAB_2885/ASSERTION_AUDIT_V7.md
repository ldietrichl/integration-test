Остальные проверки используют полную замену набора, перенос неизменных uniqueConfigurationId, fallback для отсутствующего ключа, отрицательный кеш, выбор группы/MAIN/ALL, изоляцию параллельных запросов и счётчики. Это предотвращает перезапись иной корпоративной доработки.

## Общий каталог Allure

Раньше splitterRestRegression/splitterKafkaRegression писали только в архивы build/regression-results/<env>/<stage>/runs/<id>/allure-results. testOpsUpload зависит от prepareTestOpsResults, который читает testOpsSourceResultsDir (по умолчанию build/allure-results). Поэтому одной команды testOpsUpload было недостаточно для этих архивов.

В v7 каждая из двух задач получает finalizer *AllureResults. Он выполняется после закрытия тестового JVM, в том числе при падении проверок. Перед копированием проверяются completed, счётчики JUnit/Allure, UUID, children и наличие вложений. Сохраняются исходные статусы и все файлы вложений, включая журналы сценария и подов. Общие environment/categories/executor остаются под управлением существующего отчётного механизма.

Повторный сбор того же запуска не создаёт дубликатов. Новый запуск заменяет только ранее скопированные файлы своего транспорта; другой транспорт и результаты test/IDE сохраняются. Хеши опубликованных файлов хранятся в build/splitter-allure-mirror. Изменённый файл или коллизия приводят к отказу. Незавершённый сбор блокирует prepareTestOpsResults и зависимый testOpsUpload через pending-маркер. Не следует запускать несколько Gradle-процессов записи/выгрузки одновременно; после сбоя ввода-вывода нужно повторить сбор до выгрузки.

Для уже имеющихся архивов: `gradlew.bat splitterRestRegressionAllureResults splitterKafkaRegressionAllureResults`. Для новых запусков сбор автоматический. Затем достаточно `gradlew.bat testOpsUpload`; тесты при этом повторно не запускаются. Сам патч ничего не отправляет. Общий каталог содержит также сохранённые обычные тесты/IDE; для отдельного запуска TestOps предварительно очистите результаты штатной задачей, если прежние результаты не нужны. Не делать clean между REST и Kafka.

Проверки поставки и ограничения приведены в VALIDATION.md. Исходные v6 результаты (56 = 46 PASS + 10 FAIL на каждый транспорт) не переписываются. Новый обязательный набор исключает исследовательский T37; его стендовый результат после установки v7 ещё не получен.
