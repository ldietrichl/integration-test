## Kafka

Все ошибки относятся к `Precalc2885Support.body`, строка 111, через `calculate`, строка 123. Пример из shell.txt: POST `/api/v1/splitter/reactions/pre-calculate`, requestId `b91c1845-9123-4946-b71f-64847d96b706`, soConfigVersion=100, splittingObjects=[]; ответ `HTTP/1.1 200 OK`, `content-length=0`.

Это не ошибка извлечения JSON из обёртки: в транспортном логе тело действительно отсутствует. Ошибка наступает до проверки бизнес-результата большинства сценариев.

В первоначальном helper ожидание результата Java-метода SDK было перенесено на REST endpoint без подтверждения его реализации. Исходный ZIP содержит SDK, но не код развёрнутого корпоративного REST-контроллера. Имеющийся локальный тестовый host возвращает DTO, однако не доказывает контракт корпоративного host.

До просмотра контроллера/контракта возможны два варианта:

1. Endpoint должен возвращать DTO SDK — исправить/обновить развёрнутый REST-адаптер; текущие проверки тела и счётчиков остаются обязательными.
2. Endpoint намеренно возвращает пустой успешный ответ — разделить подтверждение REST-вызова и проверки результата SDK. Бизнес-сценарии подтверждать последующим split; счётчики и версию проверять через согласованный наблюдаемый интерфейс/мониторинг. Проверку responseId такого REST-ответа обозначить неприменимой к адаптеру, а не успешной.

Для выбора нужен исходник или актуальный контракт развёрнутого обработчика `/api/v1/splitter/reactions/pre-calculate` и версия сервиса/SDK. Одного HTTP 200 недостаточно, чтобы доказать применение таблицы. Ослабление проверок без такого разграничения скроет ошибки.
