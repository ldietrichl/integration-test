# EXPLAB_2885 — предрасчёты сплиттера реакций

Дата анализа: 04.10.2026. Статус: тестовый план; тесты на стенде не запускались.

## 1. Основание и границы

Проверить, что REACTIONS рассчитывает и сохраняет связи объектов с экспериментами заранее, использует их при split и актуализирует при обновлении конфигурации, сохраняя корректность результата для каждого запроса.

В покрытии: включение функции, создание/замена таблицы, использование и обход предрасчёта в REACTIONS, обновление связей, целостность состояния, валидация входа предрасчёта, минимальная проверка его диагностики.

Вне покрытия: полный регресс MAPPER/ICP, альтернативы и подавление объектов, полный перебор операторов и типов, отдельное тестирование алгоритма хеширования, полного мониторинга EXPLAB_2398/2399/2400, всей Kafka-инфраструктуры, UI, нагрузочные SLA. Выбор MAIN/ALL проверяется только на результате предрасчёта. EXPLAB_2892 не дублируется: берётся один контроль с выбором не первой группы.

## 2. Модель проверяемой функциональности

1. `calculatePreliminary` получает полный список конфигураций объектов. Это замена набора, не добавление к нему.
2. Ключ таблицы — `uniqueConfigurationId`; `objectId` появляется из текущего split-запроса.
3. Предрасчитываются связи «объект — эксперимент — условие — группы/результаты». Сработавшая группа определяется позднее по `splittingId` каждого запроса.
4. При включённом предрасчёте известный ключ использует сохранённые связи. Известный ключ без связей не должен повторно связываться по новым параметрам запроса. Неизвестный/отсутствующий ключ рассчитывается обычным путём.
5. При выключенной функции либо отсутствии таблицы все объекты рассчитываются обычным путём.
6. При обновлении списка объектов сохранённые ключи копируются, новые рассчитываются, отсутствующие удаляются. При обновлении конфигурации экспериментов удаляются связи с остановленными и добавляются связи с новыми экспериментами.

## 3. Подготовка и критерии сравнения

### Окружение

- Инстанс REACTIONS с проверяемым SDK; зафиксировать фактическую сборку, `splittingPoint`, `rulesConfigCode=REACTIONS`, `preliminaryCalculationEnabled` и параметры формирования ответа.
- Профиль ON и профиль OFF запускать с явно заданным флагом. Горячее переключение флага не предполагается.
- Основное покрытие — Java API `calculatePreliminary`, `split`, `loadSplittingConfig`. REST используется как адаптер стенда: в integration-test заданы `/api/v1/splitter/reactions/pre-calculate`, `/split`, `/config`. Наличие адаптера и отображение SDK-ошибок в HTTP подтвердить перед запуском: в архиве SDK контроллеров нет, HTTP-коды в этом плане не выдумываются.
- Для Kafka-загрузки применять выделенную точку/инстанс и возрастающие `configVersion`; подтверждать завершение загрузки до split. Не размножать все тесты по транспортам: через Kafka повторить T25–T29 и T32.
- Для сценариев «нет конфигурации/таблицы» использовать свежий экземпляр. `clearPreliminaryHolder()` не сбрасывает `lastRequest`/историю экспериментов и не эквивалентен чистому старту.
- Изолировать состояние каждого теста. Не запускать сценарии обновления параллельно на одном инстансе, кроме специального T37.

### Оракул

- Для одинаковых конфигурации, параметров объекта и splittingId сравнивать ON с заполненной таблицей и OFF/ON без таблицы. Использовать новые экземпляры запросов: исполнитель изменяет `splittingObjects` входного DTO.
- Сравнение семантическое: порядок объектов/экспериментов нормализовать, но предварительно проверить отсутствие дублей. Не превращать ответ в Map до проверки дублей.
- Проверять `objectId`, MAIN/ALL, expId, conditionIds, expGroup/finalExpGroup, groupResultParams, layerId/layerPriority/salt/spreadValue и флаги там, где они присутствуют по контракту; `splittingConfigVersion` должна соответствовать применённой конфигурации.
- `responseId` и время не сравнивать на равенство между разными запросами. requestId и splittingId проверять на соответствие своему запросу.
- Дифференциальное сравнение дополнять независимыми ожиданиями: для C1/gold — E101/A/K10 и заданный marker; для C1/silver — отсутствие результата. Одинаковая ошибка двух веток не должна давать PASS.
- Одного успешного split недостаточно для доказательства использования кеша. T05/T06 используют намеренно противоречащие параметры, а в SDK-тесте дополнительно доступна проверка таблицы или вызовов связывания.
- Известный кешу объект без связей проверять одновременно по таблице и ответу. После удаления ключа из таблицы объект снова может связаться обычным путём: удаление из кеша не означает запрет обработки объекта.

### Вопросы, не блокирующие подготовку основного покрытия

- **Q1.** Какая редакция требований закреплена в acceptance criteria EXPLAB_2885? Карточка задачи не предоставлена. В этом плане границы определены запросом пользователя и реализацией REACTIONS; новые правила пустых conditions и полный мониторинг исключены.
- **Q2.** Может ли новый configVersion изменять правила, salt, shares или результаты существующего expId? Документированный refresh описывает дельту по ID, код также ориентируется на новые/удалённые ID. Если такое обновление допустимо, добавить обязательный параметризованный тест актуализации этих полей и считать старые значения дефектом. Пока это исследовательская проверка, а не утверждённое ожидание.
- **Q3.** Как обрабатывать дубли uniqueConfigurationId и изменение objectParams под тем же ключом? Копирование неизменного ключа описано, политика противоречащих дублей — нет.
- **Q4.** Какой статус загрузки является актуальным контрактом Java API? PDF описывает LOADED_WITH_PRECALC (например, стр. 294), но enum SDK не содержит его, успешная ручная загрузка возвращает LOADED. До согласования проверять успешное применение по версии и данным, статус фиксировать отдельно как расхождение; не смешивать его со статусом сообщения мониторинга.
