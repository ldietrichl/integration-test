Q1 — JSON-контракт и несколько связей: закрыт для реализованной матрицы

S4, страницы 95 и 284: expFlags добавляется для каждого эксперимента в ALL,
code=isAlternative, value имеет тип String; true при наличии признака, иначе false.
Пример страницы 30 подтверждает строковое значение. MAIN не получает флаг
альтернативы; null/пустой expFlags трактуется как отсутствие флагов, как в
уже принятом контракте проекта. Boolean/null вместо значения ALL не допускаются.
S1 и S4 стр.303 задают флаг эксперимента на конкретном объекте. Поэтому при
двух несработавших связанных группах A/C и сработавшей B, не связанной с объектом,
флаг относится к обоим результатам A/C этого эксперимента. T23 проверяет обе
строки и обратный порядок. MAIN удерживается отдельным F через altControl,
а R=[6] исключает откат при F.actionType=5; выбор MAIN не смешивается с разметкой.
Предыдущий широкий вопрос Q1 был избыточен: необходимые типы уже есть в S4.

Q2 — NONE и отсутствие MAIN: закрыт частично

S1 требует сработавшую группу для кандидата, поэтому NONE кандидата не образует.
T22 проверяет все шесть точек диапазонов с отдельным гарантированным MAIN=F;
нулевой finalExpGroup означает отсутствие сработавшей группы, связанные A/B
сохраняют собственные параметры в полном КАП. Ожидание полного ALL выводится
из контракта связанных результатов 2690/2984; сценарий не допускает произвольный
ALL и не опирается на фактический ответ сервиса как эталон. Публичный ALL оставляет
только сработавшие связанные строки, в NONE остаётся F. На новом стенде эта
комбинация ещё не подтверждена.
Точное решение mapperAlternative при отсутствии итогового эксперимента не
задано: нельзя без уточнения объявить объект защищённым или незащищённым.
Заблокированы T26-NO-MAIN-SOURCE и T26-NO-MAIN-RECEIVER. Ранее подтверждённые
контейнеры no-MAIN сами по себе не определяют бизнес-решение отката.

Q3 — пересечение, пустые списки и невалидные параметры: закрыт частично

S4, стр.3998 и 6432–6433: рабочие M=[0,1,2,3,4,5,6], R=[5,6]. Таким образом,
пересечение списков явно допустимо. T25-INTERSECTION проверяет значение 5,
накопление отката у источника и получателя с MAIN вне R; T11 отдельно проверяет
W в R при MAIN вне R. Это не равнозначно проверке пустых списков.
S4, стр.303: paramCode настраиваемый, поэтому T07 проверяет altAction против
actionType в обоих направлениях. T08 проверяет перестановку M=[3,1].
Точного запрета/разрешения пустых M/R и контракта ответа/запуска при отсутствующем,
null, пустом, многозначном параметре, неверном типе или неизвестной процедуре
не найдено. Это не основание выбирать HTTP 400/500 или любое фактическое поведение.
Особенно неизвестная процедура относится к конфигурации приложения и может
привести к отказу startup, а не к HTTP-ошибке загрузки экспериментов.
Эти восемь вариантов T25/T26 заблокированы до определения контракта.

Q4 — порядок, фильтрация, предрасчёт и traffic=false: закрыт частично

S4, стр.424: приоритизация MAIN → разметка альтернатив → подавление → результаты.
S4, стр.304: filterAlternative управляет подавлением по альтернативе независимо
от подавления по параметру MAIN. S4, стр.6433: рабочие значения фильтра [2,4],
enabled включает правило. T28 проверяет рабочий профиль и отключённый общий фильтр,
сохраняя точные флаги ALL. Независимая настройка filter-alternative не поддерживается
SDK 30b451ae94d и исключена из активного объёма EXPLAB-3056 по границам заявки. return-suppressed=true
оставлен как в подтверждённом профиле, чтобы не скрывать проверяемые объекты.
S4, стр.6432–6433: рабочие MAIN priorities, altControl=[5,6], M/R сохранены.

Для traffic-based-alternative=false единого контракта нет: стр.424 связывает
выполнение разметки с «Альтернатива в трафике=true», стр.6432 описывает FALSE
как альтернативу в трафике, TRUE как альтернативу в результате. Эти формулировки
нельзя незаметно считать эквивалентными. T28-TRAFFIC-OFF явно заблокирован.

T29 использует тот же splitter API и общий managed профиль с включённым
предрасчётом. Каждый из 19 основных вариантов повторяется по сохранённым связям;
runtime id=-3056 не удовлетворяет условиям, поэтому fallback на динамический
расчёт нарушит строгие ожидания. В v4 каждый вариант получает свежие ключи объектов;
проверяются copiedObjects=0 и objectsAdded=totalObjects=числу объектов. Обновление
таблицы предрасчёта не относится к вычислению альтернатив и отключено в этой заявке.
HTTP ожидает LOADED: LOADED_WITH_PRECALC является статусом мониторинга, это прежняя
ошибка автотеста. REST/Kafka здесь — способ загрузки конфигурации. Исправленные
19 вариантов прошли локально на SDK; в прогоне v4 от07–08.10.2026 T29:38/38passed. Точный исправленный commit сервиса нельзя
установить по единственной runtime-версии 0.12.3.
T30 отдельно запускается на REACTIONS с его собственным профилем и gate;
isAlternative запрещён даже со значением false/null. allowWithoutMain=false
позволяет проверить отсутствие MAIN/ALL у неподходящего объекта по принятому АК.

Наблюдаемость и оставшиеся ограничения

T15 проверяет три группы одного expId с точными положительными/отрицательными
ожиданиями; другой expId при том же code проверяется исходным T14/T15.
T16 проверяет внешний эффект двух источников одной пары, кратность строк/флагов
и повторяемость; приватный внутренний массив отката не доступен через API,
поэтому его структуру нельзя объявить непосредственно проверенной.
T20 дополнен прямой веткой → откатом → отсутствием кандидата на одной конфигурации.

В коде перечислены все 11 заблокированных вариантов ContractGap. Один отключённый
параметризованный метод unresolvedContract объясняет причину; JUnit может показать
его как один skipped template без раскрытия параметров. Это не 11 выполненных
проверок и не реализация неизвестных assertions. Перед включением нужны ожидаемый
результат и полноценное тело сценария; удаление @Disabled само по себе не допустимо.

Исправленный набор v4: 67 активных выполнений MAPPER и 2 REACTIONS
на режим загрузки; всего138 при запуске обоих режимов. При полном прохождении —
104 split MAPPER и2 REACTIONS на режим,212split суммарно. Отдельно по3disabledметода
на режим: один ContractGap и две смежные проверки вне объёма. Первые50passed
относятся только к прежнему набору v2, а разбор v3 сохранён отдельно.

Граница работы — функционал EXPLAB-3056, не общая
регрессия библиотеки. Основной предмет: исходные связи групп, отбор кандидатов,
разметка/откат, точные флаги и отсутствие их утечки. T29 проверяет этот же предмет
на заранее рассчитанных связях. Дефекты обновления таблицы, startup-совместимость
посторонних настроек и самостоятельная регрессия фильтров в активный объём
не добавляются. Существующие методы смежных проверок сохранены с явным Disabled.
Код SDK помогает диагностике, но не заменяет согласование 11 спорных вариантов.

T11 — уточнение тестовых данных после прогона v4, 08.10.2026
В «v1.0.0 MAPPER. Вычисление сработавших альтернатив / Описание / Алгоритм»
откат зависит от «результата группы итогового эксперимента объекта».
В «v1.1.0 MAPPER. Вычисление итогового эксперимента / Алгоритм», этап6,
итоговый эксперимент выбирается среди альтернатив по минимальному expId.
Старый T11 использовал один E1: связанная A=0, сработавшая B=5; MAIN тоже E1.
SDK SplittingMapperExecutor использует finalExp.getLeadGroup(), поэтому видит5.
Такое предусловие не изолирует заявленную проверку «параметр другого кандидата
входит в R, но MAIN вне R». В v5 у MAIN=E1 обе группы A/B имеют1 вне R, у другого
кандидата E2 сработавшая D=5 внутри R. При WORKING оба кандидата входят в M.
Ожидание прямой разметки обеих строк O1 сохранено, у получателей флаги false.
Проверка названного условия больше не зависит от трактовки группы MAIN.
Трактовка старого случая с разными значениями групп MAIN остаётся отдельным
неуточнённым вопросом; это не доказанный дефект продукта и не принятое уточнение АК.
