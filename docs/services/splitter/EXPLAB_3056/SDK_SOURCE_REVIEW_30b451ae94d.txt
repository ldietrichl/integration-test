1. Ошибка тестового профиля filter-alternative подтверждена

config/props/SplitterMapperSplitterRulesConfigProperties.java:115:
FilterProcParams содержит только paramCode, valueType, values.
config/SplitterAutoConfiguration.java:210: YAML читается Jackson с KEBAB_CASE;
неизвестные поля не разрешены. В штатном splitter-rules-mapper.yml поля нет.
service/executor/SplittingMapperExecutor.java:357: при filter-rule.enabled=true
альтернативы подавляются без отдельного переключателя; затем проверяется MAIN.
enabled=false отключает обе ветки фильтрации.

Наш WORKING добавляет неподдерживаемое поле true; FILTER_ALTERNATIVE_OFF добавляет
false. Оба значения несовместимы с моделью, хотя второй профиль на стенде не достигнут.
Это точно объясняет 2 readiness timeout и последующие 92 broken в прогоне v3.
Нельзя заменить filterAlternative=false на filter-rule.enabled=false: это другой
сценарий, отключающий также подавление по MAIN. Независимое отключение подавления
альтернатив этой реализацией не поддерживается; требуется решение по документации.
WORKING можно исправить удалением лишнего ключа без изменения M/R и assertions.

2. Старое actionType в T29 объясняется сохранёнными связями

service/SplitterPreliminaryLinkService.java:86–88: calculate() для существующего
uniqueConfigurationId переносит прежний SplitterPreliminaryObjectHolder в новую
таблицу и исключает этот объект из повторного построения связей. Смена только
soConfigVersion не означает пересчёт объекта.
Там же :176–194: refresh() сравнивает множества ID экспериментов. При тех же ID
изменения групп, параметров и условий не распознаются; публикации нового view нет.
service/dto/preliminary/SplitterPreliminaryCalcHolder.java:64: view использует
link.groups(), то есть группы сохранённой связи, а не заново найденные группы
актуального experimentConfig. Последующий calculate() с тем же ключом сохраняет
эти старые группы даже при новой splittingConfigVersion.

Локальное воспроизведение на настоящих классах из архива:
- исходный эксперимент id=1, B.actionType=1, объект key=same;
- refresh новой конфигурацией с тем же id, B.actionType=3: в view остаётся 1;
- calculate с новой soConfigVersion и key=same: copiedObjects=1, остаётся 1;
- calculate той же актуальной конфигурацией с key=fresh: получаем 3.
Это воспроизводит механизм наблюдаемого на стенде ответа 1 вместо загруженного 3.

В изолированных 19 вариантах T29 надо использовать новые ключи объектов между
вариантами, чтобы проверять альтернативы независимо от предыдущей конфигурации.
Внутри отдельного сценария обновления связей ключи, наоборот, должны оставаться
постоянными: иначе проверка дефекта актуализации будет потеряна. Ожидания актуальных
параметров не следует заменять на фактические старые значения ради прохождения.
34 падения T29 нельзя объявить 34 отдельными дефектами вычисления альтернатив.

3. Дополнительный дефект SDK: новые связи вычисляются, но теряются

service/SplitterPreliminaryLinkService.java:311–335, addStarted():
processPreliminaryLink() наполняет newConfigIdToObject, туда же объединяются старые
связи. Но return возвращает configIdToObject, прежнюю таблицу, а не новую.
refresh публикует полученный старый результат. Локальный пример с добавлением
эксперимента id=2 к существующему id=1 подтверждает отсутствие связи id=2 после
refresh, хотя условие эксперимента подходит объекту.
Это отдельное объяснение отсутствующих новых F/других экспериментов; новые связи
нельзя восстановить только сменой параметров assertions.

Дополнительное статическое наблюдение: lastSplittingConfigExpIds в refresh
обновляется только при пустом предыдущем множестве (:215), а не после каждого
успешного refresh. Многошаговые добавления/удаления требуют отдельной проверки;
этот пункт не включён в число локально воспроизведённых исходов.

Связь с вопросами аналитику

Исходники показывают фактическую реализацию, но не заменяют бизнес-контракт.
Например, traffic-based-alternative=false пропускает executeAlternativeRule (:293).
Прямая разметка идёт по объектам с MAIN (:310), тогда как получатель отката без
MAIN может быть помечен (:345). Эти различия помогают сформулировать уточнения,
но сами по себе не являются согласованием спорных требований. Отключённые случаи
автоматически не включались. Исторические результаты не переписывались.
