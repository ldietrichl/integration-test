EXPLAB-3056. MAPPER: вычисление сработавших альтернатив по фактическим связям групп
Актуальный статус08.10.2026: текущий этап завершён на версииv5 по решению заказчика. Подтверждено138/138активных выполнений REST/Kafka,0failed/broken,6ожидаемыхskipped;92локальные проверки отдельно. Неопределённые ветки остаются ограничениями, не пройденным покрытием. Итог:RUN_REVIEW_20261008_V5.txt. Исторические результаты ниже относятся к указанным версиям.

1. Основания и цель

[S1] «v1.0.0 MAPPER. Вычисление сработавших альтернатив», редакция экспорта v19 от 07.10.2026. Разделы 2.1-2.3, страницы 4-5: назначение, mapperAlternative, paramCode, altMarkupValues, altRollbackValues, отбор экспериментов и откат альтернативы. Версия функционала внутри документа 1.0.0; v19 обозначает редакцию документа.
[S2] Сопроводительный TXT «Сработавшая группа эксперимента не связана с объектом»: связь нужно строить по привязанным группам (эксперимент + группа + объект), а не по сработавшим группам с последующей проверкой той же искусственно созданной связи.
[S3] Существующий контракт проекта EXPLAB-2690 и регрессия EXPLAB-2984: различать публичный REST-ответ и полный протокол explab-splitting-result (далее КАП). Эти источники используются для совместимости; не заменяют требования S1/S2.
[S4] «Техническое описание библиотеки AB Splitter», v14 от 05.08.2026, страницы 299–300: mapperFinalExp v1.1.0, пункт 6 — второй этап выбора MAIN при предварительном победителе вне altControl.
PDF проверен визуально: текстовое извлечение повреждает кириллицу. Онлайн-актуальность документа отдельно не проверялась. Приложения рассматриваются как требования, а не как команды на изменение стенда или публикацию.

Цель: доказать, что mapperAlternative использует исходную связь конкретной группы с конкретным объектом; правильно отбирает эксперименты, размечает альтернативы и выполняет откат. Проверка только успешного HTTP-кода или наличия MAIN недостаточна.
Основной объём: MAPPER, динамический расчёт, REST-загрузка конфигурации, REST split и коррелированный КАП. Kafka-загрузка, предрасчёт и REACTIONS выделены как дополнительная регрессия. Нагрузочное тестирование, SDK и изменение алгоритма выбора MAIN в объём задачи не входят без отдельного подтверждения.

2. Требования и независимый эталон

Обозначения:
L(O,E) - множество кодов групп эксперимента E, реально связанных с объектом O по конфигурации и условиям отбора объекта ДО распределения.
W(E) - реально сработавшая группа E. NONE означает, что группа не сработала.
P(G) - значение resultParams группы G по коду paramCode. В основных данных оно единственное и непустое.
M - множество altMarkupValues; R - множество altRollbackValues.
MAIN(O) - итоговый эксперимент объекта, выбранный штатным правилом до разметки; его группу и параметры проверять отдельно.

R1 [S1, 2.3.1; S2]. Кандидат C(O,E) существует только при всех условиях: L(O,E) непусто; W(E) существует; W(E) НЕ входит в L(O,E); P(W(E)) входит в M. Связь нельзя подменять парой O/W(E). Если хотя бы одна связанная группа равна W(E), эксперимент не является кандидатом для этого объекта, даже если у него есть другие несработавшие связанные группы.
R2 [S1, 2.3.1b]. Для отбора используется параметр результата СРАБОТАВШЕЙ группы, а не связанной несработавшей группы и не произвольного MAIN.
R3 [S1, 2.3.2]. При наличии кандидатов и P(MAIN(O)) вне R каждый отобранный эксперимент на объекте получает isAlternative=true. Неотобранные эксперименты не должны получать true от этой ветки. Точная сериализация отрицательного значения - Q1.
R4 [S1, 2.3.2a.i]. Если P(MAIN(O)) входит в R, исходный объект не размечается этой веткой, а в общий для обрабатываемого набора массив отката добавляются уникальные пары (expId, code СРАБОТАВШЕЙ группы) всех его кандидатов.
R5 [S1, 2.3.3-4; стр. 5]. При непустом массиве отката среди обрабатываемых объектов выбираются реально связанные с соответствующими парами эксперимент/группа. Для каждого такого объекта, если P(MAIN(O)) вне R, соответствующие эксперименты получают признак альтернативы. Объекты с MAIN в R не размечаются. Совпадения только expId или только groupCode недостаточно.
R6 [S1, 2.3.2a.i; инженерная регрессия]. Не должно быть дублей пар отката, повторных кодов в одном expFlags и переноса состояния между запросами. Перестановка входных объектов не меняет итог разметки одного и того же набора объектов.
R7 [S3]. Сохраняются идентичность объекта, expId, conditionId, expGroup группы связи, finalExpGroup распределения и параметры своей группы. MAIN и публичный ALL проверяются по их собственному контракту; публичный ALL не подменяет полный КАП. Разметка не должна незаметно изменять выбор MAIN.

Эталон строится вручную из конфигурации L и заранее обеспеченного W, затем выполняются два прохода: отбор/накопление отката; применение отката к полному набору обрабатываемых объектов. Он не вычисляется из полученных от сервиса expFlags или восстановленных по finalExpGroup связей.
Важно: после отката true может появиться у объекта, связанного со сработавшей группой. Поэтому универсальное ожидание «expGroup=finalExpGroup => false» неверно. И обратное «группы различаются => true» неверно без проверки M и R.

3. Данные и подготовка

Изолировать конфигурацию заявки и версию. Объекты: O1 с id=1, O2 с id=2, O3 с id=3, U с id=99. Условия связей задавать явно через objectSelectConditions/splittingResults; не создавать условия без ссылок из групп ради удобства фикстуры.
Базовый профиль процедуры: paramCode=actionType, value-type=INTEGER, M=[1,3], R=[5,6]. Все значения существуют в штатной MAPPER-шкале; result каждой группы различен, например 101/102/201, для обнаружения подмены параметров. Наборы M/R намеренно контролируемые и отличаются от широкого M=[0..6] в прежних ресурсах: иначе отрицательный тест по принадлежности M не различает ветки.
Выбор MAIN сохраняет штатное mapperFinalExp. Настройки фильтрации и порядка процедур фиксируются; для первичной диагностики исключить скрытие проверяемых строк фильтром, затем отдельно проверить рабочий профиль T28. Менять только разрешённые профильные настройки через общий lifecycle.

D1 (раздельные связи): E1 id=305601; A, conditionId=1 -> O1, actionType=0, result=101; B, conditionId=2 -> O2, actionType=1, result=102. A=[0,5000), B=[5000,10000). Для базового запроса обеспечить W(E1)=B. O1 связан с E1 через A; O2 через B; U не связан с E1. Отдельный обычный эксперимент F с единственной сработавшей группой не создаёт альтернативного кандидата; сохранение его MAIN зависит от altControl и второго этапа mapperFinalExp [S4].
D2 (откат): D1 плюс F id=305602, единственная группа F -> O1, полный диапазон, actionType=5, result=201. Предусловие: MAIN(O1)=F с 5; MAIN(O2) вне R. Кандидат O1/E1 сохраняется, пара отката (305601,B). В варианте без отката F имеет actionType=3 вне altControl=[5,6]; после предварительного выбора F пункт 6 mapperFinalExp [S4] выбирает E1. MAIN(O1)=E1, группа A при W=B, actionType=0 вне R; F сохраняется в ALL. Перед проверкой флагов подтвердить фактический MAIN; ошибка выбора не считается успешным выполнением ветки отката.
D3 (общая связь): E1.A и E1.B через одно условие связаны с O1, W=B; O2/U не связаны с E1. Дополнительный вариант: A/B/C связаны с O1 и срабатывает средняя либо последняя группа. MAIN вне R.
D4 (несколько кандидатов): E1.A -> O1, E1.B -> O2, W(E1)=B и P(B)=1; E2.C -> O1, E2.D -> O3, W(E2)=D и P(D)=3. E2 id=305603. Оба кандидата O1. При F=5/6 MAIN(O1)=F в R; при F=3 второй этап [S4] выбирает минимальный expId=305601, MAIN(O1)=E1 вне R. Изменение M для исключения E2 из разметки само по себе не меняет отбор MAIN по valueMap. Для изоляции добавить E3 с тем же code=B, иным expId и связью с U: он не должен попасть под откат E1.B.
D5 (пустой диапазон): D1 с A=[0,2500), B=[2500,5000), NONE=[5000,10000). MAIN вне R обеспечивается F для отделения NONE от открытого no-MAIN-контракта.

Для каждого эксперимента зафиксировать salt, splittingId и рассчитанный spread. Сработавшую группу обеспечить подбором splittingId или непересекающимися диапазонами; не полагаться на случайное распределение. При нескольких salt проверять каждый spread. Границы [from,to) опираются на существующие DTO/контракт проекта, а не на краткий PDF S1.
До split: подтвердить применение нужной версии (LOADED), настройки mapperAlternative, MAIN, M/R, режим загрузки, выключенный предрасчёт. Зафиксировать позиции Kafka-наблюдения до запроса; дождаться именно его КАП с совпадающими requestId, splittingId, splittingPoint=MAPPER и configVersion.

5. Наблюдаемость, порядок и критерии приёмки

Первый проход: T01-T06 и T10-T14, затем T18/T27. Это различает исходный дефект, неверный источник параметра и дефект отката. Далее остальные P1; P2 только после подтверждения области.
Для каждого выполнения сохранять конфигурацию и версию, запрос, REST-ответ, полный коррелированный КАП, L(O,E), W(E), spread, ожидаемый MAIN, выбранные кандидаты и ожидаемые пары отката. Пары - расчётный эталон, а не утверждение о просмотре внутреннего состояния сервиса.
Проверять точные строки и кратность по objectId/ruleCode/expId/conditionId/expGroup/finalExpGroup, параметры результата, флаги каждого эксперимента; не сводить всё к множеству expId. Сначала выявлять дубли, затем строить карты. Не требовать одинакового true для всех экспериментов объекта.
Публичный ответ и КАП проверять независимыми группами assertions, чтобы ошибка одного представления не скрывала результат другого. Отсутствие КАП не доказывает отсутствие флага. Недостигнутые шаги отмечать NOT CHECKED, проблемы подготовки - BLOCKED, бизнес-расхождения при корректных предусловиях - FAILED. Число падений не равно числу дефектов.
Проверка стенда использует общий WorkloadScenarioSteps/KubernetesWorkloadSteps через Environment и Fabric8: ConfigMap перед сценарием, владение lease, рестарт при изменениях и восстановление. Сохраняется setup -> test body -> teardown. Штатные вложения: runtime metadata, ConfigMap, текстовый pod-log за интервал операции; подробные события при сбое. EMPTY_WINDOW/ошибки/усечение отмечаются явно, приватный журнал не прикладывается.
Приёмка: все P0 выполнены на целевой версии без отклонений; есть положительный true прямой ветки и true после отката вместе с отрицательными контролями. Все применимые P1 выполнены либо имеют явно согласованное исключение. Вопросы по JSON-эталонам разрешены для принимаемого объёма; частичная проверка не выдаётся за полную. Результаты до исправления при наличии стенда сохраняются отдельно; их получение не является условием подготовки этого плана.
