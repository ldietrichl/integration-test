# EXPLAB-3056: разметка и откат альтернатив MAPPER

Зафиксированный набор v5 содержит 67 активных выполнений MAPPER и 2 REACTIONS
на режим загрузки: всего 138 при запуске REST и Kafka, до 212 split.
В каждом режиме отдельно учитываются три отключённых метода: шаблон 11 вопросов
к контракту и две смежные проверки вне объёма заявки. Параметры отключённых
шаблонов не раскрываются JUnit как отдельные выполненные случаи; ожидаются
6 skipped на оба режима, они не засчитываются покрытием.
Решения по документации и границы: `DOCUMENTATION_DECISIONS.txt`.

На стенде подтверждён прежний набор v2: REST25/25 + Kafka25/25.
Прогон v3 дал 18 passed / 36 failed / 92 broken / 2 skipped; причины разобраны.
Прогон v4 от 07–08.10.2026: 136 passed / 2 failed / 6 skipped, 0 broken.

Набор проверяет исходные связи групп с объектами, отбор по параметру сработавшей
группы и откат по параметру MAIN. Положительные и отрицательные флаги проверяются
для каждой строки полного КАП; публичный ALL проверяется отдельно. После отката
`isAlternative=true` допустим у строки со сработавшей связанной группой.

## Профиль и контракт ожиданий

Собственный ресурс `splitter/EXPLAB_3056/configmap/mapper-required.yml` задаёт
`mapperAlternative`, `paramCode=actionType`, M=[1,3], R=[5,6]. Правило MAIN и
фильтрация сохраняют настройки действующего MAPPER-профиля. Метод выбирает
декларативный ScenarioProfile: дополнительный paramCode, порядок/состав M/R,
filter.enabled или PRECALC. В рабочих вариантах используются
и actionType=2/4. Для MAPPER `allow-result-without-main=true`, выдача ALL,
пустых и подавленных объектов включена. Все связанные объекты основных сценариев
имеют явно ожидаемый MAIN; несвязанные объекты используются как отрицательный контроль.
Для REACTIONS применяется отдельный профиль 2984 и allow=false. PRECALC включает
предрасчёт явным managed override; остальные варианты выключают его.

Применяется существующий JSON-контракт MAPPER: каждая строка ALL содержит один
`expFlags` с `code=isAlternative`, строковым `value="true"` или `value="false"`;
в MAIN флагов нет. Проверки не приводят Boolean/null к строке, не допускают
пропущенный флаг или дубли. Строковый контракт подтверждён таблицами AB Splitter
v14 стр.95/284; Q1 закрыт для реализованной матрицы. T23 проверяет несколько
несработавших групп одного эксперимента на объекте. Решения и оставшиеся
противоречия Q2–Q4 перечислены в DOCUMENTATION_DECISIONS.txt.

Выбор MAIN учитывает оба этапа mapperFinalExp v1.1.0. В пункте 6 предварительный
победитель с параметром вне `altControl=[5,6]` заменяется альтернативным
экспериментом с минимальным expId. Поэтому в T12-NO-ROLLBACK и T09-ALL/ONE
при F.actionType=3 итоговый MAIN объекта O1 — E1 (A/B), а F остаётся в ALL.
При F.actionType=5/6 MAIN сохраняется за F. Это правило выбора MAIN независимо
от отбора кандидатов mapperAlternative по M; профиль процедуры не изменён.

Уточнения АК от 07.10.2026 из 2690/2984 уже приняты: при allow=true связанный
объект без победителя имеет технический MAIN=[]; при false у него нет MAIN/ALL
как в REST, так и в КАП. Сам объект сохраняется. Это закрывает прежний спор о
контейнере, но не задаёт поведение mapperAlternative без MAIN и полный ALL при
NONE+allow=true. Такие ветки новым набором не проверяются.

## Запуск

В стандартном проекте с настроенными доступами:

```powershell
.\gradlew.bat explab3056LocalChecks
.\gradlew.bat explab3056MapperRest
# Дополнительный режим: конфигурация через Kafka, split по-прежнему REST.
.\gradlew.bat explab3056MapperKafka
.\gradlew.bat explab3056ReactionsRest
.\gradlew.bat explab3056ReactionsKafka
```

`explab3056Coverage` запускает MAPPER и REACTIONS в REST-режиме. Задачи зарегистрированы в
`gradle/tickets/EXPLAB_3056.gradle` и подключены каталогом задач. Требуются текущие
настройки MAPPER/gateway, `splitter.kap.kafka.env`, `splitter.kap.topic`, а для
Kafka-загрузки — штатные настройки загрузчика из существующей регрессии.

Имена workload берутся тем же способом, что в 2984: действующие настройки
`exlab2891.mapper.*` с общими/legacy defaults, затем явные настройки `explab3056.*`
и `stand.<env>.workloads.*`. Ресурс правил у заявки собственный. Задача не выдаёт
разрешений на изменение Kubernetes: они остаются в штатных настройках стенда.
Отключение управляемого профиля для динамического набора вызывает ошибку подготовки.

MAPPER зависит от read-only `explab2891StandCheck`, REACTIONS — от `explab2885StandCheck`; задачи
используют штатную приватную JVM-диагностику. Для нестандартной топологии параметры
preflight `workload.mapper.*` должны указывать на те же ресурсы, что профиль.
Чужой lease не снимается автоматически. Восстановление остаётся в общем lifecycle.

Функциональный raw: `build/allure-results`, отдельный JUnit —
`build/test-results/explab3056MapperRest` или `explab3056MapperKafka`.
Локальные проверки: `build/local-checks/explab3056`, отдельный sourceSet;
в обычную test/TestOps-выборку они не включаются. Используются существующие
подготовка результатов и TestOps-задачи, без отдельного отправителя.

предрасчёта при прежних uniqueConfigurationId. На реальных классах локально

## Исправления v4 и объём заявки

В WORKING больше не добавляется неподдерживаемое поле `filter-alternative`.
Семь активных профилей прочитаны реальной моделью настроек SDK 30b451ae94d.
Независимое отключение подавления альтернатив и обновление таблицы предрасчёта
исключены из активного набора как смежный функционал. Методы
`alternativeFilterIsIndependentOfParameterFilter` и `precalculatedLinksFollowVersion`
сохранены с `@Disabled` и причиной для истории результатов. Они не являются
пройденными проверками и не заменены ослабленными assertions.
Динамический T21 сохраняется: проверяет смену флагов при изменении связей заявки.

T29 использует существующие фабрики запросов: каждый вариант получает свежие
uniqueConfigurationId, одинаковые в pre-calculate и последующем split. Проверяются
copiedObjects=0 и objectsAdded=totalObjects=числу объектов. Runtime id=-3056
по-прежнему выявляет подмену сохранённых связей динамическим расчётом.
HTTP загрузки проверяется на LOADED; результат мониторинга LOADED_WITH_PRECALC
не подставляется в HTTP-контракт. Исследование обновления кэша не входит в T29.

Локально прошли 91 проверка 3056, 83 общих и 6 сохранённых пар REST/КАП.
Отдельно все 19 T29 выполнены на настоящих классах SDK с production DTO-фабрикой
и прежними строгими проверками MAIN/полного ALL/параметров/isAlternative.
Отправка мониторинга заменена заглушкой; HTTP/Kafka/публичное преобразование
ответа в этой дополнительной проверке не запускались. Это локальная проверка
исправления изоляции данных, а не стендовый результат и не вложение TestOps.
Новые классы не добавлены; общие Fabric8 lifecycle, Gradle и uploader не менялись.

## Исправление T11 (v5)

В прежних данных кандидат со сработавшим actionType=5 одновременно был MAIN.
У связанной группы было 0, у сработавшей — 5: условие «MAIN вне R» зависело
от трактовки группы и не отделяло итоговый эксперимент от другого кандидата.
Теперь MAIN=E1: связанная A и сработавшая B имеют actionType=1; отдельный
кандидат E2 имеет сработавшую D=5. При M=[0,1,2,3,4,5,6], R=[5,6] строки
E1/A и E2/C объекта O1 должны получить isAlternative=true; получатели O2/O3 — false.
MAIN=E1 фиксируется минимальным expId на этапе 6 mapperFinalExp.
ID, метод, число выполнений и строгие assertions сохранены. Новых классов нет:
переиспользованы MapperAlternativeMarkupCases, DTO-фабрика и существующие проверки.
Вопрос о различии параметров связанной/сработавшей группы одного MAIN этим
исправлением не разрешается; фактический ответ старого T11 не принят как контракт.
