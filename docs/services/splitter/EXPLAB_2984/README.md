# EXPLAB-2984: кандидаты MAIN и флаги альтернативы

Реализованы динамические сценарии REACTIONS и регрессия MAPPER по [тестовому плану](TEST_PLAN_JIRA.txt). Один режим загрузки содержит **39 выполнений JUnit**: 30 REACTIONS с `allow-result-without-main=true`, 3 REACTIONS с `false`, 6 MAPPER. Некоторые выполнения включают последовательность запросов; число запросов не равно числу тестов.

Каждый split выполняется через REST и проверяется вместе с полным событием `explab-splitting-result`. Режим `Kafka` в имени задачи относится к **загрузке конфигурации**, не к маршруту split.

## Что проверяется

- Неподходящий эксперимент исключается из выбора MAIN до сравнения приоритета/ID; решение принимается отдельно для каждого объекта.
- При allow-result-without-main=true полный ALL сохраняет связанные несработавшие группы. При false для объекта без MAIN ALL подавляется и в REST, и в КАП (уточнение 07.10.2026); для объекта с MAIN полный ALL сохраняется. Публичный ALL содержит сработавшие связанные группы; для MAPPER альтернативная строка остаётся вне публичного ALL.
- В REACTIONS запрещён сам `code=isAlternative`, в том числе со значением `false` или `null`. В MAIN обеих точек запрещены элементы `expFlags`.
- Сравниваются точные строки с кратностью: `expId`, `conditionId`, `expGroup`, `finalExpGroup`; дополнительно проверяются salt, spreadValue, слои и полный набор параметров группы.
- Повторяющиеся коды флагов не скрываются преобразованием массива в Map. Порядок объектов, экспериментов и групп не влияет на ожидаемый результат.
- Перестановки, повторные запросы, A → B → NONE → A без перезагрузки и изменение связей новой версией конфигурации проверяются отдельными сценариями.

REST и КАП проверяются независимыми ветвями `assertAll`. Ошибка REST-контракта не отменяет ожидание КАП. Ошибка загрузки/HTTP-запроса остаётся ошибкой предусловия/операции и не выдаётся за выполненную проверку результата.

## Запуск

Задачи подключаются через `gradle/architecture/task-catalog.gradle`, отображаются в группе `tickets`. Используются существующие настройки окружения, Kubernetes и Kafka. Разрешения на изменение стенда задаются обычными `stand.<env>.*`; задача их не включает и чужой lease не снимает.

```powershell
# Только локальные проверки, без подключения к стенду
.\gradlew.bat explab2984LocalChecks

# Основной набор: REACTIONS + MAPPER, REST-загрузка, 39 выполнений
.\gradlew.bat explab2984Coverage

# Отдельные точки
.\gradlew.bat explab2984ReactionsRest
.\gradlew.bat explab2984MapperRest

# Дополнительный режим загрузки тех же сценариев
.\gradlew.bat explab2984ReactionsKafka explab2984MapperKafka
```

REST-задачи задают `SPLITTER_API_CONFIG_LOAD=true`, Kafka-задачи — `false`. Оба режима используют `SPLITTER_PRELIMINARY_CALCULATION_ENABLED=false`, `SPLITTER_ALL_RULE_CODE_EXP_ENABLED=true`, `SPLITTER_EMPTY_OBJECTS_RESPONSE_ENABLED=true`, `SPLITTER_RETURN_SUPPRESSED=true`. Значение `SPLITTER_ALLOW_RESULT_WITHOUT_MAIN` зависит от класса сценариев.

`WorkedGroupProfile` применяет собственные правила из ресурсов `splitter/EXPLAB_2984/configmap/mapper-required.yml` и `reactions-required.yml`: MAPPER mapperFinalExp/альтернатива/фильтрация; REACTIONS finalExpByLayerAndId с максимальным приоритетом и минимальным ID. Связи и значения result из примеров сохранены; ID экспериментов изолированы в диапазоне 298401–298403, objectId и uniqueConfigurationId различаются.

Профиль проверяет ConfigMap перед каждым сценарием. Изменение состояния и перезапуск выполняются общими шагами только при необходимости; по завершении восстанавливается исходное состояние. Загрузка очередной конфигурации экспериментов сама по себе не требует перезапуска pod. При отсутствующем/неуправляемом ключе окружения подготовка завершается ошибкой, не создавая произвольный ключ в чужой ConfigMap.

Переопределения профиля: `explab2984.*` для MAPPER, `explab2984.reactions.*` для REACTIONS; имена suffix совпадают с `WorkedGroupProfile` (`stand.workload`, `stand.service`, `configmap.rules.name`, `configmap.rules.key`, `application-env.<имя-флага>`). Задачи включают `explab2984.stand.config.enabled` и `explab2984.stand.application-flags.enabled`; отключение управления для этих сценариев не поддерживается, поскольку необходимо доказать выключенный предрасчёт.

Перед функциональным Test выполняется общий read-only lease gate: `explab2885StandCheck` для REACTIONS либо `explab2891StandCheck` для MAPPER. При нестандартных именах согласованно задаются параметры gate `-Pworkload.reactions.deployment`, `-Pworkload.reactions.configmaps` (аналогично mapper) и настройки целевого workload в `stand.properties`. Gate не заменяет проверку lease непосредственно при подготовке сценария.

Отдельные настройки Deployment/ConfigMap для заявки не требуются. `WorkedGroupProfile` использует имена из существующих `ReactionsPrecalcProfile`/`MapperPrecalcProfile` и общий `StandSettings.installMissing`. Как и bindings 2885/2891, он задаёт только отсутствующие имена и readiness, сохраняя их до восстановления в конце JVM. Стандартные defaults DEV:

```properties
stand.dev.workloads.splitter-reactions.deployment=splitter-reactions-service
stand.dev.workloads.splitter-reactions.configmap=splitter-reactions-service-lib
stand.dev.workloads.splitter-mapper.deployment=splitter-mapper-service
stand.dev.workloads.splitter-mapper.configmap=splitter-mapper-service-lib
```

Явные `stand.<env>.workloads.*` из штатных источников сохраняются, включая пустые значения: ошибочную явную настройку нельзя скрыть fallback. Существующие параметры `explab2885.reactions.*`, `exlab2891.mapper.*` с совместимостью `explab2690.*` используются для имён ресурсов, порта и контейнера; переопределения `explab2984.*` необязательны. Значения бизнес-флагов и содержимое YAML других заявок не применяются. `stand.properties` и защищённые настройки поставкой не заменяются.

Среда выбирается из `env` в `test.properties` общим `TestEnvironment`; `-Denv`/`-Pfile.env` не переключают стенд. Gradle передаёт `stand.*` и параметры существующих профилей; при одновременных `-P` и `-D` для одного ключа выигрывает `-D`. Общий read-only gate также получает `stand.*` из обоих источников. Для нестандартных имён gate сохраняет параметры `workload.reactions.*`/`workload.mapper.*`; проверка и получение lease в самой тестовой сессии обязательны независимо от предварительного gate.

Первый прогон 06.10.2026 выявил отсутствие установки defaults в профиле 2984: 33 сценария остановились в setup. Это дефект подключения профиля, а не требование вручную дублировать настройки для новой заявки. После обновления требуется новый запуск Gradle-задачи. Подробности аудита — `SETTINGS_AUDIT_20261006.md`.

Маршрут КАП берётся из `regression-profiles.properties`: `<env>.splitter.kap.kafka.env`, `<env>.splitter.kap.topic`; ожидание ограничено `splitter.kap.timeout.seconds` (1–300, по умолчанию 30). Используется consumer существующего KafkaService. До split выполняется назначение partitions и фиксация конечных offsets; старые события не принимаются. Корреляция точная по requestId конверта и message, splittingPoint и версии; splittingId дополнительно проверяется в теле события. Буферы очищаются после каждого poll, размеры разбора и диагностических примеров ограничены общим BoundedKafkaObservation. Consumer закрывает сервис-владелец, а наблюдение снимает назначение при завершении.

## Отчётность

Функциональные задачи пишут в общий `build/allure-results`; JUnit/HTML раздельны в `build/test-results/<task>` и `build/reports/tests/<task>`. Самопроверки из `src/workloadChecks` пишут только в `build/local-checks/explab2984` и не входят в функциональный набор.

Используются штатные runtime metadata, ConfigMap и текстовый pod-log за интервал операции; подробные события при сбое. EMPTY_WINDOW, недоступные и усечённые логи не считаются полными. JVM-диагностика остаётся в приватном `.workload-recovery`, вне TestOps.

Между задачами одной серии `clean` не выполнять. Повторные запуски накапливают raw Allure; JUnit задачи отражает последнее выполнение. Для подготовки используется общая `prepareTestOpsResults`; отдельного uploader для заявки нет. Запуск подготовки и отправка не являются частью выполнения тестов.

План не считается полностью закрытым. Неоднозначные части Q2/Q3 явно отражаются параметрами Allure:

- Для no-MAIN проверяется отсутствие выбранного эксперимента и ожидаемый состав публичного ALL, но не выбор между отсутствующим MAIN и `MAIN.resultExps=[]`. Это отдельный новый семантический контракт; старые assertions 2690 не ослаблены.
- В NONE проверяются отсутствие победителя, пустой публичный ALL, флаги и метаданные имеющихся строк КАП. Точный состав полного ALL при NONE и allow=true остаётся открытым; при allow=false ALL обязан быть пустым.
- В MAPPER проверены альтернативный MAIN, его параметры, отсутствие флагов MAIN и дубли кодов. Таблица значений/обязательности `isAlternative` в полном ALL до Q3 не утверждается. Удаление всех этих флагов из MAPPER не будет полностью покрыто текущим набором; этот пункт приёмки остаётся открытым.
- Набор проверяет отсутствие `isAlternative` и в публичном REACTIONS-ответе согласно R4 плана; подтверждение распространения требования на этот интерфейс отмечено в Q4.

## Реализация и проверки

Переиспользованы AbstractSplitterV9FlowTest, DTO, транспорт SplitterRestSteps, общий профиль WorkedGroupProfile, WorkedGroupAssertions и Fabric8 lifecycle. В тестах остались сценарии и настройки; параметры вынесены в `support/splitter/cases/CandidateSelectionCases`.

Новые компоненты имеют отдельные обязанности:

- `WorkedGroupRequests` создаёт DTO конфигураций/запросов для динамического выбора. Фабрики предрасчёта 2885/2891 имеют другую модель и не расширялись несвязанными данными.
- `CandidateSelectionSteps` выполняет сценарий и независимые проверки REST/КАП. Наследование от WorkedGroupSteps принесло бы жёстко заданный профиль 2690 и спорный старый no-MAIN oracle, поэтому переиспользована его транспортная база и общий профиль.
- `SplitterKafkaReportClient` наблюдает полный результат через существующий KafkaService и BoundedKafkaObservation. Старый helper AbstractSplitterV9FlowTest подписывается после split и накапливает сообщения; он сохранён для прежних потребителей, новый сценарий его не вызывает. Клиент загрузки конфигурации не смешивается с наблюдением результатов.

Изменённый профиль сохраняет прежнюю сигнатуру `prepare(boolean, boolean)` и прежние пять флагов для 2690. Новая перегрузка добавляет пространство настроек, режим загрузки и явное выключение предрасчёта. Самопроверки проверяют совместимость прежнего набора флагов, запрет неуправляемого запуска, корреляцию КАП и ошибки бизнес-ответа.

Проверено локально 06.10.2026: изменённые Java-компоненты, новые функциональные классы и существующие классы 2690 скомпилированы на доступном корпоративном classpath (Java 17). Выполнены 50 самопроверок без падений: 31 новая, 7 прежних no-MAIN, 5 общего lifecycle и 7 ограниченного Kafka-наблюдения. Настоящая `explab2984LocalChecks` отдельно выполнила те же 31 новую проверку; это не ещё 31 уникальный сценарий.

Настоящие изменённые Gradle-скрипты задачи и reliability применены в изолированной сборке: проверены четыре режима/фильтра, зависимости от нужного lease gate, состав агрегата, единый функциональный Allure и изоляция самопроверок. Проверка не запускала функциональные Test-задачи и стендовые JavaExec.

Полная корпоративная сборка с Nexus, стендовый прогон, установка и отправка в TestOps не выполнялись. Подготовлен корпоративный replacement-патч splitter-explab2984-20261006-v4; получение архива не подтверждает установку.

## Уточнение КАП при allow-result-without-main=false, 07.10.2026

Параметр действует одновременно на публичный ответ и КАП. Для объекта без MAIN тесты требуют отсутствие строк MAIN/ALL; объект сохраняется. Для объекта с MAIN проверяется прежний полный набор ALL. В T20 обновлено только ожидаемое представление КАП, не отключена проверка ALL. Добавлены проверки запрета лишних строк и неизменности allow=true, включая NONE при false.

Дополнение splitter-explab2984-q2-20261007-v1 ставится поверх EXPLAB-2984 v4 и не заменяет общие assertions из последующей поставки no-MAIN. Исторические результаты не пересчитываются; локальная проверка сохранённых ответов не является новым стендовым прогоном.
