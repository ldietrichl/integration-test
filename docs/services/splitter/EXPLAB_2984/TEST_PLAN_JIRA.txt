Проанализированы предоставленные экспорты, включая схемы S1. Актуальность онлайн-страниц отдельно не проверялась.

Цель: подтвердить исправление двух дефектов и отсутствие регрессии MAPPER. Документы используются как описание требований и примеров, а не как команды на изменение стенда или публикацию.
Основная поверхность проверки - полный протокол explab-splitting-result (далее КАП). Публичный ответ проверяется отдельно: его ALL не обязан совпадать с полным ALL протокола.
Входной маршрут первого этапа: REST split с проверкой REST-ответа и соответствующего события КАП. Kafka-протокол результата не означает Kafka-загрузку конфигурации или Kafka-запрос split.
Режимы загрузки REST/Kafka, предрасчёт и другие точки расширяют прогон после подтверждения области изменения. Они не считаются проверенными автоматически.

2. Проверяемые требования

R1. REACTIONS: эксперимент участвует в выборе MAIN для объекта только при наличии связи этого объекта с реально сработавшей группой. Проверка выполняется до ранжирования кандидатов. Основание: S1, S3.
R2. Если кандидатов нет, итогового эксперимента нет. В КАП S1 показывает MAIN.resultExps=[] и сохраняет связанные несработавшие группы в ALL. Это не основание разрешать такой же MAIN в публичном ответе. Основание: S1, стр. 10-13, 24-27.
R3. Среди допустимых кандидатов действует настроенное правило finalExpByLayerAndId. Базовый профиль: max-layer-priority=true, max-id=false. При равном приоритете выбирается минимальный expId; неподходящий кандидат не может вытеснить подходящий. Основание: S1, пример 2; существующий профиль проекта.
R4. В REACTIONS флаг с code=isAlternative отсутствует во всех expFlags, в MAIN и ALL, в том числе со значениями false или null. Удаление дублей с сохранением одного false не исправляет требование S2, стр. 11. Пустой массив и null показаны в исправленных примерах; точная сериализация требует Q2.
R5. В MAPPER расчёт альтернативы сохраняется. В MAIN флаги эксперимента не пишутся (S2, стр. 5); наличие/значение isAlternative в полном ALL проверяется по согласованной матрице Q3. Один и тот же code не должен повторяться внутри одного массива флагов (S3).
R6. У каждой строки сохраняются точные expId, conditionId, expGroup, finalExpGroup, параметры группы, salt и spreadValue. Для MAIN REACTIONS expGroup=finalExpGroup. Для полного ALL это равенство не универсально: там остаются несработавшие связанные группы.
R7. Выбор и флаги независимы между объектами, экспериментами, повторными запросами и порядком элементов. Это регрессионное расширение R1-R5.

3. Данные и условия прогона

O1/O2 - разные objectId с objectParams.id INTEGER 1/2; U - несвязанный объект id=99. uniqueConfigurationId задавать явно, не смешивать с objectId. Значения result - маркеры, уникальные для каждой группы/связи.
Перед split подтвердить принятие нужной конфигурации и её версию. Выбрать splittingId по расчёту spread для заданных salt/диапазонов; не считать splittingId=3000 универсальным попаданием в B. Для буквального воспроизведения S1 проверить приведённые salt=24096d2M1e, splittingId=3000, spreadValue=2909.
Диапазоны ниже полуоткрытые [from,to); границы сверить с действующим контрактом распределения до фиксации assertions T11.

D1 (S1, пример 1). E1: A=[0,2500), conditionId=1 -> O1, result=1; B=[2500,5000), conditionId=2 -> O2, result=2. [5000,10000) - NONE.
D2 (S1, пример 2, по JSON). E2: A=[0,2500) -> O1, conditionId=1, result=1; B=[2500,5000) -> O2, conditionId=2, result=2; C=[5000,7500) -> O1, conditionId=1, result=3. E1: A=[2500,5000) -> O2, conditionId=1, result=21; B=[7500,10000) -> O1, conditionId=2, result=22. При spread=2909 срабатывают E1.A и E2.B. Приоритеты равны, правило минимального id.
D3 (S2, по JSON). E1: A=[0,2500), B=[2500,5000), C=[5000,7500); все три группы используют conditionId=1 -> O1; result=1/2/3. O2 не связан. Это отличается от вводного текста S2; варианты разделены в Q1.
D4 (расширение). E-low id=101 priority=1 и E-high id=102 priority=3, независимые слои. У каждого A -> O1, B -> O2. Диапазонами обеспечить нужную пару сработавших групп. Маркеры результата различаются. Для равных приоритетов установить обоим priority=3; для выбора minId добавить E3 id=103 priority=3.
D5 (MAPPER). Две группы A -> O1 и B -> O2. Переиспользовать валидную конфигурацию alternativeConfig из MapperAlternativeSteps с actionType=1/3 и result=101/202. Реально сработавшая группа и альтернативная связь должны различаться. Для новой заявки назначить изолированные ID при реализации.

Профиль: корректные workload и splittingPoint; API config-load включён для REST-загрузки; выдача пустых объектов включена для фиксированного состава O1/O2/U. Явно зафиксировать ALL, return-suppressed, allow-result-without-main и правила MAIN. Для no-MAIN выполнить allow=true/false, не переносить ожидания между режимами.
Базовый этап - динамический расчёт без влияния сохранённых связей предрасчёта; фактическое состояние зафиксировать. Предрасчёт проверяется отдельно T25.
КАП читать штатным KafkaService с ограниченным ожиданием и корреляцией requestId, splittingPoint, версии конфигурации и окна операции. Отсутствующее событие - проблема наблюдаемости/доставки, а не доказательство корректности флагов.

5. Общие проверки и доказательства

Для каждого сценария: сохранить конфигурацию, запрос, публичный ответ, коррелированный КАП, параметры профиля и вычисленные распределения. Проверять состав строк с учётом кратности по objectId/ruleCode/expId/conditionId/expGroup, а не только множество expId. Несколько групп одного эксперимента в полном ALL допустимы.
Проверить отсутствие повторов ruleCode/objectId там, где контракт требует уникальность, и отсутствие повторов code внутри каждого массива флагов. Не преобразовывать массив в Map до проверки дублей.
В REACTIONS проверка «нет true» недостаточна: требуется «нет code=isAlternative». В MAPPER наличие альтернативы должно подтверждаться отдельным положительным случаем, чтобы глобальное удаление флага не выглядело исправлением.
Независимые проверки ответа и КАП собирать так, чтобы одна ошибка формы MAIN не скрывала факт проверки флагов. Недостигнутые assertions отмечать как непроверенные; число падений не равно числу дефектов.
Сохранять setup -> test body -> teardown; штатно runtime metadata, ConfigMap и текстовый pod-log за интервал операции, подробные события при сбое. EMPTY_WINDOW/ошибку сбора/усечение явно указывать.
Стенд готовит общий WorkloadScenarioSteps/KubernetesWorkloadSteps через Environment и Fabric8: проверка ConfigMap перед сценарием, lease, рестарт при изменении, восстановление. Чужой lease не снимать.
Приёмка: все согласованные P0 выполнены без отклонений, P1 выполнены либо имеют явное решение по области; есть КАП-доказательства обеих исходных проблем; открытые вопросы не замаскированы допусками assertions. Статус BLOCKED отделять от FAILED/PASSED.

6. Вопросы к АК и расхождения источников

Q1. Данные S2: текст говорит A/C -> O1, B -> O2, но JSON связывает A/B/C одним conditionId с O1. Основной T10 повторяет JSON; раздельная привязка проверяется T01/T19. В S1, пример 2, вводный текст E1 также расходится с JSON; D2 следует JSON и схеме связей. На схемах стр. 23-24 для E1 указано «сработала null», хотя заголовок, диапазон и итоговый JSON дают A. Подтвердить JSON-топологии как эталон.
Q2. Подтвердить отдельно КАП и REST: no-MAIN при allow=true/false; полный ALL при NONE; допустимость отсутствующего expFlags, null и []. S1 явно показывает технический MAIN=[] в КАП. Это не закрывает прежний спор 2690 о публичном MAIN=[]; существующие assertions автоматически не ослаблять. Если иных флагов нет, уточнить точную форму expFlags; требование отсутствия isAlternative однозначно независимо от формы.
Q3. MAPPER: согласовать таблицу isAlternative для полного ALL (сработавшая группа, несработавшая связанная группа, выбранная альтернатива, NONE).
